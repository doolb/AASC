# AI 伪代码翻译

## 任务目标

将用户伪代码翻译为目标语言代码，在保证行为一致的前提下，遵循目标项目的编码规范、目录结构与依赖约束。

默认目标语言为 Unity。用户可显式指定其他目标语言；若未指定，则先在当前文件夹匹配已有平台目录。

## 适用场景

- 根据伪代码快速产出工程化代码
- 在多语言目标之间复用同一份伪代码
- 将业务伪代码落地为可维护的模块化项目
- 在澄清需求后持续迭代伪代码与代码实现

## 项目目录约束

生成代码时，目录结构必须与用户伪代码目录结构一致，并且顶层分为 4 个模块：

目标代码根目录固定为 `{平台名}`（例如 `unity`、`dotnet`、`golang`、`nodejs`）。
即生成路径形如：`{平台名}/hal`、`{平台名}/core`、`{平台名}/framework`、`{平台名}/app`。

目录按需生成规则：若本次未产生任何 `hal` 相关目标代码（含并入后无独立落盘内容），则不要创建 `{平台名}/hal` 文件夹。

- `hal`：语言平台相关代码（运行时封装、平台适配、基础设施接入）
- `core`：公共代码（通用模型、工具类、公共接口、共享逻辑）
- `framework`：模块相关代码（业务能力编排、模块实现骨架、模块间协作）
- `app`：应用相关代码（应用入口、场景装配、应用级配置与流程）

如果用户伪代码已经包含更细分目录，需在 `hal/core/framework/app` 内保持相同层级映射，不得随意合并目录。

模块名一致性规则（必须执行）：

1. 伪代码中的模块标识必须与文件实际路径一致
2. 若文件路径为 `.src/core/...`，则文件内模块名必须为 `core`（`hal/framework/app` 同理）
3. 若不一致，必须先修正伪代码文件（或提示用户确认修正方案）再生成目标代码

`hal` 模块下允许按目标平台继续分层，例如：

- `hal/dotnet`：可指定指令对应的 .NET 平台代码文件
- `hal/unity`：可指定指令对应的 Unity 平台代码文件
- `hal/golang`：可指定指令对应的 Golang 平台代码文件
- `hal/nodejs`：可指定指令对应的 Node.js 平台代码文件
- 其他平台按同样规则扩展（保持命名语义清晰）

## 输入信息收集

在开始翻译前，优先收集以下信息（若用户未提供，则按默认值执行并在结果中说明）：

1. 伪代码所在目录结构（至少区分 `hal/core/framework/app`）
2. 目标语言（可选；例如 Unity / C# / Java / TypeScript / Go）
3. 目标运行时与版本（例如 .NET 8、Node 20、Go 1.22）
4. 功能边界（仅核心逻辑，或包含 I/O、配置、日志、测试）
5. 兼容性要求（接口签名、错误码、输入输出格式、性能目标）
6. 是否保留原命名与注释风格
7. 伪代码语言（支持中文，默认按中文语义解析）

若用户未指定目标语言，按以下顺序处理：

1. 在当前文件夹匹配平台目录（如 `unity` / `dotnet` / `golang` / `nodejs`）
2. 若匹配到唯一平台，则使用该平台
3. 若匹配到多个平台，需让用户确认
4. 若未匹配到平台目录，则默认按 Unity 生成代码

## 伪代码指令约定

为便于稳定触发技能，伪代码开头必须包含技能名标记：

```text
#skill: ai-code-translation
```

技能名支持缩写：`act`。

等效标记：

```text
#skill: act
```

用户也可以手动调用技能并直接提需求，由技能先生成伪代码，再生成目标代码。

推荐调用方式：

```text
/skill ai-code-translation <需求描述>
```

缩写调用方式：

```text
/skill act <需求描述>
```

手动调用后，先输出需求理解与生成计划，并直接生成“中文伪代码草案预览”；伪代码可直接写入 `.src`，无需确认。仅在生成目标代码前请求用户确认。

伪代码写作约束：

默认标准（必须执行）：

- L4 框架：`已有声明` / `新增定义` / `操作流程`
- 中文指令式内容：步骤驱动、可带变量名
- 行尾原因注释：同一行 `//`，优先说明“为什么这样做”

1. 使用中文命令式步骤表达（动词优先）
2. 不使用 `()` 参数式写法
3. 可使用 Markdown 语法组织内容（标题、列表、代码块）
4. 指令式步骤中可使用变量名，推荐采用 `变量 = 动作结果` 形式串联数据流
5. 变量名需语义清晰、前后统一，避免同义多名
6. 默认必须生成变量名（极简单语句除外），用于明确数据流

伪代码注释规则（必须保留）：

1. 注释使用中文，优先说明业务意图与约束条件
2. 注释核心目标是说明“为什么这样做”
3. 注释要简短，避免逐行复述步骤内容
4. 关键分支、边界条件、平台差异处必须有注释
5. 注释需可追踪：必要时附对应模块或路径（如 `hal/unity`、`.src/app/xxx.md`）
6. 禁止空泛注释（如“开始处理”“执行逻辑”）
7. 注释统一使用同一行尾注格式：`// 说明`
8. 注释默认追加在语句后，不单独起行（除非整段说明）

L4 伪代码规范（参考 `程序等级划分.html`，默认启用）：

1. 只写名字，不写类型（例如写 `guild.getMembers()`，不写 `List<Member>`）
2. 优先引用“当前程序已有声明”（`类名.方法名` / `对象.属性`）
3. 新增结构使用英文名 + 字段名，不写类型（例如 `RewardMail { targetId, itemId, count }`）
4. 操作流程使用中文，变量名用于串联数据流
5. 禁止输出完整可运行代码
6. 禁止异常处理样板和工程化防御模板（只保留必要业务分支）
7. 禁止函数封装式输出（流程块替代函数定义）
8. 伪代码建议使用固定分段：`已有声明`、`新增定义`、`操作流程`

优先级规则：当历史规则与 L4 规范冲突时，以 L4 规范为准。

强制门禁规则（必须执行）：

1. 未收到用户明确确认前，禁止生成任何目标代码文件
2. 未收到用户明确确认前，禁止修改现有目标代码文件
3. 未收到用户明确确认前，允许生成并写入中文伪代码（`.src/*.md`）；不落目标代码
4. 只有在用户给出明确确认指令后，才可进入代码生成阶段
5. 以上门禁对所有入口都生效：自然语言需求、`/skill act ...`、`/ai-code-translation ...`、以及直接传入 `.md` 伪代码文件
6. 首轮对话也必须先完成伪代码生成，再进入“待确认”状态；禁止首轮直接生成目标代码
7. 禁止在伪代码生成前请求确认
8. 首轮确认提示前必须已写入至少 1 个 `.src/*.md` 伪代码文件
9. 后续每一轮确认提示前同样必须先完成本轮伪代码写入，并附路径清单
10. 首轮 `.md` 调用（如 `/ai-code-translation xxx.md`）强制两阶段：
    - 阶段A：仅读取/标准化/写入伪代码，并输出待确认选项
    - 阶段B：仅在用户选择 1 或 2 后才允许生成目标代码
11. 若本轮未出现用户选择项（1/2/3/4）或明确确认语句，必须自动判定为“未确认”，并中止代码生成
12. 任何“解析 .md 后直接生成目标代码”的行为视为违规，必须回滚该次生成并重新走确认流程

可视为“明确确认”的示例：`确认`、`可以生成`、`开始生成`、`ok`、`yes`

支持以下特殊指令：

- `/hal`：语言平台相关指令
- `/hal: unity`：仅在 Unity 目标平台生效

伪代码支持在函数和类上使用 `inline` 标注。

- `inline function`：声明“不要生成独立函数代码”
- `inline class`：声明“不要生成独立类代码”

推荐写法示例：

```text
inline function 计算加法
- 读取 输入a
- 读取 输入b
- 返回 输入a 加 输入b
```

或：

```text
function 计算加法 [inline]
- 读取 输入a
- 读取 输入b
- 返回 输入a 加 输入b
```

类标注示例：

```text
inline class DamageRule
```

或：

```text
class DamageRule [inline]
```

Markdown 命令式示例：

```markdown
#skill: act

## framework/战斗流程.md

- 定义流程 结算伤害 // 统一伤害入口，避免分散在多个模块
- 读取 攻击者属性 // 确保后续计算有基础攻击参数
- 读取 防御者属性 // 用于减伤和护盾判定
- 如果 防御者有护盾 // 先消耗护盾，符合战斗规则
  - 先扣减护盾值 // 护盾优先于生命值扣减
- 计算 最终伤害 // 输出本次结算伤害结果
- 写入 战斗日志 // 支持回放与问题排查
```

平台定向指令规则：

1. 当目标语言为 Unity 时，执行 `/hal` 与 `/hal: unity`
2. 当目标语言非 Unity 时，`/hal: unity` 不生效，需跳过并记录
3. 若存在 `/hal: <platform>`，仅在目标平台匹配时执行

`inline` 规则：

1. 标注为 `inline` 的函数，不生成独立函数/方法定义
2. 其逻辑应并入宿主实现，不生成跨文件或独立声明
3. 若存在多个调用点，优先采用“单点并入 + 引用映射”，避免在每个调用点重复展开
4. 标注为 `inline` 的类，不生成独立类定义；其字段/方法需并入宿主类、模块或文件级实现
5. `inline class` 下的 `inline function` 继续按函数展开规则执行
6. 若 `inline` 与平台约束冲突，以平台约束优先，并在输出中记录

`hal` 默认 inline 规则：

1. `hal` 模块内的伪代码默认视为 `inline`（即使未显式标注）
2. `hal` 内函数默认不生成独立函数定义，按“宿主并入”处理
3. `hal` 内类默认不生成独立类定义，按“宿主并入”处理
4. 若用户在 `hal` 中显式要求生成独立实现，需先确认后再例外处理，并记录原因
5. `hal` 默认 inline 禁止“多调用点重复展开”；发现重复展开应回退为单点并入

## 翻译原则

1. 先保证功能等价，再优化代码风格
2. 严格保持伪代码目录映射关系，尤其是 `hal/core/framework/app` 分层
3. 保持函数职责单一，避免翻译后“巨型函数”
4. 优先使用目标语言生态中的标准库与成熟模式
5. 保留关键边界行为：空值、异常、精度、并发、时区、编码
6. 对不可直接映射的伪代码指令，给出明确替代方案和原因
7. 伪代码与目标代码必须保持一致，任一侧变更后需同步更新另一侧
8. AI 自动生成伪代码时，按职责拆分为多个流程块（非函数封装），避免单块大流程
9. 若为单一业务功能需求，伪代码尽量集中在一个 `.md` 文件中维护
10. 生成的目标代码必须包含必要注释，说明模块职责、关键流程与非直观逻辑
11. 目标代码注释中应包含对应伪代码片段或伪代码引用路径，便于双向追踪
12. 一份伪代码可映射为多个目标代码文件，按职责拆分实现（接口、模型、服务、适配层等）

## 执行流程

### 0) 需求转伪代码（支持手动调用）

- 当用户仅提供自然语言需求时，先生成结构化伪代码
- 伪代码根目录固定为 `.src`
- 伪代码必须按 `hal/core/framework/app` 分模块落盘（位于 `.src` 下）
- 生成伪代码文件时，在文件头加入技能名标记：`#skill: ai-code-translation`
- 伪代码文件统一使用 `.md` 扩展名
- 若用户未指定平台，先在当前文件夹执行平台目录匹配，再确定代码输出根目录
- AI 自动生成伪代码时必须使用中文命令式语句
- AI 自动生成伪代码时禁止使用 `()` 参数式写法
- AI 自动生成伪代码时，优先拆分为多个小流程块（每块单一职责，不使用函数封装）
- 伪代码默认采用 `已有声明` / `新增定义` / `操作流程` 三段结构
- 若需求属于单一业务功能，优先生成单文件伪代码（通常放在 `.src/app` 或 `.src/framework`）
- 先生成并预览中文伪代码结构与关键指令，并立即写入 `.src` 目录（无需确认）
- 输出确认提示前，必须附上“本轮已写入伪代码文件路径清单”
- 若用户已给出部分伪代码，则在原文件基础上增量补全
- 若需求不明确，先向用户确认，再更新对应模块伪代码文件

### 0.5) 用户确认门禁（仅针对目标代码，必须执行）

- 仅在“中文伪代码草案已生成并已写入 `.src/*.md`”之后，生成目标代码前，才可请求用户明确确认
- 每一轮对话只要涉及“新增/修改目标代码”，都必须再次提示确认（不能只在第一次提示）
- 即使用户在首轮通过 `/ai-code-translation <xxx.md>` 直接提供伪代码，也必须先输出确认提示
- 后续轮次也必须先完成伪代码落盘，再输出确认提示
- 若用户未确认，只能继续澄清需求或调整伪代码草案
- 确认通过后再执行后续翻译流程（1)~6) 并生成代码文件
- 在目标代码生成前，可询问用户是否同时生成自测代码（如单元测试/最小验证脚本）
- 若用户未明确选择，默认不生成自测代码，并在输出中说明
- 若选择生成自测代码，必须同时生成对应的中文伪代码 `.md` 文件，并保存到 `.src` 的对应模块路径
- 若测试伪代码文件生成失败或缺失，禁止落盘任何自测代码文件
- 确认提示尽量使用“选项列表”让用户直接选择，减少自由输入
- 执行前必须进行确认状态检查：`confirmed = false` 时禁止进入代码生成步骤

### 0.6) 项目伪代码对齐（可选）

- 当用户选择“按当前项目结构对齐伪代码”时，调用 `project-pseudocode-sync`
- 调用后仅允许修改 `.src/**/*.md`，禁止生成或修改目标代码
- 对齐完成后回到本技能，继续输出确认选项并等待用户选择
- 若用户未选择该选项，不主动触发该技能

### 1) 分析伪代码

- 识别入口、依赖、数据流、状态管理与副作用
- 识别伪代码对应的目录层级与模块归属（`hal/core/framework/app`）
- 校验“模块名 vs 文件路径”一致性；发现不一致时先进入修正流程
- 识别平台指令（如 `/hal`、`/hal: unity`）及其生效范围
- 识别函数/类修饰指令（如 `inline`）及其可映射性
- 对 `hal` 模块应用“默认 inline”判定
- 解析中文伪代码语义（动词、条件、循环、异常、输入输出）并建立结构化映射
- 解析 Markdown 结构（标题、列表、代码块）并映射为执行步骤
- 标记语言特性差异点（异步模型、类型系统、内存管理）

### 2) 设计目标实现

- 明确模块拆分与文件结构，确保与伪代码目录一致
- 在 `hal` 下按目标平台落到对应子目录（如 `hal/unity`、`hal/dotnet`、`hal/golang`、`hal/nodejs`）
- 目标代码根目录使用 `{平台名}`，并在其下保持 `hal/core/framework/app` 结构
- 允许将单个伪代码文件拆分为多个目标代码文件，并建立清晰映射关系
- 定义公共接口、数据结构与错误处理策略

### 3) 分批翻译

- 先翻译纯逻辑层，再翻译外部交互层（文件/网络/数据库）
- 每次仅翻译一个可验证单元，避免大段一次性迁移
- 每个翻译单元写入对应目录，禁止跨层乱放文件
- 对单份伪代码的实现可拆分到多个代码文件，拆分依据为职责边界而非行数
- 对平台定向伪代码，仅生成到对应平台子目录
- 所有代码文件必须写入 `{平台名}` 根目录下
- 为新增/修改的目标代码补充必要注释（避免无意义注释）
- 在关键实现处附带“伪代码对应注释”（伪代码摘要或 `.src/*.md` 路径）
- 对 `inline` 函数执行“调用点展开”，禁止生成独立函数定义
- 对 `inline` 类执行“宿主并入”，禁止生成独立类定义
- 对 `hal` 模块按默认 inline 处理，除非用户明确确认例外
- 若出现重复展开，必须收敛为“单点并入 + 引用映射”
- 若 `hal` 最终无落盘文件，跳过 `{平台名}/hal` 目录创建
- 若包含自测代码输出，先写入测试伪代码 `.src/**/*.md`，再写入测试代码文件

### 4) 校验一致性

- 用样例输入比对伪代码预期/目标实现输出
- 补齐单元测试与关键边界测试
- 校验目录结构与伪代码目录一致
- 校验伪代码模块名与 `.src` 文件路径一致
- 校验 `hal` 平台子目录与目标语言一致
- 校验代码根目录为 `{平台名}`
- 若用户未指定平台，记录“平台匹配结果”与最终采用的平台
- 校验按需目录规则：无 `hal` 落盘文件时，`{平台名}/hal` 不存在
- 若生成了自测代码，校验每个测试代码文件均有一一对应的测试伪代码 `.md` 文件
- 若发现历史测试代码缺少测试伪代码，必须在本轮补齐对应 `.src/*.md` 文件
- 记录已知差异与风险

### 5) 处理不明确指令（必须执行）

- 若伪代码指令不明确，必须向用户发起确认
- 确认后需手动更新伪代码内容
- 更新后的伪代码必须保存到对应模块的 `.md` 伪代码文件中（`hal` / `core` / `framework` / `app`）
- 继续翻译时以最新伪代码文件为准

### 6) 双向同步更新（必须执行）

- 当用户修改伪代码时，必须同步更新对应目标代码文件
- 当用户要求直接修改目标代码时，必须同步回写对应伪代码文件
- 同步更新时保持目录映射不变（`hal/core/framework/app`）
- 若无法一一映射，需记录差异并向用户确认后再落盘
- 当存在测试代码但缺少测试伪代码时，必须先补齐测试伪代码再继续后续改动

## 输出格式（建议）

1. 需求理解：用户目标、范围、假设
2. 伪代码清单：新增/修改的伪代码文件路径（含模块归属）
3. 翻译说明：目标语言（含默认值说明）、生成策略
4. 目录映射：伪代码目录 -> 目标代码目录（含 `hal/core/framework/app`）
4.1 文件映射：单个伪代码文件 -> 多个目标代码文件（逐项列出）
5. 代码清单：新增/修改文件路径
6. 差异说明：与伪代码预期不完全一致的点
7. 验证方式：如何运行与测试
8. 同步状态：伪代码与目标代码是否已完全同步
9. 平台指令状态：如 `/hal: unity` 的执行或跳过结果
10. 平台解析来源：用户指定或当前目录匹配结果
11. 确认状态：`待确认（伪代码已写入，目标代码未开始）` 或 `已确认（附用户确认语句）`
12. 修饰映射：如 `inline function` 的展开位置、`inline class` 的并入位置与处理结果
13. hal inline 状态：默认 inline 是否生效、是否存在已确认例外
14. 中文伪代码解析状态：关键语义映射与歧义确认记录
15. 目录按需状态：是否跳过 `{平台名}/hal` 及原因
16. 自测代码状态：是否询问、用户选择、生成文件路径（若有）
17. 伪代码风格检查：命令式合规、`()` 禁用检查、Markdown 结构检查
17.1 伪代码注释检查：是否说明“为什么这样做”、关键分支是否有注释、是否使用同一行 `//` 格式、是否存在空泛注释
18. 测试伪代码状态：是否生成、对应 `.src` 路径、与测试代码映射关系
19. 测试一致性检查：测试代码与测试伪代码一一对应结果
20. 测试伪代码补齐记录：已发现缺失项与补齐文件路径
21. 注释追踪状态：代码注释中的伪代码引用覆盖情况
22. 模块路径一致性：伪代码模块名与文件路径校验结果
23. L4 合规检查：无类型、已有声明引用、新增定义规范、非函数封装

记录规则：伪代码相关改动（含内容与注释）一律不纳入任何变更记录。
输出限制：禁止输出“伪代码更新记录”或“伪代码变更记录”字段。

伪代码路径约定：所有伪代码文件路径以 `.src/` 开头，且文件后缀为 `.md`。
目标代码路径约定：所有目标代码文件路径以 `{平台名}/` 开头。
测试映射约定：每个测试代码文件必须有同名或可追踪映射的 `.src` 测试伪代码文件。

## 常见注意事项

- 动态类型转静态类型时，先收紧核心数据模型
- 浮点计算需检查精度误差与舍入策略
- 异步代码需确认取消、超时与异常传播行为
- 时间处理需统一时区与格式化规则
- 正则表达式在不同语言实现可能存在差异
- 伪代码中缺失输入/输出定义时，先确认再落代码，不要自行假设
- 平台专属指令必须显式标注，避免默认落入错误平台目录
- 推荐统一使用平台目录名：`dotnet` / `unity` / `golang` / `nodejs`
- 中文伪代码中的歧义词（如“处理”“检查”“适配”）必须先确认再实现
- AI 自动生成的伪代码内容必须使用中文描述
- 伪代码必须采用命令式表达，避免声明式函数签名
- 伪代码中禁止使用 `()`，改用“输入/输出/步骤”描述
- 可使用 Markdown 语法增强可读性，但语义必须可解析
- 自动生成伪代码时，优先拆分为可复用的小流程块（非函数封装，保持低耦合）
- 单一业务功能优先单文件伪代码；仅在跨模块依赖明显时再拆分多文件
- 注释要求：优先注释“为什么这样做”，避免逐行复述“代码做了什么”
- 关键代码注释需带伪代码来源（如 `.src/app/xxx.md`）或伪代码步骤摘要
- 若伪代码模块名与路径不一致，优先修正伪代码再继续生成代码
- 单份伪代码拆分多文件时，优先按“模型/接口/实现/适配”分离，避免职责混杂
- 伪代码注释优先写“为什么这样做（业务意图/约束）”，不要逐条重复流程语句
- 伪代码相关改动（含内容与注释）一律不纳入任何变更记录

## 质量门槛

- 代码可编译/可运行

- 目标代码根目录为 `{平台名}`，且所有代码文件均位于该目录下

- 伪代码注释检查通过（说明“为什么这样做”，关键分支有注释，使用同一行 `//`，无空泛注释）

- 未指定平台时，当前目录匹配逻辑执行正确（多候选时已确认）

- 每一轮涉及目标代码变更时，均有独立确认记录
