# 需求等级分析技能（统一版）

## 任务目标

基于 `程序等级划分.html` 对输入需求做分层判级，识别混层与断点，并输出可执行的 L4 改写结果。默认模式为 `enterprise`（第二种）。

## 模式说明

- `standard`：轻量分析，适合日常需求沟通与快速评审
- `enterprise`：企业评审，包含评分、置信度算法与评审结论

## 选择策略（必须）

- 若用户未明确指定模式，先提示可选模式：
  - 1) `standard`
  - 2) `enterprise`（默认）
- 若用户未回复或回复不明确，自动按 `enterprise` 执行
- 若用户已明确指定模式，直接执行，不再二次询问

## 调用方式

```text
/skill analyze-requirement-level mode=standard
```

```text
/skill analyze-requirement-level mode=enterprise
```

若未传 `mode`，默认按 `enterprise` 执行。

## 层级基线

- `L4`：声明级伪代码（变量串联数据流，非可运行代码）
- `L5`：业务流程（规则、状态、步骤）
- `L6`：功能模块（输入输出、约束、接口契约）
- `L7`：系统架构（服务拓扑、通信、中间件、一致性）
- `L8`：领域方案（行业链路与跨组织方案）

## 通用执行流程

### 步骤 1：语义切片

- 将输入拆为最小评审片段（流程、契约、架构、方案）

### 步骤 2：片段判级

- 输出每片段的候选层级与证据片段

### 步骤 3：混层识别

- 标记跨层跳跃与信息断点

### 步骤 4：结论与改写

- 产出主等级/次等级与风险
- 评判“程序应使用哪一级能力”，并判断是否需要下放到 L4
- 生成 L4 三段草案：`已有声明` / `新增定义` / `操作流程`

### 步骤 5：能力级别下放评估（必须）

- 输出 `下放判定`：`无需下放` / `建议下放` / `必须下放`
- 输出 `能力等级`：`L4` / `L5` / `L6` / `L7` / `L8`
- 输出能力判定证据（例如规则密度、契约约束、架构依赖、领域跨度）
- 输出下放后的拆解动作：如何把需求拆到可执行的 L4 表达

### 步骤 6：后续动作询问（必须）

- 完成判级输出后，询问用户是否继续调用 `ai-code-translation`
- 询问格式使用固定选项：
  - 1) 调用 `ai-code-translation`，基于当前 L4 草案进入翻译流程
  - 2) 仅保留本次判级结果，暂不翻译
- 若用户未明确选择，不自动调用 `ai-code-translation`

## standard 模式

### 输出模板

```markdown
## 需求等级结论
- 主等级: Lx
- 次等级: Ly, Lz
- 总体判断: 单层/混层

## 证据
- [Lx] <原句片段>
- [Ly] <原句片段>

## 风险
- 信息断点: <有/无 + 描述>
- 直接开发风险: <高/中/低>

## 能力级别下放评估
- 下放判定: 无需下放 | 建议下放 | 必须下放
- 当前建议能力等级: L4 | L5 | L6 | L7 | L8
- 触发证据: <原句片段>
- 拆解建议: <如何下放到 L4>

## 降级到 L4 建议
### 已有声明
- <类名.方法名 或 对象.属性>

### 新增定义
- <EnglishName> { fieldA, fieldB }

### 操作流程
- <中文操作语句，变量串联数据流>
```

### 质量门槛

- 证据条目不少于 2 条
- 混层输入必须分片段判级
- 结论必须包含风险
- L4 改写必须无类型、无函数封装、非可运行代码
- 必须包含能力级别下放评估，且给出至少 1 条拆解建议
- 必须在输出结尾给出“是否调用 ai-code-translation”的二选一询问

## enterprise 模式

### 评分维度（100 分）

1. `层级清晰度`（25）
2. `证据充分度`（20）
3. `实现完备度`（20）
4. `风险暴露度`（20）
5. `L4 可落地性`（15）

### 置信度算法

`置信度 = (主等级证据权重和 / 全部证据权重和) * 一致性系数`

- 权重：强证据 3，中证据 2，弱证据 1
- 一致性系数：
  - 单层一致：1.00
  - 邻层混合：0.90
  - 跨两层以上混合：0.75
  - 含 L2 与业务混杂：0.65

### 评审结论枚举

- `可开发`
- `需补充`
- `需重构后再评审`

### `需补充`判定的补充点清单（必须）

当结论为 `需补充` 时，必须明确列出待补充项，至少覆盖以下 6 类中的 3 类：

1. `范围与目标`：功能边界、是否包含跨模块联动、明确不做项
2. `输入输出契约`：入参来源、出参结构、字段约束、空值策略
3. `业务规则`：状态流转、优先级、冲突处理、幂等约束
4. `异常与边界`：失败分支、超时重试、回滚策略、极端输入
5. `依赖与约束`：上游系统、配置项、权限、性能/时延预算
6. `验收与观测`：验收标准、测试场景、日志/指标、告警条件

输出每个补充点时需包含：`缺失原因`、`补充建议`、`不补充风险`。

```markdown
- 下放判定: 无需下放 | 建议下放 | 必须下放
- 当前建议能力等级: L4 | L5 | L6 | L7 | L8
- 触发证据: <原句片段>
- 拆解建议: <如何下放到 L4>

- 风险暴露度: x/20

- [Lx|强] <原句片段>

- [输入输出契约] 缺失原因: <描述> | 补充建议: <描述> | 不补充风险: <描述>
- [业务规则] 缺失原因: <描述> | 补充建议: <描述> | 不补充风险: <描述>

## L4 落地草案

- <类名.方法名 或 对象.属性>

### 新增定义
- <EnglishName> { fieldA, fieldB }

### 操作流程
- <中文操作语句，变量串联数据流>
```

### 质量门槛

- 必须包含：证据、评分、结论、L4 草案
- 证据少于 3 条时，不得给出“可开发”
- 置信度 < 0.60 时，只能给“需补充”或“需重构后再评审”
- 存在关键断点时，必须给出至少 2 条修复行动项
- 当结论为“需补充”时，必须给出至少 3 条“需补充项”，且每条都包含缺失原因、补充建议、不补充风险
- 必须给出能力级别下放评估与至少 1 条拆解建议
- 必须在输出结尾给出“是否调用 ai-code-translation”的二选一询问
