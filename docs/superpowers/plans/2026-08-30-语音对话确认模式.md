# 语音对话确认模式 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为唤醒后的普通语音增加全局关闭、手动确认和自动确认三种模式，避免错误 ASR 在确认前污染聊天与 Pi 历史。

**Architecture:** 服务端保存全局确认模式和待确认语音，普通语音在进入聊天前先转为待确认记录。原显示端立即收到完整文本弹窗，TTS 继续走通用路由；确认、取消、30 秒超时或自动确认 7 秒窗口结束后，服务端才决定是否将原始文本送入正常聊天路径。

**Tech Stack:** Node.js/CommonJS 服务端、WebSocket、原生 HTML/CSS/JavaScript、Node test runner。

**Spec:** `docs/design/display-voice-conversation.md`、`docs/spec/display-voice-conversation.md`

## Global Constraints

- 全局确认模式默认关闭，兼容现有普通语音立即聊天行为。
- 内置语音指令、唤醒/退出指令和确认/取消指令不进入对话确认流程。
- 手动确认等待 30 秒；自动确认在 TTS 播放完成后等待 7 秒，仅“取消/拒绝”可以阻止发送。
- 确认前不调用 Pi、不写入聊天历史，确认后使用完整原始 ASR 文本。
- TTS 失败不能立即提交；天气同款弹窗仍显示待确认文本，自动模式随后进入 7 秒取消窗口。
- 控制端设置是全局的，待确认记录保留来源显示端标识。
