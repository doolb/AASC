# 聊天系统重构设计文档

## LLM 三档与双端快选（2026-10-19，源码完成）

控制端和显示端右下角均提供“模型”快选，当前 Provider 与三档选择由服务端共享。档位是调用偏好，不暗示三套独立模型权重。`src/apps/server/modules/chat2api/chat2api-default-model-mappings.js` 中的三档定义兼容旧 LLM 模型名；现在选档将提交给 Chat2API 的请求别名直接写入当前 LLM profile 的模型字段，Chat2API 默认映射负责实际目标。快选服务与 Provider 注册表从这里读取，用户界面不编辑映射。

| 档位 | 中文名 | Qwen 网页目标模型 | 豆包现有模型别名 |
|------|--------|-------------------|------------------|
| mini | 轻量 | Qwen3.6-Flash | doubao（思考0） |
| flash | 普通 | Qwen3.7 | doubao-think → doubao（思考0） |
| pro | 专业 | Qwen3.7-Max | doubao-expert（思考3） |

Qwen 初始档位为 flash，豆包初始档位为 mini。切换 Provider 时恢复它自己的上次档位。当前普通 LLM profile 的 `model` 是模型选择的权威来源，快选时更新控制端“LLM 服务器配置”里当前 profile 的模型名：Qwen 分别写入 `aasc-qwen-mini/flash/pro`，豆包分别写入 `doubao/doubao-think/doubao-expert`。`chat.modelTierSelection` 记忆各 Provider 的档位偏好。豆包轻量和普通的 Chat2API 默认实际目标都是 `doubao`，因此两端按当前模型名即可区分按钮。控制端与显示端通过 `getChatModelTierConfig`、`setChatModelTierSelection` 和 `chatModelTierConfig` 同步权威状态；断线期间不可提交，重连补发。Provider 候选来自当前运行的 Chat2API 代理中已启用且有凭据的账号，并要求 Provider 自身启用且开发映射存在；账号已配置不代表远端仍有效。

模型名按开发维护的名称表直接反查 Provider 和档位，不读取 Chat2API 的映射配置；手工修改模型名或切换 profile 后，两端依当前模型名重算。旧 `Qwen3.6-Flash` 名称仍识别为 Qwen 轻量档，再次选档会把配置字段写成请求别名；未知名称显示原值但不选中档位。手工配置 `doubao-think` 时识别为豆包普通，Chat2API 默认映射实际调用 `doubao`。选择只影响后续普通 LLM 聊天，当前为 Agent profile 时快选不可编辑，角色 Agent 保持角色配置。服务端发起三档请求时再次检查代理和账号；失败返回具体错误，不切换到别的 Provider 或档位。旧 `Qwen3.6-Flash → Qwen3.7` 内置兼容映射已移除，Qwen 三档仍使用各自的专用别名。豆包快选使用现有的 0/0/3 模式请求，不添加未经验证的 Lite 选择键或 model_config 参数。

普通聊天把本次目标交给同一运行中的 Chat2API Responses 服务，复用既有账号调度与会话持久化。AASC 续接指纹包含请求别名及 Provider 地址，切换档位后旧上游引用不会被当作兼容状态复用。面板展示实际提交给 Chat2API 的请求模型名、Provider 与档位；例如 Qwen 轻量显示 `aasc-qwen-mini`，普通显示 `aasc-qwen-flash`。请求名由服务端从已识别的 Provider 和档位计算并随权威快照下发，LLM 配置里保存的模型名仍用于识别档位。Agent 配置显示不适用；未知配置保留原模型名并标记未匹配三档。档位按钮使用当前主题预览的选中和未选中状态：选中为主题强调色渐变、白字和强调色外圈，未选中为中性背景、次要文字和边框，浅色主题同样保持区分。面板预留禁用的“外部登录（后续开放）”按钮和接线方法，本次不启动外部登录。

当前只完成代码与定向测试。Qwen 三个目标是否被真实账号接受、豆包文字是否解除现有上游风控、Offline APK/ADB 两端界面仍需设备和账号验收；上游返回的内部编号不用于推断模型版本。

## 豆包语音括号与协议错误（2026-10-19，源码完成并通过 Node 实网验收）

手动朗读包含全角 `（`、`）` 的回复时，现场连续三次记录 `doubao_speech_protocol`。应用分句器保留括号，Chat2API 豆包语音入口把分句原样传给 VoiceGenie；本次文本也产生独立表情符号分句。在线分句并发生成，现有日志只有整批错误码，无法确定失败分句或上游事件，因此括号是待验证诱因，尚不能归为已证实根因。

用户确认由现有共享分句器处理括号：遇到左括号先结束前文，括号内文字单独分段；遇到右括号结束括号内文字，然后继续后文。全角 `（ ）` 与半角 `( )` 均作为边界，不把括号字形交给语音上游，括号内正文和聊天历史显示文本保留。Chat2API 豆包入口也对直接调用的文本移除这四个括号字符，避免绕过分句器的请求仍原样发送。协议失败时仅记录脱敏的分句序号、状态阶段和事件名称，不记录正文、凭据或原始上游载荷。离线用例与真实账号 Node 验收均已通过。

2026-10-19 使用已保存账号由 Node 向豆包真实发送：短句带全角 `（耳朵通红）` 与去全角括号两次均成功。旧分句器处理现场原文后发起 3 并发、11 条可朗读分句请求，前 10 条成功；末尾半角 `( 轻轻蹭了蹭你的脸颊)` 返回 `doubao_speech_protocol`，脱敏事件为 `stage=sentence event=TTSSentenceEnd`。单独对照该句：去半角括号成功合成 200100 字节 WAV，保留半角括号复现同码且上游未返回音频。加入半角括号分句和豆包入口清理后，现场原文再次 3 并发发送，11/11 成功；直接通过 Chat2API 语音服务发送带半角括号的末句也成功生成 200100 字节 WAV。

## Chat2API 错误显示端提示（2026-10-18，待确认）

2026-10-18 从本机 `127.0.0.1:8083/v1/responses` 用当前豆包映射发起全新流式会话，代理返回 HTTP 200 的 SSE：先 `response.created`，再 `response.failed`，错误为 `doubao_risk_control`。这次请求没有旧会话引用，证明当前安全验证错误不依赖旧会话是否存在。测试没有取得完整回复，也没有继续发第二轮。

随后选取本机保存的最近一个 `ready` 豆包旧会话，用该会话状态的内存副本直接调用现有豆包适配器。请求确认携带与保存记录一致的上游 `conversation_id`，且 `need_create_conversation=false`；结果仍为 `doubao_risk_control`（403）。旧会话存在且确实发出原生续接请求，本次风险控制并非仅由本地引用缺失造成；本地会话存储未被这次探测改写。网页账号验证的触发条件由豆包决定，官网正常可发送而非官方接口仍被拦截时，不能假定有可手动输入的验证 Token。

当前适配器在 Node 内以 Axios 发送官网 `/chat/completion` 请求，复用保存时采集的 Cookie、CSRF、设备 ID、Web ID、指纹值和 User-Agent，并自行生成 `web_tab_id`；它不是当前浏览器标签页的 `fetch`。即使地址、请求体与当时网页抓包接近，浏览器当前登录状态、Cookie 更新、运行环境及网络请求特征仍可能与这份保存快照不同。新旧会话均 403 只能确认上游拒绝当前 Node 请求；具体命中的检查项缺少上游证据，不归因为单一字段或旧会话失效。

显示端聊天窗自行发起的聊天，已有 `chatResponse.success=false` 错误状态和文字。显示端语音来源及控制端指定显示端的普通聊天，`handleChatMessage` 失败后目前仅通过 `sendToControl` 回报，目标显示端看不到原因。拟在失败回调中向本轮相关显示端发独立错误消息，包含请求 ID 和公开错误文字；显示端使用现有旋转适配弹窗醒目显示，即使聊天窗展开也可见。按当前请求和在线目标过滤，迟到的旧请求错误不得覆盖新回复，不向无关显示端广播。待用户确认后实施。

## Responses 流错误透传（2026-10-18，源码完成）

本机 Chat2API 代理会先向 Responses 客户端发送 `response.created`。此后上游报错时，HTTP 响应头已发出，旧代理直接销毁连接，客户端只看到 `socket hang up`，无法区分原生会话失效与其他上游故障。即使客户端已有一次断连重试，也可能继续得到同一条笼统错误。

代理在已开始的 SSE 流发生错误时发送 `response.failed`，附规范化错误码、HTTP 状态和可公开消息，再结束流；不能发送完成标记。流开始前继续使用原 JSON 错误响应，客户端已断开时不写入。客户端据事件里的状态和错误码沿用已有的会话重建判断。代理日志只记录失败阶段、错误码和状态，不记录聊天正文或凭据；本机服务已重启加载，真实账号恢复仍待验证。

本机重启后，真实请求已显示“豆包网页要求安全验证，请在官网处理后重试”，对应适配器固定错误 `doubao_risk_control`（403），说明原先被 `socket hang up` 掩盖的错误类别已经显露。该错误需要当前账号在官网完成安全验证；一次性验证码只输入官网验证页。`doubaochat` 的手动账号字段是完整豆包网页 Cookie，不是单个 Token 或验证码；文字聊天还要求同账号登录上下文的 `nodeProfile`，单填 Cookie 不能补齐。完成验证后重试聊天以验收恢复，不能把风控视为会话引用失效并自动绕过。

仅凭 403 不能确定该次请求是否携带了豆包旧会话 ID。本地找不到 Responses 引用使用 404，豆包续接状态不确定或身份不匹配使用 409；上游对特定旧 ID 的返回原因仍需请求级证据，不能由 403 反推“会话不存在”。

## Responses 流式连接中断恢复（2026-10-18，源码完成）

显示端说出“我们来玩五子棋。”后，语音门控和临时会话路由均已接受输入，但 Responses 流式请求报告 `socket hang up`，本轮无法得到回复。该日志只能确认连接中断，不能单凭日志确定是上游关闭、代理重启还是网络断开。旧逻辑只对会话引用失效自动重建，普通连接中断直接报错；客户端也可能把没有 `response.completed` 或 `[DONE]` 的正常 HTTP 结束误认作成功。

对可识别的连接中断，在尚未向控制端输出正文时，清除旧 Responses 上游引用，使用本地完整历史和本轮输入新建上游会话，短暂退避后最多重试一次。若本轮已有正文，直接报告错误并清除不确定的旧引用，让下一轮新建上游会话，避免当前页面出现两份回复。控制端及临时会话 ID、已完成的本地历史保持；鉴权、参数和普通业务错误不自动重试。收到 `response.completed` 或 `[DONE]` 才视为流完成；未收到完成标记便结束的 SSE 流记为连接提前结束。离线模拟已覆盖建连中断、部分正文中断和完成事件；真实网络环境待验收。

## 豆包失效上游会话自动恢复（2026-10-17，已实现）

当豆包原生续接返回 `doubao_session_uncertain`，聊天服务将当前 Responses 引用视为失效，删除本地持久化引用，再以当前已选历史和本轮输入建立新的豆包上游会话。控制端原有会话、历史和显示范围继续使用原值；恢复成功后保存新的 Responses 引用。

非流式请求和尚未输出正文的流式请求最多自动重试一次。流式请求已输出正文时只清除失效引用并报告本轮失败，后续请求再建立新上游会话，避免同一轮在控制端出现重复内容。其他错误仍由原错误处理流程返回。

## 概述

重构现有的聊天系统，支持群聊和私聊模式，统一管理所有角色（系统、AI助手、显示端、控制端）的聊天记录，并整合语音播报和搜索功能。

## 系统架构

### 角色定义

| 角色 | 标识格式 | 说明 |
|------|----------|------|
| 系统 | `系统` | 系统消息、指令响应 |
| AI助手 | `{助手名字}` | 各个AI聊天助手 |
| 显示端 | `{显示端名字, IP}` | 显示端语音输入 |
| 控制端 | `{控制端名字, IP}` | 控制端语音/文本输入 |

### 聊天模式

1. **群聊模式**（默认）
   - 所有消息广播给所有参与者
   - 系统和AI助手根据规则响应
   - 语音播报在显示端播放

2. **私聊模式**
   - 只与指定的AI助手通信
   - 发起：`私聊{助手名字}`
   - 退出：`退出私聊` 或切换私聊对象
   - Pi Agent 模式下每个私聊角色使用独立进程；切换群聊或角色时重置旧 Pi 会话，不混入其他模式历史

3. **指令模式**（新增）
   - 语音输入过滤模式，通过 `打开指令模式`/`关闭指令模式` 切换
   - 指令模式 ON：只处理内置命令，LLM 需要唤醒词（助手名字）
   - 私聊模式下指令模式只放行 "退出私聊"，其余全走 LLM
   - 指令模式状态持久化到 config.json
   - 模式切换时广播到所有控制端保持 UI 同步

4. **工作 AI 角色模式**
   - 与选中的工作 AI 角色使用独立上下文和历史
   - 控制端可以通过工作组页签进入，也可以通过“退出工作组”返回群聊

5. **语音修复模式**
   - 显示端使用共用明文语音密码进入，不走普通聊天 Agent。
   - 进入后每条请求必须确认，再交给配置的工作 AI 角色；角色从 `aiRoles` 列表选择，支持多角色。
   - 修复期间暂停普通 TTS，修复提示和工作 Agent 回复保持可播报。

### 控制端聊天模式页签

群聊、私聊和工作组页签都必须是可点击的模式入口。群聊页签点击后统一调用 `setMode('group', null)`，清理私聊目标、工作组角色和私聊会话状态，再刷新当前群聊历史。私聊模式和工作组模式在模式指示区分别显示“退出私聊”和“退出工作组”按钮，两个按钮都返回群聊，避免用户只能依赖语音命令退出当前上下文。

### 消息格式

```
{角色}: {消息内容}
```

示例：
```
系统: 早上好！今天天气晴朗
小爱: 你好！有什么可以帮助你的吗？
显示端(客厅, 192.168.1.100): 今天天气怎么样
控制端(手机, 192.168.1.50): 播放音乐
```

### 聊天传输协议配置

聊天设置中的“调用协议”属于具体 LLM 服务器配置，不属于全局聊天配置。每个 profile 使用自己的协议、Chat Completions API URL 和 API Key：

- `protocol=openai-responses` 时，使用当前 LLM profile 的 `apiUrl` 和 `apiKey`；将 `apiUrl` 中的 `/chat/completions` 后缀去掉后请求同一服务的 `/responses`。
- `protocol=openai-completions` 时，使用当前 LLM profile 的 `apiUrl`、`apiKey` 和模型配置，请求 profile 中保存的 Chat Completions 地址。
- profile 中的 `apiUrl` 标签明确写成“Chat Completions API URL”，并提示 Responses 模式会复用该地址的服务基址和同一个 API Key。
- 控制端通过现有 `/api/chat/profiles` 配置流程读写 profile 的协议字段；聊天设置页面通过 `/api/chat/config` 只编辑系统提示词和全局 Agent 后端等聊天级设置。服务端保留旧的 `apiUrl`、`model` 等字段作为无 profile 配置的兼容回退，正常请求优先使用当前 profile。
- 旧配置中的全局 `chat.protocol` 仅在启动迁移时作为缺少 profile 协议的默认值；全局 `responsesBaseUrl`、`responsesApiKey` 会被忽略，不再作为请求来源。

### 1. 系统指令

系统指令用于处理特定关键词触发的组合操作。

#### 内置指令

|------|------|----------|

| `私聊{助手名字}` | 进入私聊模式 | 已实现 |
| `退出私聊` | 退出私聊模式 | 已实现 |
| `提醒{时间} {内容}` | 设置提醒 | 已实现 |
| `每天/每周/每月/每年提醒{时间} {内容}` | 设置重复提醒 | 已实现 |
| `报时` / `现在几点` | 播报当前时间 | 已实现 |
| `开启报时` | 开启整点报时功能 | 已实现 |

| `拒绝` / `取消` | 取消待确认操作 | 已实现 |
| `{助手名字}{消息}` | 与指定助手对话 | 已实现 |

#### 指令处理流程

```
用户输入
    ↓
handleSystemCommand() 检查系统指令
    ├─ 系统帮助 → 返回帮助文本
    ├─ 私聊{名字} → 切换私聊模式
    ├─ 退出私聊 → 切换群聊模式
    └─ 自定义指令 → executeCommands()
    ↓
指令模式检查（新增，系统指令后）
    ├─ 指令模式 OFF → 走原有流程
    └─ 指令模式 ON:
       ├─ 私聊模式 → 发私聊助手 LLM（已无退出私聊）
       └─ 群聊模式:
          ├─ 含助手名字 → 去前缀发 LLM
          ├─ 内置命令 → 继续走原有处理（取消/提醒/报时/天气等）
          └─ 非内置命令 → 忽略
    ↓
processVoiceCommand() 处理其他命令
    ├─ 拒绝/取消 → handleCancelCommand()
    ├─ 提醒 → handleReminderCommand()
    ├─ 报时 → handleTimeAnnounceCommand()
    ├─ 搜索 → handleSearchCommand()
    ├─ 助手名字 → 返回聊天请求
    └─ 其他 → 返回默认聊天
```

当控制端高级指令路由设置为 `llm` 且当前 profile 为 Pi Agent 时，群聊中的天气/搜索关键词不再触发控制端旧的多处理器；消息只交给当前 Pi 对话。路由设置为 `system` 时保持原有内置处理；普通 LLM profile 的行为不变。

#### 自定义指令配置

在控制端配置指令组合：

```json
{
```

### 2. 语音播报增强

AI/Agent 回复按对应聊天模板的 Provider 和音色覆盖系统 AI 默认；文本阅读使用独立配置；报时、状态提示、任务结果、错误提示和控制端自定义播报使用系统播报配置。国内千问网页朗读仅用于 AI/Agent 回复。详细归属和优先级见 [Provider 设计](tts-providers.md)。

#### 播报规则
- **所有聊天消息都要进行语音播报**
- 根据当前选择决定播报到哪个设备
- 播报内容包括：系统消息、AI助手回复、用户消息确认等

#### 显示端播报（默认）
- 所有语音播报在显示端播放
- 同时显示文本内容
- 需要选择显示端才能播报

#### 控制端播报
- 当没有显示端连接时，在控制端播放
- 当勾选"在控制端播放语音"选项时，在控制端播放
- 使用 Web Speech API 或 Audio 播放

#### 播报流程
```
聊天消息生成
    ↓
检查播报目标
    ├─ playOnControl = true → 控制端播放
    ├─ displayId 存在 → 显示端播放
    └─ 无显示端 → 控制端播放
    ↓
生成 TTS 音频
    ↓
发送到目标设备播放
```

## 消息流程

### 流式请求上下文

控制端发送每一条 LLM 聊天消息时生成唯一 `requestId`。服务端处理普通群聊/私聊 LLM 请求时，必须将该请求号透传到每一条 `chatChunk` 增量消息和最终 `chatResponse` 完成/失败消息，保证控制端可以把异步回包归属到当前流式消息；没有请求号的历史内部调用仍保持协议兼容。

### 群聊模式流程

```
用户输入 -> 解析指令 -> 
  如果是系统指令:
    系统处理 -> 生成系统消息 -> 广播
  如果是搜索:
    执行搜索 -> 生成结果消息 -> 广播
  如果是聊天:
    AI助手响应 -> 生成助手消息 -> 广播
    -> 语音播报
```

### 私聊模式流程

```
用户输入 -> 
  如果是"退出私聊":
    退出私聊模式 -> 生成系统消息
  否则:
    发送给指定AI助手 -> 生成助手消息
```

## LLM Profile 与 Pi Agent 路由

聊天请求统一经过服务端聊天路由：

```text
控制端输入
    ↓
确定性内置命令识别
    ├─ 已识别 → 现有服务器命令处理
    └─ 未识别 → 当前 profile
                    ├─ mode=llm → OpenAI 兼容接口
                    └─ mode=agent/backend=pi → 服务器托管 Pi RPC
```

每个 LLM profile 独立保存 `mode`、服务器地址、模型和凭据。Agent 请求会收到当前模板系统提示词、当前 profile/template 的上下文记录和当前用户消息。模板的 `permissionProfile` 由控制端直接设置；服务器只接受枚举策略并映射固定白名单，当前策略为 `readonly`，允许文件读取/搜索和受限网络查询，不允许 shell、编辑或写入文件。

未来扩展服务器内置命令时，Pi Runtime 复用聊天路由，但命令工具必须由服务器显式注册并使用独立权限策略，不能由聊天文本或模板内容动态生成任意 shell 命令。

## 私聊模板与测试隔离修复

聊天模板是控制端私聊入口和历史筛选的来源。模板测试不得把临时模板持久化到用户目录，否则服务重启后模板标签消失，但 `chat-history-*.json` 中的私聊记录仍然存在。

模板设置接口支持仅更新内存的测试选项 `persist: false`；生产 API 继续默认持久化。启动时保留已有私聊历史对应的模板入口，避免历史记录因模板配置被清空而不可见。

## 群聊全部角色模板

1. 群聊请求统一读取当前控制端“模板”列表，将所有有效角色的名称和 `template` 内容组合为一个群聊系统提示词。
2. 群聊用户消息保持原样发送；即使消息包含角色名前缀，也不删除前缀、不选择单个角色模板。
3. 群聊历史继续使用统一的群聊会话；私聊仍只使用目标角色模板和对应私聊历史。
4. 子显示端语音和控制端文本都遵循同一群聊模板规则，角色名只用于语音输入的唤醒/接受判断，不改变消息内容。

## 群聊历史遗留工具调用异常（暂不处理）

已确认一个待处理问题：未指定角色的群聊使用统一 `group/default` 历史时，旧历史中可能包含来源于旧工具调用流程的未闭合 Chat2API 工具调用文本。上游流式接口发生错误时可能返回 `[Error: write after end]`，当前流程会把它当作普通助手文本并触发 TTS。该问题已记录，暂不修改历史数据和处理逻辑。
## 显示端语音普通聊天复用正常路径

显示端语音普通文本与控制端文本共享 `handleChatMessage()`、请求号、流式回包和历史写入逻辑。服务端在进入聊天流前向控制端发送 `chatInput`，控制端仅创建正常聊天的临时用户/助手消息节点，不重复提交请求。服务端同时记录来源 `displayId`，完成响应时向来源显示端发送带完整 `detailText` 的 `voiceCommand` 弹窗；TTS 按来源显示端优先、在线 `voicePlayback` 能力兜底的单目标动态规则发送。

控制端收到成功的 `chatResponse` 后，以服务端最终历史作为普通群聊/私聊的显示依据；临时对话回包同时携带完成后的临时会话快照，控制端先更新快照，再重绘消息列表。最终渲染不依赖此前创建的流式 DOM 节点顺序，使实时结果和页面刷新后的历史顺序一致。临时助手消息快照保留正文、思考内容和语音文本，保持历史消息操作一致。

## 聊天历史安全持久化

普通聊天保存只更新当前消息所在的群聊或私聊目标文件，不再根据内存中缺失的会话文件执行自动删除。显式清空、删除会话和替换导入需要明确模式、目标和会话 ID，并在变更前保留配置快照。系统按上海时区每天保留上一天 `aasc-user` 下所有持久化配置的一份快照；控制端可以导出/导入聊天历史和整个配置目录。

清空私聊会话时，本地消息历史和对应的 Responses 续接引用必须同时失效。续接引用以 profile、模板、模式、目标和会话 ID 隔离；清空指定角色的指定私聊会话时，删除所有 profile/模板下属于该会话的引用并持久化，其他角色和同角色其他会话继续保留。下一次私聊用清空后的本地历史建立新上游会话，避免旧 `previous_response_id` 把已清空内容带回来。

## 模式切换审计日志

群聊、私聊和其他聊天模式的切换必须在服务端统一记录，便于定位重启后模式异常变化。日志只记录实际发生的模式或私聊目标变化，不记录同一状态的重复同步。

控制端通过 WebSocket 保存模式时携带来源标识：页签/按钮使用 `controlManual`，文本系统命令使用 `controlCommand`，控制端语音命令使用 `controlVoice`，收到服务端广播后的被动同步使用 `serverSync`。显示端语音状态机直接切换服务端模式时使用 `displayVoice`，同时记录触发切换的 `displayId`。

服务端日志包含旧模式、新模式、旧/新私聊目标、来源和可用的 `displayId`。服务端是唯一的实际切换审计入口，控制端本地不额外输出重复的状态切换日志。

## 聊天配置与历史兼容

聊天历史消息会记录写入时的 `profileName`。切换或恢复 LLM profile 时不得删除历史文件；历史查询应继续返回已持久化的旧 profile 消息，避免配置变更被误判为聊天记录丢失。恢复已有 profile 时，`activeProfile` 与 `llmProfiles` 必须保持一致；配置文件只恢复聊天路由字段，不覆盖 TTS、ASR、语音窗口等其他运行参数。

聊天协议配置归属于 profile：`protocol`、`apiUrl` 和 `apiKey` 必须从当前 profile 一起读取，Responses 模式由 `apiUrl` 派生服务基址。恢复 profile 或切换 profile 时，协议、地址和密钥必须同步切换；旧全局 `responsesBaseUrl`、`responsesApiKey` 会被忽略，不继续参与请求。

聊天设置外部“保存设置”只负责全局聊天字段。该入口不得提交或覆盖 `llmProfiles`、`activeProfile` 以及 profile 内的协议、地址、模型和密钥；LLM profile 只能通过 profile 专用保存接口更新。服务端保存全局字段时必须合并到已有 `config.chat`，保留 profile 配置原值，避免规范化返回值把多个 profile 的协议意外改成同一个 Responses 协议。

## 临时角色选择消息注册约束

临时角色选择使用 WebSocket 消息 startTemporaryConversation。该消息必须同时存在于服务端控制端消息类型注册表和统一 Fallback 处理器中；只实现 Fallback 分支而未注册消息类型时，WebSocket 层会提前拒绝请求，控制端会一直停留在“切换中”状态。新增控制端消息时，注册表、处理器、控制端错误回包和回归测试必须一起更新。

## 临时对话单角色绑定与控制端选择

1. 临时对话仍是服务端唯一的全局会话；新的语音唤醒或控制端角色选择会替换旧临时会话，并清空旧临时历史。
2. `小爱` 等临时唤醒词不写死为命令，必须沿用服务端当前自动匹配到的角色名。服务端在创建临时会话时记录 `roleName` 和 `templateId`，后续请求只按该快照选择角色定义。
3. 临时会话的系统提示词只包含被唤醒角色对应的模板定义和基础提示词，不再调用群聊的全部角色提示词；“开始对话”进入的普通群聊仍保留全部角色定义。
4. 控制端临时页签增加当前角色选择器。选择角色通过 `startTemporaryConversation` 请求服务端创建/替换临时会话，服务端校验模板并广播权威会话快照；普通临时聊天消息只发送当前 `temporaryConversationId`，不发送角色提示词。
5. 控制端刷新或多个控制端并行操作时，以服务端广播的 `temporaryConversation` 快照为准；没有当前角色和会话 ID 时禁止发送，避免消息落入未绑定角色的临时会话。
6. 控制端临时页签用下拉菜单切换历史临时会话；选项显示开始时间、角色和消息数，并始终提供“当前对话”选项。查看历史时只读，选择当前对话后恢复实时消息和发送能力。
