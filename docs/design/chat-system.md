# 聊天系统重构设计文档

## 概述

重构现有的聊天系统，支持群聊和私聊模式，统一管理所有角色（系统、AI助手、显示端、控制端）的聊天记录，并整合语音播报和搜索功能。

## 系统架构

### 角色定义

| 角色 | 标识格式 | 说明 |
|------|----------|------|
| 系统 | `系统` | 系统消息、指令响应 |
| AI助手 | `{助手名字}` | 各个AI聊天助手 |
| 显示端 | `{显示端名字, IP}` | 显示端语音输入 |
| 控制端 | `{控制端名字, IP}` | 控制端语音/文本输入 |

### 聊天模式

1. **群聊模式**（默认）
   - 所有消息广播给所有参与者
   - 系统和AI助手根据规则响应
   - 语音播报在显示端播放

2. **私聊模式**
   - 只与指定的AI助手通信
   - 发起：`私聊{助手名字}`
   - 退出：`退出私聊` 或切换私聊对象
   - Pi Agent 模式下每个私聊角色使用独立进程；切换群聊或角色时重置旧 Pi 会话，不混入其他模式历史

3. **指令模式**（新增）
   - 语音输入过滤模式，通过 `打开指令模式`/`关闭指令模式` 切换
   - 指令模式 ON：只处理内置命令，LLM 需要唤醒词（助手名字）
   - 私聊模式下指令模式只放行 "退出私聊"，其余全走 LLM
   - 指令模式状态持久化到 config.json
   - 模式切换时广播到所有控制端保持 UI 同步

4. **工作 AI 角色模式**
   - 与选中的工作 AI 角色使用独立上下文和历史
   - 控制端可以通过工作组页签进入，也可以通过“退出工作组”返回群聊

5. **语音修复模式**
   - 显示端使用共用明文语音密码进入，不走普通聊天 Agent。
   - 进入后每条请求必须确认，再交给配置的工作 AI 角色；角色从 `aiRoles` 列表选择，支持多角色。
   - 修复期间暂停普通 TTS，修复提示和工作 Agent 回复保持可播报。

### 控制端聊天模式页签

群聊、私聊和工作组页签都必须是可点击的模式入口。群聊页签点击后统一调用 `setMode('group', null)`，清理私聊目标、工作组角色和私聊会话状态，再刷新当前群聊历史。私聊模式和工作组模式在模式指示区分别显示“退出私聊”和“退出工作组”按钮，两个按钮都返回群聊，避免用户只能依赖语音命令退出当前上下文。

### 消息格式

```
{角色}: {消息内容}
```

示例：
```
系统: 早上好！今天天气晴朗
小爱: 你好！有什么可以帮助你的吗？
显示端(客厅, 192.168.1.100): 今天天气怎么样
控制端(手机, 192.168.1.50): 播放音乐
```

## 功能设计

### 1. 系统指令

系统指令用于处理特定关键词触发的组合操作。

#### 内置指令

| 指令 | 说明 | 实现状态 |
|------|------|----------|
| `系统帮助` | 显示所有可用指令 | 已实现 |
| `私聊{助手名字}` | 进入私聊模式 | 已实现 |
| `退出私聊` | 退出私聊模式 | 已实现 |
| `提醒{时间} {内容}` | 设置提醒 | 已实现 |
| `每天/每周/每月/每年提醒{时间} {内容}` | 设置重复提醒 | 已实现 |
| `报时` / `现在几点` | 播报当前时间 | 已实现 |
| `开启报时` | 开启整点报时功能 | 已实现 |
| `关闭报时` | 关闭整点报时功能 | 已实现 |
| `搜索{关键词}` | 搜索信息 | 已实现 |
| `拒绝` / `取消` | 取消待确认操作 | 已实现 |
| `{助手名字}{消息}` | 与指定助手对话 | 已实现 |

#### 指令处理流程

```
用户输入
    ↓
handleSystemCommand() 检查系统指令
    ├─ 系统帮助 → 返回帮助文本
    ├─ 私聊{名字} → 切换私聊模式
    ├─ 退出私聊 → 切换群聊模式
    └─ 自定义指令 → executeCommands()
    ↓
指令模式检查（新增，系统指令后）
    ├─ 指令模式 OFF → 走原有流程
    └─ 指令模式 ON:
       ├─ 私聊模式 → 发私聊助手 LLM（已无退出私聊）
       └─ 群聊模式:
          ├─ 含助手名字 → 去前缀发 LLM
          ├─ 内置命令 → 继续走原有处理（取消/提醒/报时/天气等）
          └─ 非内置命令 → 忽略
    ↓
processVoiceCommand() 处理其他命令
    ├─ 拒绝/取消 → handleCancelCommand()
    ├─ 提醒 → handleReminderCommand()
    ├─ 报时 → handleTimeAnnounceCommand()
    ├─ 搜索 → handleSearchCommand()
    ├─ 助手名字 → 返回聊天请求
    └─ 其他 → 返回默认聊天
```

当控制端高级指令路由设置为 `llm` 且当前 profile 为 Pi Agent 时，群聊中的天气/搜索关键词不再触发控制端旧的多处理器；消息只交给当前 Pi 对话。路由设置为 `system` 时保持原有内置处理；普通 LLM profile 的行为不变。

#### 自定义指令配置

在控制端配置指令组合：

```json
{
  "commands": {
    "早上好": ["今天天气", "今日提醒", "搜索1", "搜索2"],
    "晚安": ["关闭所有媒体", "设置明天闹钟"]
  }
}
```

当用户说"早上好"时，系统依次执行配置的指令。

### 2. 语音播报增强

#### 播报规则
- **所有聊天消息都要进行语音播报**
- 根据当前选择决定播报到哪个设备
- 播报内容包括：系统消息、AI助手回复、用户消息确认等

#### 显示端播报（默认）
- 所有语音播报在显示端播放
- 同时显示文本内容
- 需要选择显示端才能播报

#### 控制端播报
- 当没有显示端连接时，在控制端播放
- 当勾选"在控制端播放语音"选项时，在控制端播放
- 使用 Web Speech API 或 Audio 播放

#### 播报流程
```
聊天消息生成
    ↓
检查播报目标
    ├─ playOnControl = true → 控制端播放
    ├─ displayId 存在 → 显示端播放
    └─ 无显示端 → 控制端播放
    ↓
生成 TTS 音频
    ↓
发送到目标设备播放
```


### 4. 搜索功能整合

移除独立的搜索页面，将搜索功能整合到聊天系统：
- 搜索指令：`搜索{关键词}`
- 搜索结果显示在聊天记录中
- 搜索历史作为聊天记录的一部分

### Markdown 消息显示

控制端聊天消息统一支持 Markdown 显示，范围包括用户消息、普通 LLM 回复、群聊消息、私聊消息和工作 AI 角色消息。输入框继续使用纯文本输入，不提供 Markdown 编辑器或额外格式化按钮。

每条用户消息提供“删除本轮”操作。服务端按消息 ID 删除该用户消息及其紧随的助手回复，允许删除中间任意一轮；若助手尚未回复，则只删除用户消息，不影响其他历史。

- 历史消息和流式消息使用同一个前端渲染器，避免刷新前后显示效果不一致。
- 支持标题、粗体、斜体、删除线、列表、引用、表格、代码行、代码块、分隔线和链接等常用语法。
- 原始 HTML 只作为文本显示；链接仅允许 `http`、`https`、`mailto`、站内路径和锚点，拒绝 `javascript`、`vbscript`、`data` 等危险协议。
- 流式消息在 Markdown 结构尚未闭合时也能按当前文本渲染；代码块未闭合时按代码块暂存，后续内容到达后自然更新。
- 渲染器只生成受控标签，聊天内容不直接拼接未经转义的 HTML。

## 消息流程

### 流式请求上下文

控制端发送每一条 LLM 聊天消息时生成唯一 `requestId`。服务端处理普通群聊/私聊 LLM 请求时，必须将该请求号透传到每一条 `chatChunk` 增量消息和最终 `chatResponse` 完成/失败消息，保证控制端可以把异步回包归属到当前流式消息；没有请求号的历史内部调用仍保持协议兼容。

### 群聊模式流程

```
用户输入 -> 解析指令 -> 
  如果是系统指令:
    系统处理 -> 生成系统消息 -> 广播
  如果是搜索:
    执行搜索 -> 生成结果消息 -> 广播
  如果是聊天:
    AI助手响应 -> 生成助手消息 -> 广播
    -> 语音播报
```

### 私聊模式流程

```
用户输入 -> 
  如果是"退出私聊":
    退出私聊模式 -> 生成系统消息
  否则:
    发送给指定AI助手 -> 生成助手消息
```

## LLM Profile 与 Pi Agent 路由

聊天请求统一经过服务端聊天路由：

```text
控制端输入
    ↓
确定性内置命令识别
    ├─ 已识别 → 现有服务器命令处理
    └─ 未识别 → 当前 profile
                    ├─ mode=llm → OpenAI 兼容接口
                    └─ mode=agent/backend=pi → 服务器托管 Pi RPC
```

每个 LLM profile 独立保存 `mode`、服务器地址、模型和凭据。Agent 请求会收到当前模板系统提示词、当前 profile/template 的上下文记录和当前用户消息。模板的 `permissionProfile` 由控制端直接设置；服务器只接受枚举策略并映射固定白名单，当前策略为 `readonly`，允许文件读取/搜索和受限网络查询，不允许 shell、编辑或写入文件。

未来扩展服务器内置命令时，Pi Runtime 复用聊天路由，但命令工具必须由服务器显式注册并使用独立权限策略，不能由聊天文本或模板内容动态生成任意 shell 命令。

## 私聊模板与测试隔离修复

聊天模板是控制端私聊入口和历史筛选的来源。模板测试不得把临时模板持久化到用户目录，否则服务重启后模板标签消失，但 `chat-history-*.json` 中的私聊记录仍然存在。

模板设置接口支持仅更新内存的测试选项 `persist: false`；生产 API 继续默认持久化。启动时保留已有私聊历史对应的模板入口，避免历史记录因模板配置被清空而不可见。

## 群聊全部角色模板

1. 群聊请求统一读取当前控制端“模板”列表，将所有有效角色的名称和 `template` 内容组合为一个群聊系统提示词。
2. 群聊用户消息保持原样发送；即使消息包含角色名前缀，也不删除前缀、不选择单个角色模板。
3. 群聊历史继续使用统一的群聊会话；私聊仍只使用目标角色模板和对应私聊历史。
4. 子显示端语音和控制端文本都遵循同一群聊模板规则，角色名只用于语音输入的唤醒/接受判断，不改变消息内容。

## 群聊历史遗留工具调用异常（暂不处理）

已确认一个待处理问题：未指定角色的群聊使用统一 `group/default` 历史时，旧历史中可能包含来源于旧工具调用流程的未闭合 Chat2API 工具调用文本。上游流式接口发生错误时可能返回 `[Error: write after end]`，当前流程会把它当作普通助手文本并触发 TTS。该问题已记录，暂不修改历史数据和处理逻辑。
## 显示端语音普通聊天复用正常路径

显示端语音普通文本与控制端文本共享 `handleChatMessage()`、请求号、流式回包和历史写入逻辑。服务端在进入聊天流前向控制端发送 `chatInput`，控制端仅创建正常聊天的临时用户/助手消息节点，不重复提交请求。服务端同时记录来源 `displayId`，完成响应时向来源显示端发送带完整 `detailText` 的 `voiceCommand` 弹窗；TTS 按来源显示端优先、在线 `voicePlayback` 能力兜底的单目标动态规则发送。

## 聊天历史安全持久化

普通聊天保存只更新当前消息所在的群聊或私聊目标文件，不再根据内存中缺失的会话文件执行自动删除。显式清空、删除会话和替换导入需要明确模式、目标和会话 ID，并在变更前保留配置快照。系统按上海时区每天保留上一天 `aasc-user` 下所有持久化配置的一份快照；控制端可以导出/导入聊天历史和整个配置目录。

## 模式切换审计日志

群聊、私聊和其他聊天模式的切换必须在服务端统一记录，便于定位重启后模式异常变化。日志只记录实际发生的模式或私聊目标变化，不记录同一状态的重复同步。

控制端通过 WebSocket 保存模式时携带来源标识：页签/按钮使用 `controlManual`，文本系统命令使用 `controlCommand`，控制端语音命令使用 `controlVoice`，收到服务端广播后的被动同步使用 `serverSync`。显示端语音状态机直接切换服务端模式时使用 `displayVoice`，同时记录触发切换的 `displayId`。

服务端日志包含旧模式、新模式、旧/新私聊目标、来源和可用的 `displayId`。服务端是唯一的实际切换审计入口，控制端本地不额外输出重复的状态切换日志。

## 聊天配置与历史兼容

聊天历史消息会记录写入时的 `profileName`。切换或恢复 LLM profile 时不得删除历史文件；历史查询应继续返回已持久化的旧 profile 消息，避免配置变更被误判为聊天记录丢失。恢复已有 profile 时，`activeProfile` 与 `llmProfiles` 必须保持一致；配置文件只恢复聊天路由字段，不覆盖 TTS、ASR、语音窗口等其他运行参数。

## 临时角色选择消息注册约束

临时角色选择使用 WebSocket 消息 startTemporaryConversation。该消息必须同时存在于服务端控制端消息类型注册表和统一 Fallback 处理器中；只实现 Fallback 分支而未注册消息类型时，WebSocket 层会提前拒绝请求，控制端会一直停留在“切换中”状态。新增控制端消息时，注册表、处理器、控制端错误回包和回归测试必须一起更新。

## 临时对话单角色绑定与控制端选择

1. 临时对话仍是服务端唯一的全局会话；新的语音唤醒或控制端角色选择会替换旧临时会话，并清空旧临时历史。
2. `小爱` 等临时唤醒词不写死为命令，必须沿用服务端当前自动匹配到的角色名。服务端在创建临时会话时记录 `roleName` 和 `templateId`，后续请求只按该快照选择角色定义。
3. 临时会话的系统提示词只包含被唤醒角色对应的模板定义和基础提示词，不再调用群聊的全部角色提示词；“开始对话”进入的普通群聊仍保留全部角色定义。
4. 控制端临时页签增加当前角色选择器。选择角色通过 `startTemporaryConversation` 请求服务端创建/替换临时会话，服务端校验模板并广播权威会话快照；普通临时聊天消息只发送当前 `temporaryConversationId`，不发送角色提示词。
5. 控制端刷新或多个控制端并行操作时，以服务端广播的 `temporaryConversation` 快照为准；没有当前角色和会话 ID 时禁止发送，避免消息落入未绑定角色的临时会话。
