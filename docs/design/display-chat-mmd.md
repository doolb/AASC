# 显示端聊天与 VRM/MMD 同位分层设计

> 状态：同页聊天舞台与在线 VRM 运行时已接入；VMD/VRMA 动作资源和复杂动作生成仍按后续阶段推进。当前代码按“不使用 iframe、同一 display.html 内拆分模块”的方案落地。多助手/群聊历史范围修复已发布为 code v30。

## 1. 需求目标

显示端运行在浏览器中，需要在现有全屏媒体显示能力上增加一个类似聊天应用的入口，同时支持 VRM/MMD 角色显示与动作控制。聊天和角色画面必须适合手机屏幕，并且与控制端使用同一份聊天数据和实时会话状态。

目标包括：

- 显示端提供聊天入口，可选择角色或其他聊天对象，点击后进入对应聊天。
- 角色聊天页面顶部提供角色会话切换，角色 A 与角色 B 的历史和会话上下文相互隔离。
- 控制端与显示端共享同一聊天服务端状态；任一端发送消息、收到流式回复或切换会话，另一端都能同步。
- 媒体层始终作为最底层；MMD/VRM 与聊天占据同一个全屏舞台，可配置角色在聊天之上或之下。
- 直接在浏览器中加载 VRM，使用 `three-vrm` 渲染；参考 MMDAgent-EX 的指令语义，但不在浏览器中运行桌面版 MMDAgent-EX。
- 先支持预置动作、表情、口型和 VMD/VRMA 资源；复杂动作生成作为异步扩展，不阻塞首期聊天和显示。
- VRoid 模型采用在线获取：显示端保存模型页面地址，由本机服务端解析并代理临时 VRM 资源，浏览器端只加载同源模型地址；模型不打入 APK。
- 在线模型下载失败时保留已缓存模型或 Canvas 占位，不影响聊天和媒体。

非目标：

- 首期不把 PMX 模型直接交给浏览器运行，也不把 MMDAgent-EX 的桌面原生模块移植到 Web。
- 首期不实现在线实时文本生成全新动作；复杂动作生成要经过异步任务、缓存和安全校验。
- 不把 VRoid 模型二进制打入 APK；显示端聊天、舞台分层、three-vrm 在线运行时和默认模型加载由服务代码包提供。

## 2. 全屏同位分层

聊天和 MMD 不采用左右分栏，也不使用 iframe。二者共享 `display.html` 内的 `displayStage`、DOM、主题和 WebSocket 上下文，以便手机竖屏时保持沉浸式布局；媒体仍位于底层。

代码按模块拆分，页面文档保持单一：

- `display.html` 只保留媒体节点、分层容器和启动入口。
- `display-stage.js` 负责舞台尺寸、层级、显示开关和模块事件总线。
- `display-chat.js` 负责聊天对象、会话、消息、输入和聊天可见性。
- `display-mmd.js` 负责 VRM/MMD Canvas、模型加载、点击检测和动作运行时。
- `display-mmd-command-adapter.js` 负责高级动作计划和低级兼容命令。
- 聊天和 MMD 使用独立 CSS 文件，并以各自根容器为作用域，避免污染现有媒体样式。
- 舞台模块在 `DOMContentLoaded` 后再初始化，确保同页 `defer` 加载的聊天和 MMD 模块已经注册，避免入口按钮连接到空容器。
- `render-display` 覆盖层只高于媒体层，低于 MMD、聊天和交互控制层；聊天界面使用现有主题变量，不使用固定深色配色。
- 对象和会话切换使用同页 HTML 下拉菜单，避免 Android WebView 弹出系统原生选择器。
- 下拉菜单区分未选中、悬停/聚焦和已选中状态：未选中直接复用主题小卡片的 `card-background`（不按群聊/助手染色），已选中使用主题强调底色，悬停使用浅强调色，避免不同状态颜色相同。
- 聊天窗口铺满整个舞台；最外层聊天背景保持透明以显示媒体，顶部栏、消息气泡、状态栏、输入区和下拉菜单使用实色主题背景。
- 显示端聊天输入区采用“输入框左侧、操作按钮右侧”的两列布局；发送和清空按钮在右侧竖向排列，发送位于上方。
- 聊天对象下拉菜单与控制端保持同一命名方式：群聊只显示“群聊”，助手/角色私聊项只显示助手名称，不在选项文字中追加“所有角色”“私聊”或“角色”等模式后缀。
- 群聊项与助手项携带不同的目标类型标记，只使用不同的选中底色；会话下拉菜单继续复用通用选中状态样式。普通项、选中项和选中悬停项都必须有明确的非透明背景。
- 浅色主题的通用按钮渐变使用 `!important` 时，下拉项必须以相同层级的限定选择器覆盖普通、悬停和选中状态，保证通用按钮皮肤不影响列表项状态。
- 聊天层打开时隐藏显示端的播报文字，避免播报字幕遮挡聊天内容；TTS 音频队列和实际播放不受影响，聊天关闭后恢复当前文字显示。

推荐的视觉层级：

| 层级 | 内容 | 默认行为 |
|------|------|----------|
| 0 | 媒体层：图片、视频、HTML、文本和已有媒体提示 | 始终保留现有播放逻辑 |
| 100 | `render-display` 任务覆盖层 | 只覆盖媒体层，不遮挡聊天和 MMD |
| 200 | VRM/MMD 透明 Canvas | 显示角色、动作、表情和口型 |
| 210 | 显示端聊天应用层 | 角色列表、会话、消息气泡和输入区 |
| 220 | 交互控制层 | 左下角显示开关、顶部会话切换、输入和错误提示 |

“MMD 在聊天上面”只改变视觉层级，不改变控制层级。左下角显示开关、顶部会话切换和输入控件始终可点击；角色 Canvas 不能遮挡聊天输入。默认采用聊天在上、MMD 在下，后续允许按角色或显示端配置切换。

聊天层采用“容器不拦截、实际控件拦截”的策略：聊天面板和输入控件可操作，聊天透明区域允许触摸事件到达 MMD。聊天整体隐藏时，MMD Canvas 获得完整触摸区域；聊天状态保留，不销毁运行时。

移动端布局约束：

- 舞台使用 `100dvh` 与安全区内边距，兼容浏览器地址栏和刘海/底部手势区。
- 软键盘弹出时只调整聊天输入区域，不能重新计算角色的逻辑比例或导致 VRM 被放大。
- 使用同一舞台的 ResizeObserver 更新聊天和 Canvas；高 DPI 只影响 Canvas 绘制分辨率，不改变 CSS 视觉尺寸。
- 隐藏 MMD 时暂停渲染循环和动作采样；隐藏聊天时不暂停媒体或角色播放。
- 媒体层的播放、裁剪、旋转和睡眠逻辑保持现有职责，不由聊天层接管。

## 3. 显示端聊天入口与会话

### 3.1 入口和对象选择

显示端默认提供一个不遮挡主要媒体内容的聊天入口。入口打开后进入对象选择页，初始对象来源复用现有角色、聊天模板和助手配置。没有 VRM 模型的对象仍然可以聊天，只是不显示 MMD 层。

选择对象后进入角色聊天页：

- 顶部显示当前角色名称、头像/模型状态和会话选择器。
- 会话选择器固定在角色聊天界面顶部，不放到底部输入栏附近。
- 中部显示消息列表，支持正文和 think 内容的现有分流规则。
- 底部显示输入框、发送、语音输入和显示层开关。
- 返回对象选择不会删除会话；切换角色只改变当前 `ChatContext`。

### 3.2 会话键和历史边界

建议的逻辑键：

```text
group
role:<roleId>:<sessionId>
private:<targetId>:<sessionId>
temporary:<conversationId>
```

角色聊天的历史、未完成流式回复、think 内容和动作计划都绑定到 `ChatContext`。切换角色或会话时，客户端先显示服务端确认的上下文，再载入对应历史；不能用前一个角色的本地消息临时冒充新会话。

当前范围沿用项目已有的全局聊天上下文：显示端和控制端切换后同步当前权威会话。此前记录的“按 `displayId` 独立保存和路由”仍是后续扩展，不在本设计首期强行改变全局行为。未来增加独立显示端会话时，只扩展 `displayId` 维度，不改变前端组件和消息语义。

### 3.3 聊天对象名称与历史读取边界

显示端不直接读取 Android/Node 文件系统中的聊天目录，也不根据设备上的 `HOME` 或
`USER_CONFIG_DIR` 拼接路径。聊天历史统一通过现有 WebSocket `chatHistory` 消息从服务器获取，
服务器负责从实际运行环境的历史存储加载并按会话范围筛选。

- 对象列表由 `assistantConfig.defaultName`、`assistantConfig.assistants[]` 和兼容字段组成，去重后每个助手都生成一个 `private:<assistantName>` 目标。
- `群聊` 是独立目标，显示文字严格为“群聊”，对应 `mode=group`、`target=null`。
- 助手私聊只显示助手名称，对应 `mode=private`、`target=<assistantName>` 和 `sessionId`。
- 切换对象或会话时，显示端先清空旧消息视图，再请求新的服务器历史；服务端返回后只渲染当前范围，不能把上一个对象的本地历史临时保留在页面中。
- 控制端收到显示端或其他控制端广播的 `chatSession` 后，必须立即按当前会话重新渲染已有服务端历史；历史数据仍由服务器接口提供，不新增独立文件读取或聊天 HTTP 接口。

## 4. 控制端与显示端同步

沿用现有 WebSocket 聊天链路，不新增独立 HTTP 聊天读写接口。服务端是聊天状态、历史、角色会话切换和流式回复的权威来源。

客户端发送现有类型的 `chatMessage`，补充或复用以下语义：

- `requestId`：请求去重、流式片段关联和错误恢复。
- `mode`、`target`、`templateTarget`：复用现有群聊/私聊/助手目标。
- `sessionId`：当前角色会话。
- `displayId`/`displayIds`：复用现有路由；没有独立显示端会话时仍按当前全局规则处理。

服务端继续广播权威的 `chatChunk`、`chatResponse`、`chatHistory`、`chatSession`、`privateSessions` 和切换确认消息。显示端和控制端都必须：

1. 先按 `requestId` 去重。
2. 将流式片段合并到当前会话，而不是只写入当前打开的页面。
3. 收到历史或会话快照后，用服务端结果覆盖过期的本地选择。
4. 断线期间只保留待发送草稿；重连后先恢复服务端上下文，再决定是否重发。

聊天正文、think 内容和动作计划属于同一响应，但 UI 分开消费：消息气泡显示正文；显示端可显示 think；控制端按照现有规则折叠 think；TTS 只读正文。动作计划不直接显示在气泡中。

控制端在现有“显示控制”区域提供一个 MMD 可见性切换按钮。按钮只作用于当前选中的显示端，
复用既有 WebSocket `control` 消息，不新增独立 HTTP 配置接口。显示端收到命令后只改变 MMD
舞台可见性，保留模型、动作和聊天上下文；显示端手动切换也必须回传服务器并同步控制端。

显示端聊天对象与历史范围修复已通过 Offline code v30 发布到局域网和外网；沿用 dependencies v5
与 min APK v33，不重新打包原生 APK 或依赖包。

2026-09-20 已完成首版实现：聊天输入区使用 CSS 两列布局，右侧操作区纵向排列；聊天打开时通过 `display-chat-open` 和 `data-chat-suppressed` 双重状态隐藏播报文字；控制端通过 `mmdVisibility` 控制当前显示端，显示端以 ACK 回传权威状态。2026-09-22 改为单个切换按钮，并补充服务端按 `displayId` 持久化和显示端手动切换回传。

## 5. VRM/MMD 浏览器运行时

### 5.1 模型加载

采用 `three.js + three-vrm` 直接加载 VRM。VRoid Hub 页面地址不是模型二进制，浏览器不能把页面地址直接交给 `GLTFLoader`；显示端通过同源服务端资源解析接口获取受控代理地址。VRoid Hub 官方 API 的授权流程会返回临时对象存储地址，本项目使用公开可预览模型的 `optimized_preview` 资源，并由服务端带上 `X-Api-Version` 请求头跟随重定向。

浏览器侧的最小流程为：

1. 页面初始化时创建透明 Canvas 和 WebGL renderer。
2. 以模型页面地址请求 `/api/vrm/model`，校验只允许 `hub.vroid.com` 的角色模型 URL。
3. 服务端返回模型元数据和同源 `/api/vrm/model/file` 代理地址。
4. 服务端从 VRoid `optimized_preview` 下载 AES-CBC + zstd 封装的预览载荷，解包后按预览资源路径恢复顶点，再校验为正常 GLB 通过同源接口返回。
5. 浏览器通过 Cache API/HTTP 缓存复用模型字节，使用本地 `GLTFLoader`、`KTX2Loader` 与 VRM plugin 创建场景对象。
6. 清理无用顶点和关节，设置模型朝向、缩放和初始表情。
7. 把模型绑定到角色实例；切换角色时先停止旧动作，再释放旧场景。
8. 加载失败时显示占位，不阻塞聊天和媒体。

用户提供的 VRoid 模型页面可作为初始资源登记来源：
`https://hub.vroid.com/en/characters/1786977751194326803/models/3931412591784052736`。
实际发布前需要保存模型作者、版本、许可证和资源哈希；运行时使用本地缓存或项目资源地址，避免离线包启动依赖外部站点。

服务端只保存来源页面地址、角色 ID 和模型 ID，不保存 VRoid Hub 登录凭证；模型代理响应设置短期公共缓存，临时 URL 过期后重新解析。VRoid 的公开预览网格带有私有优化扩展，服务端按版本 5.0 的确定性种子恢复 POSITION 顶点，并通过缓存版本号丢弃旧的压缩顶点缓存。模型页面或模型资源不可访问时，显示端状态栏提示原因，聊天仍可用。

### 5.2 动作和表情

常用动作采用预置资源，优先支持：

- VRMA/FBX 动画片段；
- 通过 `mmd-parser` 读取 VMD 并映射到 VRM normalized bones；
- VRM expression/morph 映射；
- TTS 音频驱动的基础口型；
- 待机、点头、挥手、开心、疑惑、拒绝等可组合动作。

参考 Lobe Vidol 的浏览器实现方式：GLTF/VRM loader 负责模型，VMD 经过解析和骨骼归一化后生成 `AnimationClip`，表情和口型由独立控制器叠加。此处只参考公开的技术思路和接口边界，不复制业务代码。

### 5.4 模型触摸交互

MMD 模块在同一页面内直接监听 Canvas 的 pointer 事件，并使用 Three.js Raycaster 检测角色网格。只有角色点击确认后才执行本地预置反馈，再按角色策略决定是否通知聊天模块。

首期交互区域包括头部、脸部、头发、身体和手部；交互事件使用 `mmd.interaction` 内部事件，不自动产生聊天消息。点击联动聊天必须由角色配置显式开启，避免误触造成重复聊天。

Canvas 任意位置都可开始本地旋转拖动，包括角色网格上：在 `pointerdown` 时执行 Raycaster，命中角色时仅保留触摸候选，并为同一指针建立旋转拖动状态。移动达到 8 像素后取消触摸候选；只有角色上按下、松开时仍未达到该阈值的点击才执行既有触摸互动，`pointercancel` 和已开始的拖动不发布互动。水平位移增量映射为角色 Y 轴转身，纵向位移增量映射为角色 X 轴俯仰；俯仰始终限制在上下各 45°，防止模型倒置或超出可用视角。PMX 与 VRM runtime 在模型归一化后以包围盒中心创建旋转枢轴，保留模型贴地位置、动画根节点与命中网格不变；拖动只更新目标角度，渲染循环以约 140ms 的指数缓动追向目标。松开指针后等待当前角度收敛，再按最终姿态刷新阴影范围。旋转不持久化、不通过 WebSocket 广播，也不影响动作播放、聊天状态或灯光设置；Canvas 占位角色仅保留既有点击命中，不支持伪 3D 旋转。

### 5.3 MMDAgent-EX 兼容层

浏览器不直接执行 MMDAgent-EX，但提供一个低级命令适配层，支持项目需要的有限命令语义：

- `MOTION_ADD`：加载并播放动作片段；
- `MOTION_DELETE`：停止或移除指定动作；
- `MODEL_BINDFACE`：设置表情/口型权重；
- `MODEL_BINDBONE`：设置骨骼目标或骨骼叠加层。

适配层将这些命令转换为 three-vrm 的动作、表情和骨骼 API，并对未知命令返回可观察错误，不影响聊天和媒体播放。

## 6. AI 动作协议

### 6.1 高级动作计划

AI 面向 `mmd.action.plan`，不直接输出骨骼四元数。计划应包括：

- `planId`、角色和会话上下文；
- 由多个 step 组成的动作序列或并行动作轨道；
- 每个 step 的语义动作、时长、强度、表情、口型和可取消性；
- 优先级、打断策略、超时和 fallback；
- 资源选择提示，而不是任意文件路径。

示例语义可以是“先看向用户，挥右手两次，再开心地点头”，由客户端动作库选择实际 VMD/VRMA 和表情曲线。动作计划不得拥有文件系统路径、脚本执行权限或任意 JavaScript。

### 6.2 低级动作接口

低级接口服务于预置动作播放器、调试工具和兼容旧动作数据。它必须经过白名单、资源 ID 映射和参数范围校验，不能绕过模型资源管理。

### 6.3 复杂动作生成

复杂动作不是聊天请求的同步阻塞步骤。未来可以新增 `mmd.motion.generate` 任务：

1. LLM 将自然语言转换为结构化动作描述（可参考 PoPo 的语义动作语言思路）。
2. 动作生成器（例如 HY-Motion-MMD 类管线）异步生成候选动作。
3. 服务端完成模型重定向、VMD 校验、时长/骨骼白名单检查和缓存。
4. 显示端收到可播放资源 ID 后再执行计划。

首期只定义消息和缓存边界，不绑定具体生成模型，也不允许生成任务阻塞聊天首包。

## 7. 资源和离线策略

资源分为模型包、动作包、表情/口型包和聊天代码包。首期模型与动作从本地服务或离线包读取，版本化后可沿用已有热更清单机制；未来模型热更必须独立于代码包并支持哈希回滚。

缓存键至少包含 `resourceId + version + sha256`。加载失败时：

- 已缓存旧版本可安全使用则回退旧版本；
- 没有可用模型时保留聊天和媒体功能，显示角色占位状态；
- 动作缺失时播放待机动作，不阻塞正文回复；
- 所有资源错误进入现有可观察日志，但不写入聊天正文。

### 7.1 静态 VRM/MMD 模型资源

默认模型和后续角色模型可以预先上传到公网静态资源目录
`http://c.aasc.us/mnt/mmd/`。显示端不直接访问 VRoid Hub 的临时 CloudFront
地址，也不在 HTTPS WebView 中直接请求 HTTP 资源；本地 Node 服务通过同源 HTTPS
代理获取静态模型。

模型资源配置只携带受校验的相对文件名，例如 `default-vroid.vrm.zst`，不允许角色配置
注入任意 URL。Node 服务获取资源时复用 Offline 热更的 DNS 规则：先解析
`c.aasc.us`，再把 URL 主机替换成解析到的 IP，不保留 Host 头。这样可避开域名入口
的代理限制，同时保留统一域名配置和后续多模型扩展能力。

静态资源允许使用 zstd 压缩文件（`.vrm.zst`/`.glb.zst`），Node 服务解压后再以 GLB
响应给 WebView，以降低外部真机首次下载耗时。每个模型至少包含 `resourceId`、`fileName`、`version` 和可选 `sha256`；模型通过
`mmd.model.profile`/`vrm.model.profile` 选择，默认角色只引用默认文件。静态资源
下载失败时继续保留聊天、媒体和占位角色，不阻塞 WebSocket。

## 8. 性能、兼容性与安全

- 首屏加载媒体和聊天壳，同时按默认角色配置异步加载在线 VRM；three-vrm 运行时或网络不可用时显示安全占位交互区。
- 模型加载、动作解析和复杂动作生成不得阻塞 WebSocket 聊天连接。
- 使用帧预算监控；后台或隐藏角色暂停渲染，低端设备降低 Canvas 像素比和动作采样频率。
- 资源包限制大小、MIME、解压路径、哈希和版本，禁止从动作计划执行脚本或任意网络请求。
- Chrome/Android WebView 优先验证；没有 WebGL/WebGPU 或 VRM 加载失败时，聊天和媒体仍可用。
- 高 DPI 只提高实际绘制 buffer，不放大 UI；软键盘只影响输入区布局。

## 9. 分阶段实施

1. **同页舞台与模块边界**：增加 MMD/chat 根容器、独立 JS/CSS 模块、共享事件总线和层级测试。
2. **协议与数据模型**：确定角色、会话、动作计划和同步消息的字段，并补充契约测试。
3. **显示端聊天壳**：增加对象选择、顶部角色/会话切换、消息同步、显示开关和移动端布局。
4. **VRM/MMD 层**：接入 three-vrm、VMD/VRMA 播放、表情和基础口型，完成资源缓存和销毁。
5. **模型触摸交互**：接入 Raycaster、命中区域映射、本地反馈和可选聊天联动。
6. **动作控制**：接入高级动作计划、低级 MMDAgent-EX 兼容命令和安全白名单。
7. **异步复杂动作**：单独接入动作生成任务、资源缓存和回退，不能影响前六阶段的聊天可用性。

## 10. 验收标准

- 显示端能打开对象选择，进入角色聊天，并在顶部切换角色会话。
- 角色 A/B 的历史、流式回复和动作状态不会串到另一会话。
- 控制端和显示端的同一条聊天在发送、流式回复、清空和切换后保持一致。
- 媒体位于最底层；MMD 与聊天在同一全屏舞台，可切换视觉上下关系，输入控件始终可操作。
- 浏览器能通过同源代理加载 VRoid 在线 VRM，播放基础表情和口型；VMD/VRMA 预置动作接入后再扩展完整动作能力。
- AI 输出高级动作计划时，角色动作执行，聊天气泡只显示正常文本；动作失败不影响聊天回复。
- 离线无外网时，已缓存模型和动作仍可运行；没有模型时聊天和媒体正常。
- Android WebView 高 DPI、竖屏、软键盘和隐藏/恢复场景无明显放大、遮挡或渲染泄漏。

- 显示端语音输入进入普通聊天后，服务端同时向发起语音的显示端和控制端发送 `chatInput`、`chatChunk`、`chatResponse`，显示端自动呈现用户消息及流式回复。

## 12. 聊天层联动语音监听会话

- 显示端聊天层打开时，以当前聊天对象作为该显示端的临时语音监听上下文：群聊对应 `activeGroup`，私聊和角色聊天对应 `activePrivate + target`。
- 聊天层打开期间暂停服务端语音会话倒计时，服务端保存暂停瞬间的 `remainingMs`；显示端只展示服务端下发的暂停值，不自行推进或决定超时。
- 聊天层打开期间切换对象时，立即更新当前显示端的监听目标，但继续保持倒计时暂停。
- 聊天层关闭时保留当前监听上下文，并从暂停时保存的剩余时间继续服务端倒计时。
- 该状态是显示端连接级临时状态，不广播给其他显示端，不写入远端配置或持久化聊天设置；监听未启用时不强行开启监听。

## 14. 播报辅助层与聊天层语音自动发送（2026-09-21）

- 显示端增加位于 MMD 与聊天之间的播报辅助层；聊天 TTS 文字和天气详情弹窗均进入该层，默认层级为“媒体 < MMD < 播报辅助层 < 聊天层”。
- 聊天层打开时隐藏当前仍在有效期内的天气详情弹窗和 TTS 播报文字，但不删除节点、不重置显示计时；聊天关闭后仍未到期的内容恢复显示，已到期内容不恢复。
- 隐藏只影响文字和弹窗，不停止 TTS 音频队列、音频播放、录音暂停恢复或服务端播报状态。
- 聊天层打开时，当前显示端的语音监听上下文继续使用聊天对象/角色/私聊会话；识别到最终文本后直接进入当前聊天会话并自动发送，不再被普通语音对话确认模式拦截。
- 语音聊天的 `chatInput`、`chatChunk` 和 `chatResponse` 同时回传控制端与发起语音的显示端，保证显示端聊天窗口能够自动更新用户消息和流式回复。

## 15. 普通 TTS 弹窗层级修复（2026-09-21）

- 普通 TTS 弹窗必须带有聊天抑制标记；聊天层打开时隐藏弹窗，聊天层关闭且弹窗仍未到期时恢复显示。
- 隐藏只改变视觉状态，不停止 TTS 音频、不删除弹窗节点、不重置弹窗生命周期计时。

## 16. 普通聊天回复的语音能力兜底（2026-09-21）

- 普通语音聊天完成回传按来源显示端的 `voicePlayback` 能力分流。
- 有语音播放能力的来源端已经通过 TTS 音频和播报文字展示回复，不再额外发送 response 弹窗，避免重复显示。
- 没有语音播放能力的来源端继续接收 response 弹窗，作为无声播放能力设备的文字兜底。
- 兜底判断只读取来源端能力，不改变音频实际播放目标在其他显示端之间的既有选择逻辑。

## 17. 天气播报的语音能力兜底（2026-09-21）

- 天气播报与普通聊天回复使用相同的来源端能力分流：来源端具有 `voicePlayback` 时，仅保留通用 TTS 播放和播报文字，不再额外创建天气详情弹窗。
- 来源端没有 `voicePlayback` 时，继续发送 `weatherResult`，用完整天气详情作为无声设备的文字兜底。
- 天气详情仍位于 MMD 上方、聊天层下方的播报辅助层；聊天打开时隐藏，关闭后按弹窗原生命周期恢复。
- 该分流不改变通用 TTS 的实际播放目标选择，也不影响其他显示端继续作为语音播放设备工作。

## 18. TTS 播报文字自适应布局（2026-09-21）

- TTS 播报文字根据旋转后的逻辑画布短边和文本长度动态计算字号，范围限制为 `16px–36px`，避免高 DPI/300% 缩放下文字超出屏幕。
- 播报文字最大宽度扣除动态安全边距；90/270 度竖屏使用较小的自适应侧边距，减少左右两侧固定空白。
- 长文本使用自动换行、最大高度和纵向滚动，不改变播报音频和聊天层隐藏/恢复生命周期。

## 21. TTS/天气弹窗缩放适配与下拉状态对比（2026-09-22）

- TTS 和天气详情共用的响应弹窗按旋转后的当前逻辑视口宽度动态计算边距，每侧为逻辑宽度的 5%，并限制在 12px–64px。
- 边距跟随 WebView 当前逻辑视口变化，避免 300% 缩放时仍保留原始分辨率固定像素，导致左右空白占比异常。
- 弹窗使用 `border-box`，把边框和内边距纳入宽度计算，并继续限制在当前可视区域内，避免原始分辨率边距导致小视口溢出。
- 90/270 度旋转使用交换后的逻辑宽高重新计算，聊天隐藏、滚动和播报层级保持不变。
- 聊天下拉列表通过 `aria-selected`、`data-selected` 和 `is-selected` 同步选中状态；选中项增加主题强调背景、文字、加粗和左侧标记，悬停/聚焦不覆盖选中状态。
- 角色对象和聊天会话两个 HTML 下拉菜单都复用这套状态样式，确保选中深色、未选中浅色。

## 20. MMD 可见性双向同步与显示端状态持久化（2026-09-22）

MMD 可见性按显示端独立保存。控制端操作当前选中的 `displayId`，显示端底部入口也可以直接
切换；两种操作都先进入服务端统一状态处理，再广播权威结果。服务端复用已有显示端状态存储，
不新增 HTTP 配置读写接口。

状态和消息约束：

- `displayData.state.mmdVisible` 是当前显示端的权威运行时字段，缺失旧数据按 `true` 处理。
- 控制端发送 `control/mmdVisibility`，服务端校验布尔值、更新内存状态、通过 `updateDisplayStateById`
  持久化，然后下发给目标显示端并广播 `mmdVisibilityChanged`。
- 显示端手动操作发送 `mmdVisibilityRequest`，服务端使用同一套更新流程，避免控制端和显示端各自维护
  一份状态。
- 显示端重连时服务端下发保存的 `control/mmdVisibility`；控制端通过 `displayState` 和实时广播恢复按钮。
- 单个显示端的状态不会覆盖其他显示端；多个控制端收到同一条广播后显示相同状态。

模型对象、动作队列、聊天上下文和 MMD WebGL 运行时不因隐藏而销毁；可见性只改变舞台层、按钮状态
和 pointer 路由。
