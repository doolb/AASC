# 显示端聊天与 VRM/MMD 同位分层设计

> 状态：第一阶段已实现，VRM/MMD 本地运行时接入待后续阶段。当前代码按“不使用 iframe、同一 display.html 内拆分模块”的方案落地。

## 1. 需求目标

显示端运行在浏览器中，需要在现有全屏媒体显示能力上增加一个类似聊天应用的入口，同时支持 VRM/MMD 角色显示与动作控制。聊天和角色画面必须适合手机屏幕，并且与控制端使用同一份聊天数据和实时会话状态。

目标包括：

- 显示端提供聊天入口，可选择角色或其他聊天对象，点击后进入对应聊天。
- 角色聊天页面顶部提供角色会话切换，角色 A 与角色 B 的历史和会话上下文相互隔离。
- 控制端与显示端共享同一聊天服务端状态；任一端发送消息、收到流式回复或切换会话，另一端都能同步。
- 媒体层始终作为最底层；MMD/VRM 与聊天占据同一个全屏舞台，可配置角色在聊天之上或之下。
- 直接在浏览器中加载 VRM，使用 `three-vrm` 渲染；参考 MMDAgent-EX 的指令语义，但不在浏览器中运行桌面版 MMDAgent-EX。
- 先支持预置动作、表情、口型和 VMD/VRMA 资源；复杂动作生成作为异步扩展，不阻塞首期聊天和显示。
- 离线环境优先从本地服务和缓存读取模型、动作与资源；外部 VRoid 地址仅作为初始资源来源，不作为运行时硬依赖。

非目标：

- 首期不把 PMX 模型直接交给浏览器运行，也不把 MMDAgent-EX 的桌面原生模块移植到 Web。
- 首期不实现在线实时文本生成全新动作；复杂动作生成要经过异步任务、缓存和安全校验。
- 第一阶段不引入外部模型二进制；显示端聊天、舞台分层、模块总线和无运行时 Canvas 降级已接入，Offline min v20 与 code v11 已用于真机验证。

## 2. 全屏同位分层

聊天和 MMD 不采用左右分栏，也不使用 iframe。二者共享 `display.html` 内的 `displayStage`、DOM、主题和 WebSocket 上下文，以便手机竖屏时保持沉浸式布局；媒体仍位于底层。

代码按模块拆分，页面文档保持单一：

- `display.html` 只保留媒体节点、分层容器和启动入口。
- `display-stage.js` 负责舞台尺寸、层级、显示开关和模块事件总线。
- `display-chat.js` 负责聊天对象、会话、消息、输入和聊天可见性。
- `display-mmd.js` 负责 VRM/MMD Canvas、模型加载、点击检测和动作运行时。
- `display-mmd-command-adapter.js` 负责高级动作计划和低级兼容命令。
- 聊天和 MMD 使用独立 CSS 文件，并以各自根容器为作用域，避免污染现有媒体样式。
- 舞台模块在 `DOMContentLoaded` 后再初始化，确保同页 `defer` 加载的聊天和 MMD 模块已经注册，避免入口按钮连接到空容器。
- `render-display` 覆盖层只高于媒体层，低于 MMD、聊天和交互控制层；聊天界面使用现有主题变量，不使用固定深色配色。
- 对象和会话切换使用同页 HTML 下拉菜单，避免 Android WebView 弹出系统原生选择器。
- 下拉菜单区分未选中、悬停/聚焦和已选中状态：已选中使用主题强调色背景，悬停使用浅强调色，避免不同状态颜色相同。
- 聊天窗口铺满整个舞台；最外层聊天背景保持透明以显示媒体，顶部栏、消息气泡、状态栏、输入区和下拉菜单使用实色主题背景。

推荐的视觉层级：

| 层级 | 内容 | 默认行为 |
|------|------|----------|
| 0 | 媒体层：图片、视频、HTML、文本和已有媒体提示 | 始终保留现有播放逻辑 |
| 100 | `render-display` 任务覆盖层 | 只覆盖媒体层，不遮挡聊天和 MMD |
| 200 | VRM/MMD 透明 Canvas | 显示角色、动作、表情和口型 |
| 210 | 显示端聊天应用层 | 角色列表、会话、消息气泡和输入区 |
| 220 | 交互控制层 | 左下角显示开关、顶部会话切换、输入和错误提示 |

“MMD 在聊天上面”只改变视觉层级，不改变控制层级。左下角显示开关、顶部会话切换和输入控件始终可点击；角色 Canvas 不能遮挡聊天输入。默认采用聊天在上、MMD 在下，后续允许按角色或显示端配置切换。

聊天层采用“容器不拦截、实际控件拦截”的策略：聊天面板和输入控件可操作，聊天透明区域允许触摸事件到达 MMD。聊天整体隐藏时，MMD Canvas 获得完整触摸区域；聊天状态保留，不销毁运行时。

移动端布局约束：

- 舞台使用 `100dvh` 与安全区内边距，兼容浏览器地址栏和刘海/底部手势区。
- 软键盘弹出时只调整聊天输入区域，不能重新计算角色的逻辑比例或导致 VRM 被放大。
- 使用同一舞台的 ResizeObserver 更新聊天和 Canvas；高 DPI 只影响 Canvas 绘制分辨率，不改变 CSS 视觉尺寸。
- 隐藏 MMD 时暂停渲染循环和动作采样；隐藏聊天时不暂停媒体或角色播放。
- 媒体层的播放、裁剪、旋转和睡眠逻辑保持现有职责，不由聊天层接管。

## 3. 显示端聊天入口与会话

### 3.1 入口和对象选择

显示端默认提供一个不遮挡主要媒体内容的聊天入口。入口打开后进入对象选择页，初始对象来源复用现有角色、聊天模板和助手配置。没有 VRM 模型的对象仍然可以聊天，只是不显示 MMD 层。

选择对象后进入角色聊天页：

- 顶部显示当前角色名称、头像/模型状态和会话选择器。
- 会话选择器固定在角色聊天界面顶部，不放到底部输入栏附近。
- 中部显示消息列表，支持正文和 think 内容的现有分流规则。
- 底部显示输入框、发送、语音输入和显示层开关。
- 返回对象选择不会删除会话；切换角色只改变当前 `ChatContext`。

### 3.2 会话键和历史边界

建议的逻辑键：

```text
group
role:<roleId>:<sessionId>
private:<targetId>:<sessionId>
temporary:<conversationId>
```

角色聊天的历史、未完成流式回复、think 内容和动作计划都绑定到 `ChatContext`。切换角色或会话时，客户端先显示服务端确认的上下文，再载入对应历史；不能用前一个角色的本地消息临时冒充新会话。

当前范围沿用项目已有的全局聊天上下文：显示端和控制端切换后同步当前权威会话。此前记录的“按 `displayId` 独立保存和路由”仍是后续扩展，不在本设计首期强行改变全局行为。未来增加独立显示端会话时，只扩展 `displayId` 维度，不改变前端组件和消息语义。

## 4. 控制端与显示端同步

沿用现有 WebSocket 聊天链路，不新增独立 HTTP 聊天读写接口。服务端是聊天状态、历史、角色会话切换和流式回复的权威来源。

客户端发送现有类型的 `chatMessage`，补充或复用以下语义：

- `requestId`：请求去重、流式片段关联和错误恢复。
- `mode`、`target`、`templateTarget`：复用现有群聊/私聊/助手目标。
- `sessionId`：当前角色会话。
- `displayId`/`displayIds`：复用现有路由；没有独立显示端会话时仍按当前全局规则处理。

服务端继续广播权威的 `chatChunk`、`chatResponse`、`chatHistory`、`chatSession`、`privateSessions` 和切换确认消息。显示端和控制端都必须：

1. 先按 `requestId` 去重。
2. 将流式片段合并到当前会话，而不是只写入当前打开的页面。
3. 收到历史或会话快照后，用服务端结果覆盖过期的本地选择。
4. 断线期间只保留待发送草稿；重连后先恢复服务端上下文，再决定是否重发。

聊天正文、think 内容和动作计划属于同一响应，但 UI 分开消费：消息气泡显示正文；显示端可显示 think；控制端按照现有规则折叠 think；TTS 只读正文。动作计划不直接显示在气泡中。

## 5. VRM/MMD 浏览器运行时

### 5.1 模型加载

采用 `three.js + three-vrm` 直接加载 VRM。浏览器侧的最小流程为：

1. 根据角色配置得到模型资源 ID，而不是直接信任任意外部 URL。
2. 优先请求本地离线资源或服务端缓存。
3. 校验资源版本、大小、哈希和允许的 MIME 类型。
4. 通过 GLTF loader 与 VRM plugin 创建场景对象。
5. 清理无用顶点和关节，设置模型朝向、缩放和初始表情。
6. 把模型绑定到角色实例；切换角色时先停止旧动作，再释放旧场景。

用户提供的 VRoid 模型页面可作为初始资源登记来源：
`https://hub.vroid.com/en/characters/1786977751194326803/models/3931412591784052736`。
实际发布前需要保存模型作者、版本、许可证和资源哈希；运行时使用本地缓存或项目资源地址，避免离线包启动依赖外部站点。

### 5.2 动作和表情

常用动作采用预置资源，优先支持：

- VRMA/FBX 动画片段；
- 通过 `mmd-parser` 读取 VMD 并映射到 VRM normalized bones；
- VRM expression/morph 映射；
- TTS 音频驱动的基础口型；
- 待机、点头、挥手、开心、疑惑、拒绝等可组合动作。

参考 Lobe Vidol 的浏览器实现方式：GLTF/VRM loader 负责模型，VMD 经过解析和骨骼归一化后生成 `AnimationClip`，表情和口型由独立控制器叠加。此处只参考公开的技术思路和接口边界，不复制业务代码。

### 5.4 模型触摸交互

MMD 模块在同一页面内直接监听 Canvas 的 pointer 事件，并使用 Three.js Raycaster 检测角色网格。命中后先执行本地预置反馈，再按角色策略决定是否通知聊天模块。

首期交互区域包括头部、脸部、头发、身体和手部；交互事件使用 `mmd.interaction` 内部事件，不自动产生聊天消息。点击联动聊天必须由角色配置显式开启，避免误触造成重复聊天。

### 5.3 MMDAgent-EX 兼容层

浏览器不直接执行 MMDAgent-EX，但提供一个低级命令适配层，支持项目需要的有限命令语义：

- `MOTION_ADD`：加载并播放动作片段；
- `MOTION_DELETE`：停止或移除指定动作；
- `MODEL_BINDFACE`：设置表情/口型权重；
- `MODEL_BINDBONE`：设置骨骼目标或骨骼叠加层。

适配层将这些命令转换为 three-vrm 的动作、表情和骨骼 API，并对未知命令返回可观察错误，不影响聊天和媒体播放。

## 6. AI 动作协议

### 6.1 高级动作计划

AI 面向 `mmd.action.plan`，不直接输出骨骼四元数。计划应包括：

- `planId`、角色和会话上下文；
- 由多个 step 组成的动作序列或并行动作轨道；
- 每个 step 的语义动作、时长、强度、表情、口型和可取消性；
- 优先级、打断策略、超时和 fallback；
- 资源选择提示，而不是任意文件路径。

示例语义可以是“先看向用户，挥右手两次，再开心地点头”，由客户端动作库选择实际 VMD/VRMA 和表情曲线。动作计划不得拥有文件系统路径、脚本执行权限或任意 JavaScript。

### 6.2 低级动作接口

低级接口服务于预置动作播放器、调试工具和兼容旧动作数据。它必须经过白名单、资源 ID 映射和参数范围校验，不能绕过模型资源管理。

### 6.3 复杂动作生成

复杂动作不是聊天请求的同步阻塞步骤。未来可以新增 `mmd.motion.generate` 任务：

1. LLM 将自然语言转换为结构化动作描述（可参考 PoPo 的语义动作语言思路）。
2. 动作生成器（例如 HY-Motion-MMD 类管线）异步生成候选动作。
3. 服务端完成模型重定向、VMD 校验、时长/骨骼白名单检查和缓存。
4. 显示端收到可播放资源 ID 后再执行计划。

首期只定义消息和缓存边界，不绑定具体生成模型，也不允许生成任务阻塞聊天首包。

## 7. 资源和离线策略

资源分为模型包、动作包、表情/口型包和聊天代码包。首期模型与动作从本地服务或离线包读取，版本化后可沿用已有热更清单机制；未来模型热更必须独立于代码包并支持哈希回滚。

缓存键至少包含 `resourceId + version + sha256`。加载失败时：

- 已缓存旧版本可安全使用则回退旧版本；
- 没有可用模型时保留聊天和媒体功能，显示角色占位状态；
- 动作缺失时播放待机动作，不阻塞正文回复；
- 所有资源错误进入现有可观察日志，但不写入聊天正文。

## 8. 性能、兼容性与安全

- 首屏只加载媒体和聊天壳，VRM 在选中角色后按需加载；当前无本地 VRM 运行时时显示安全占位交互区。
- 模型加载、动作解析和复杂动作生成不得阻塞 WebSocket 聊天连接。
- 使用帧预算监控；后台或隐藏角色暂停渲染，低端设备降低 Canvas 像素比和动作采样频率。
- 资源包限制大小、MIME、解压路径、哈希和版本，禁止从动作计划执行脚本或任意网络请求。
- Chrome/Android WebView 优先验证；没有 WebGL/WebGPU 或 VRM 加载失败时，聊天和媒体仍可用。
- 高 DPI 只提高实际绘制 buffer，不放大 UI；软键盘只影响输入区布局。

## 9. 分阶段实施

1. **同页舞台与模块边界**：增加 MMD/chat 根容器、独立 JS/CSS 模块、共享事件总线和层级测试。
2. **协议与数据模型**：确定角色、会话、动作计划和同步消息的字段，并补充契约测试。
3. **显示端聊天壳**：增加对象选择、顶部角色/会话切换、消息同步、显示开关和移动端布局。
4. **VRM/MMD 层**：接入 three-vrm、VMD/VRMA 播放、表情和基础口型，完成资源缓存和销毁。
5. **模型触摸交互**：接入 Raycaster、命中区域映射、本地反馈和可选聊天联动。
6. **动作控制**：接入高级动作计划、低级 MMDAgent-EX 兼容命令和安全白名单。
7. **异步复杂动作**：单独接入动作生成任务、资源缓存和回退，不能影响前六阶段的聊天可用性。

## 10. 验收标准

- 显示端能打开对象选择，进入角色聊天，并在顶部切换角色会话。
- 角色 A/B 的历史、流式回复和动作状态不会串到另一会话。
- 控制端和显示端的同一条聊天在发送、流式回复、清空和切换后保持一致。
- 媒体位于最底层；MMD 与聊天在同一全屏舞台，可切换视觉上下关系，输入控件始终可操作。
- 浏览器能直接加载本地 VRM，播放预置动作、VMD/VRMA、表情和基础口型。
- AI 输出高级动作计划时，角色动作执行，聊天气泡只显示正常文本；动作失败不影响聊天回复。
- 离线无外网时，已缓存模型和动作仍可运行；没有模型时聊天和媒体正常。
- Android WebView 高 DPI、竖屏、软键盘和隐藏/恢复场景无明显放大、遮挡或渲染泄漏。
