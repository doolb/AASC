## 2026-09-30 Blender刚体、传统布料与XPBD修正方法（技术核对）

用户询问Blender如何修正物理误差。需区分三条路径：Blender刚体通过rb_bullet_api.cpp使用btSequentialImpulseConstraintSolver和btDiscreteDynamicsWorld，提供子步/迭代与Split Impulse参数；传统Cloth修改器走顶点质量弹簧和隐式积分，源码implicit_blender.cc/implicit_eigen.cc联立质量、力导数与阻尼求解速度增量，再更新位置；Blender 5.2官方手册的实验性几何节点Cloth Dynamics/Hair Dynamics使用XPBD Solver，不应据此把传统Cloth或刚体统称XPBD。

当前PMX效果由刚体/关节驱动骨骼，更接近Blender刚体路径；借鉴传统Cloth或XPBD节点需另做数据和求解适配。仅查官方手册/源码并读取原生默认参数，未修改生产代码、执行新功能自测、构建或发布。参考：<https://github.com/blender/blender/blob/main/intern/rigidbody/rb_bullet_api.cpp>、<https://github.com/blender/blender/blob/main/source/blender/simulation/intern/implicit_blender.cc>、<https://docs.blender.org/manual/en/5.2/modeling/geometry_nodes/simulation/xpbd_solver.html>、<https://developer.blender.org/docs/features/nodes/xpbd_solver/xpbd_method/>。

## 2026-09-30 先预测位置与XPBD式求解（可行性核对）

用户询问能否像XPBD一样先预测位置。Ammo/Bullet上游的internalSingleStepSimulation已调用predictUnconstraintMotion，再进行碰撞检测、约束求解和integrateTransforms；刚体predictIntegratedTransform按当前线/角速度生成候选姿态。该候选状态不等同XPBD的位置约束迭代，也不能宣称预测姿态已经包含最终约束/接触冲量。当前网页继续调用一次world.stepSimulation，由引擎推进，无额外JS预测写回。

XPBD流程为预测动态位置/姿态、使用柔度及累计乘子迭代修正约束、由修正后的位移更新速度。若采用此流程，需新增或替换位置约束求解器，并同步关节、接触、旋转及速度；单独在JS先移动到预测位置再让Ammo走一步，可能重复积分。只计算不写回的预测缓存可用于诊断，但本身不改变物理响应，不能视为静止抖动修复。骨骼锚点运动外推是另一用途，主要处理跟随延迟，静止时没有该收益。

本轮只核对当前适配与上游源码并记录边界，尚未新增预测/位置求解代码、运行新自测、构建或发布。保留已有Ammo修复；XPBD式求解仍是可选评估，具体是否替换动态求解及碰撞职责须另定。参考：<https://github.com/kripken/ammo.js/blob/main/bullet/src/BulletDynamics/Dynamics/btDiscreteDynamicsWorld.cpp>、<https://github.com/kripken/ammo.js/blob/main/bullet/src/BulletDynamics/Dynamics/btRigidBody.cpp>、<https://mmacklin.com/xpbd.pdf>。

## 2026-09-30 Ammo求解方式与XPBD可行性（技术评估）

用户询问Ammo使用的物理方法及能否采用XPBD。实际固定MMDPhysics._createWorld创建btSequentialImpulseConstraintSolver与btDiscreteDynamicsWorld，约束为btGeneric6DofSpringConstraint。现有裙摆/头发效果由PMX刚体、6自由度弹簧关节与骨骼回写产生，未运行网格顶点布料求解。Bullet官方将该求解器描述为PGS（投影高斯-赛德尔）迭代方法；当前流程以速度/冲量处理碰撞和关节，再推进刚体姿态。

## 2026-09-30 重力方向 1:1 与锚点死区/缓动（已实现）

用户明确移除重力灵敏度，但保留首次姿态归零和“重力居中”，并在重力方向应用到角色锚点时增加缓动和死区。原实现使用中性参考与当前重力方向间的旋转，并把夹角乘以灵敏度；重力层与手动层共用缓动系数。此次方案按用户最新修正保留相对中性姿态语义。

每个有效 beta/gamma 样本直接推导重力方向，求中性方向到当前方向的旋转，不读取 alpha、不缩放夹角。锚点的重力层依次经过角度死区与独立缓动，再与手动旋转叠加。死区比较当前输入与上次接受目标的四元数夹角，小于阈值保持目标；超过阈值接收完整输入角度，不扣减阈值、不修改旋转幅度；缓慢移动可累积越过阈值，避免逐样本比较导致永久不响应。缓动按帧时间计算球面插值，最终收敛到接受目标，保留原手动层和定位相机更新流程。

重力分类独立提供“重力死区”0–3°（默认 0.5°）和“重力缓动”0–500ms（默认 20ms），保存于当前浏览器；参数与相机死区/缓动分别生效，0 分别表示关闭该过滤步骤。首次样本作为中性姿态；居中/关闭将重力目标归零并绕过死区，防止残留小角度，手动状态保持。权限取消、横竖屏/后台参考重建、模型重载与物理角速度保护继续保留。

实现位于 `3rd/mmd-ar-test/web-gravity-mode.js`、`build.js`、`web-panel-groups.js` 和新增网页重力滤波模块 `web-gravity-filter.mjs`，只进入网页副本。新增重力定向测试和真实网页事件/控件及重载回归，同步使用与自测文档；真机方向、噪声和性能待现场验收。

## 1. 目标

### 测试网页动作播放开关

HTTPS MMD AR 测试页灯光面板提供“播放动作”复选框，默认开启并只保存到当前浏览器的专用 `localStorage` 键。关闭时暂停 VMD 在当前帧，PMX 刚体/布料物理和渲染循环继续；重新开启从暂停帧接续。刷新页面不会在隐藏加载阶段自动套用 VMD 第 0 帧或预热物理；新模型首个实际渲染帧只更新物理且不绘制角色，第二帧起推进 VMD 并显示，关闭状态保留 PMX 绑定姿态。该项只用于测试网页诊断布料首屏行为，不加入 APK 界面或正式显示端控制面板。

### 测试网页物理开关

HTTPS MMD AR 测试页“物理”分类提供默认开启的 PMX 物理开关，用于对照布料关闭物理后的穿模情况。切换时重新加载当前模型、从头播放 VMD：关闭状态创建 `physics: false` 的 helper，不请求 Ammo；开启状态只初始化 Ammo，不自动套用 VMD 首帧或进行隐藏预热。不能只暂停现有物理世界，否则残留的布料形变会干扰对照。设置仅保存在测试网页的专用 `localStorage` 键；APK 和正式显示端不显示此控件，正式显示端默认物理开启。模型重载期间保留原模型，重载失败时恢复原开关。实际穿模观感需在目标设备现场验证。

### HTTPS 网页形态

当前模拟画面由所选原图比例决定，而不是固定 16:9：画布宽 960 像素，高度按解码原图比例取整；预览宽高比和左右竖向滑条长度使用同一原图比例，画布流直接作为校准与 MindAR 输入。下方水平旋转在原图三维平面内先发生，再计算经纬度透视；此前投影后直接旋转归一化画面的行为已废弃。下文关于 960×540 的描述属于此前版本或未选图占位状态。

HTTPS 网页继续保留完整 MMD 测试 harness：模型、Three.js/Ammo runtime、灯光/AO、动作物理、旋转交互和定位校准均正常初始化。网页专用定位流程使用 MindAR Basic 的 A-Frame `mindar-image-target` 锚点；找到目标时，半透明蓝色矩形及中心十字直接随目标平面移动、旋转和缩放；目标丢失时锚点自动隐藏。状态从锚点事件同步到原定位面板，不向 MMD 模型写入跟踪姿态。校准沿用独立视频流：真实模式用实体相机，模拟模式用当前透视画布；定位启动前释放校准流，再由 A-Frame 独占相应输入。停止、切换和页面离开均清理资源。APK 和正式显示端仍使用原流程。

当前网页在锚点标记之外接入独立 PMX 相机：目标图视为水平地面，其中心对应模型原有脚底中心；目标姿态经平面转正、模型高度换算与逆矩阵得到世界相机姿态，PMX 画布同步 A-Frame 的投影矩阵和视频裁切。定位不改变模型根节点的位置、缩放或旋转，已有动作与物理继续原样运行。目标丢失时保持最后视角和角色显示，重新找到后继续更新相机；停止时还原普通展示相机。模拟输入仅在切后台前正处于定位时回前台自动恢复；真实摄像头仍需手动启动。这个处理仅提供单图相对定位，不提供脱离目标图的世界级 SLAM。

没有实体摄像头的电脑可在 HTTPS 测试页选择“模拟摄像头”，从本地选一张作为相机画面的图片。图片仅在当前浏览器内解码，不上传或写入定位图存储。固定焦距的平面投影由经度、纬度、缩放和图片平移决定四角，独立 WebGL 画布再用逆单应映射生成 960×540 连续视频帧，交给现有 MindAR A-Frame 视频入口；灰色背景模拟视野外区域。上方缩放、右侧竖向纬度和下方经度滑条分别控制对应参数；鼠标拖动图片只平移，重置恢复正面、100% 缩放和居中。四角不能自由拖动，投影退化时保留上一次有效画面。切换真实/模拟输入先停止当前定位，停止和页面离开释放捕获轨道与绘制计时器。测试页的拍照校准在模拟模式下复用模拟视频帧，在真实模式下仍使用实体摄像头；拍照后默认四边各内缩 15% 的矩形，可拖动内部平移、拖动边或角改变尺寸，框选始终保持轴对齐且受照片边界限制。保存时换算为原有四点数据以兼容 IndexedDB 与 MindAR 编译；正式显示端及旧测试 APK 保留独立四角选区。已有内置官方定位图可直接用于无相机测试。模拟首锁用于开发回归，不等同真机识别验收；正式显示端与旧测试 APK 不加入模拟输入。

手机浏览器下，灯光/定位面板高度以动态可视高度和安全边为限，允许面板纵向触摸滚动；Canvas 仍独立禁止浏览器手势。下方定位操作可滚动到屏幕内。网页脚本和 PMX runtime 的 URL 带内容版本，避免页面更新后读取旧缓存。

## 3. 架构

```text
3rd/mmd-ar-test/
├── Android 测试工程
│   ├── 仅绑定 127.0.0.1 的 APK 内置静态 HTTP 服务
│   ├── 单独测试 Activity 与相机授权
│   └── 本地静态 HTTP 服务只提供 MMD profile 和 APK assets
├── MMD AR 测试页面
│   ├── 复用 web-mediacenter 的 MMD、PMX、AR、跟踪及灯光模块
│   ├── APK 与 HTTPS 测试页只提供 MindAR 跟踪和单算法指标
│   └── 仅提供模型舞台、定位面板和灯光面板
├── model-manifest.json
│   └── 当前默认 PMX 及配套资源的固定长度和 SHA-256
└── output/
    └── aasc-mmd-ar-test.apk
```

APK 启动时会在固定回环地址 `127.0.0.1:17836` 上启动静态 HTTP 服务，从 APK assets 提供页面、模型、纹理、动作和 WASM。固定 origin 确保跨启动保留 IndexedDB 定位图和本地灯光设置。WebView 只允许访问该回环 origin；服务不绑定 LAN 地址，也不启动 AASC/Node 服务。相机仅在网页请求视频捕获时申请 Android CAMERA 权限，WebChromeClient 只授权本地 origin 的视频捕获。

Android Activity 按窗口、本地资源服务、WebView 创建和页面加载分阶段启动。窗口内容挂载并获得焦点后才读取 `window.insetsController` 并请求沉浸式显示；若 controller 为空或厂商窗口 API 报错，恢复普通系统栏和默认内容布局后继续运行。同步启动异常会记录阶段与完整堆栈，并展示可截图、可选择文字的错误页；WebView 恢复失败或渲染进程退出时也显示诊断页。此诊断不改变相机权限时机或权限范围。

## 4. 资源边界

- 下载源使用已发布的 `miya-v1` 固定资源，构建前逐文件核对 manifest 声明的大小和 SHA-256。
- PMX、纹理与默认 VMD 存放在本地构建缓存并进入 APK assets；缓存和 APK 均不提交 Git。
- JS/CSS/Three.js/Ammo 仅从当前仓库现有显示端源码中按清单打包，避免复制维护另一份运行时实现。
- APK 内模型 URL 限于 `/api/mmd/static/` 固定前缀；HTTP handler 只接受 GET/HEAD 和静态 allowlist 路径，拒绝路径越界、非回环访问及外部资源回退。
- 测试 APK 固定内置 MindAR 1.2.5 的识别运行时代码和 Apache-2.0 许可证，构建下载缓存和 APK asset 均逐文件校验大小/SHA-256；运行时不访问 CDN。
- MindAR 运行时代码在用户开始定位时从 APK 本地资源动态加载。测试流程不再装载当前 JS 跟踪器；定位复用 IndexedDB 中的参考照片和四角选区。MindAR 每轮将选区透视校正为独立目标图并重新编译；首锁时间包含首次本地 JS 模块加载，但不包含相机授权等待。
- 指标记录目标准备/编译耗时、识别首锁耗时、算法识别帧率、按时间加权的可见率、丢失次数和屏幕锚点 RMS 偏差。MindAR 不提供匹配置信度，测试页面明确不显示伪造的置信度值；锚点偏差需在目标静止时测量才可近似表示抖动。

### 4.1 历史：跟踪器 A/B 对比范围

- 对比入口和 MindAR 适配器只注入到生成的 `3rd/mmd-ar-test/` 测试 APK 页面，不写入正式 `display.html` 或生产显示端 tracker。
- 一次只运行一个算法；每轮都使用同一保存目标、选区、视频层和现有 MMD 姿态映射。算法初始化计时从 tracker 启动开始，不含系统摄像头授权等待。
- 当前 JS 的“准备时间”统计参考图载入/特征提取；MindAR 统计选区矫正/目标编译。两者是各自引擎对应的目标预处理阶段，结果用于设备侧对比，不宣称算法内部操作完全相同。
- “识别帧率”按各 tracker 实际产出的新识别样本计数，MindAR 由其 `processDone` 回调计样本，避免把重复读取的旧姿态算成新帧；可见率按时间加权，减少两种引擎帧率不同造成的抽样偏差。
- MindAR 运行时状态不得在共享摄像头已就绪后继续显示“请求摄像头权限”：目标编译期间明确提示引擎准备阶段，启动后切换为寻找定位图，错误仍由共享 AR 状态机显示。
- MindAR `Compiler.compileImageTargets` 调用必须提供进度回调；进度同步到定位状态和 A/B 提示，编译/初始化失败时显示具体错误，禁止继续显示“正在寻找定位图”。
- 竖屏测试页左上提示需为右上灯光按钮及安全 Insets 留出完整宽度；长文案允许换行，横屏布局保持现状。该规则只作用于独立测试 APK 的生成页。

## 7. 风险与处理

- WebView 本地页需被识别为安全来源：使用 `127.0.0.1` 回环来源，并由 WebChromeClient 只授予本地 origin 的摄像头视频捕获权限；静态服务仅绑定回环地址。

- Android 设备 WebView/图形驱动的 PMX 物理表现可能不同：测试 APK 保留明确状态提示，最终视觉与性能仍需真机验收。

## 9. Android WebView 触摸安全区域

- Android 沉浸式窗口的绘制 frame 可能大于应用实际可用区域；控件布局不能只依赖 CSS `env(safe-area-inset-*)`，因为旧版 Android WebView 未必提供对应值。
- Activity 读取当前窗口 Insets，将实际安全距离按 WebView CSS 像素换算后写入页面 CSS 自定义属性；测试页的右上角灯光/定位控件据此向内偏移。
- Activity 记录右上区域原生触摸的 raw/local 坐标；测试页记录 DOM `pointerdown`/`click` 目标与面板状态，通过 WebChromeClient console 日志对照验证事件链；蓝色点击高亮不作为事件成功的唯一依据。
- 测试 harness 必须保留 `.display-interaction-layer` 的 `z-index: 50` 层叠上下文；只抽取内部按钮会使 `z-index: 10` 的交互 canvas 抢占 DOM hit-test。
- 修复仅作用于 `3rd/mmd-ar-test/` APK，不修改正式显示端共享 CSS/JS；验收需确认灯光面板和定位面板均可开合，模型拖动旋转仍有效。
- 根因：独立测试 harness 只抽取灯光/定位控件，没有保留正式页面 `.display-interaction-layer` 的 `z-index: 50` 层叠上下文，导致 `z-index: 10` 的 MMD canvas 抢占 DOM 命中。补回交互层包装后，pointerdown/click 均命中按钮；动态 Insets 同步同时解决右侧布局落入系统安全区的问题。

## 2026-10-08 UE 风格 SSGI 历史输入与光照分类（已实现，设备验收待完成）

参考用户提供的《UE5 SSGI源码解析》文章存档（知乎原文：https://zhuanlan.zhihu.com/p/2075720410394580895）：SSGI 使用前帧 SceneColor 作为入射光颜色输入，结合 Reduction 颜色层级与 HZB 深度层级，经过重投影后做短射线查询；射线结果再由 SS Denoiser 使用深度引导双边滤波，抑制噪点并尽量保留几何轮廓。这里实现的是历史场景颜色输入，不直接把上一帧 SSGI 输出做无条件时域累积。

面板层级调整为“间接光 -> SSGI”，SSGI 作为子类控件组；接触阴影仍为独立类别。移除实验性质的可见命名，但实现仍只在独立 MMD-AR 测试网页/测试 APK 副本中生效，不修改正式显示端。沿用默认关闭、已有质量/强度设置和本地存储键。

每帧先保存未合成屏幕光照的场景颜色及深度，历史为双缓冲且输入/输出分离。颜色与深度按每维最多1/2逐级缩至效果分辨率；颜色四点采样以对应深度和当前逆投影做深度权重，避免跨轮廓混色。普通Z下HZB每层保存near=min/far=max范围，空层用near=1/far=0表示（near对应UE reversed-Z的max-near语义），RGBA两组16-bit编码后兼容8-bit附件。射线按上一帧投影位置及屏幕步长选HZB粗层，候选用mip0细化并反投影到当前深度验证；验证失败回退当前帧SceneColor，命中颜色仍执行限幅与置信度权重。SSGI每帧重算，不累加历史SSGI结果。

SS Denoiser 使用深度/法线引导双边空间滤波，仅处理 SSGI RGB；接触阴影 alpha 保留中心值。历史只从未合成 SSGI 的场景颜色采集，历史读写纹理严格分离。分辨率/质量/投影变化、明显相机切断及WebGL上下文丢失/恢复时失效；GI关闭时释放Reduction/HZB历史，runtime销毁释放全部目标和材质。UI为“接触阴影”与“间接光 -> SSGI”并列/嵌套分类，保留默认关闭、历史设置键及参数默认。

当前runtime没有通用运动矢量；角色动画或动态物体的前后深度/当前可见性校验失败时保守拒绝历史并回退当前颜色。此举可能降低动态区域复用并造成局部闪烁，优先避免拖影。9项SSGI主功能定向测试、接触阴影步数兼容及两个浏览器测试合计12/12通过；SwiftShader真实WebGL2完成全部四个Screen Lighting Shader编译/链接；`npm run build:web:mmd-ar-test`成功。用户模型同视角、手机GPU帧时和画质仍待现场验收。
