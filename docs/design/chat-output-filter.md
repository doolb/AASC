# 聊天输出过滤与私聊清空交互设计

## 需求

1. 控制端聊天气泡只显示最终回答；有 think 内容时显示 Think 按钮，点击后在弹窗中查看思考内容。
2. 控制端以外的聊天回复气泡显示 think 正文和最终回答，不显示 `<think>`/`<thinking>` 标签。
3. TTS 按模型输出顺序播报 think 正文和最终回答，仅剥除 think 标签本身。
4. 聊天流、历史分别保留回答、思考内容和无标签的原始播报顺序；旧历史没有 reasoning 字段时继续正常显示。
5. 兼容模型只返回孤立 `</think>` 的情况：结束标记前可能包含内部角色配置，应继续丢弃，避免显示或播报泄漏内容。
6. 私聊点击“清空”时必须携带当前助手和私聊会话 ID；服务端拒绝时控制端要显示实际错误，不得静默无响应。

## 设计原则

- 聊天服务层解析并分流 answer、reasoning 和 speech；页面按自身展示策略选择折叠或展开，TTS 使用无标签 speech。
- 流式解析器按累计原始文本维护状态，支持标签跨 chunk 分割；不把未完成的 think 标签片段发送给界面或 TTS。
- 正常回复没有思考标记时 answer 与 speech 相同；未闭合 think 在响应结束时归入 reasoning 和 speech，但不得混入最终回答。
- Think 内容单独存入聊天记录，不进入后续 LLM 上下文；播报回放优先使用保存的 speech 顺序，兼容旧记录回退到回答正文。
- 清空私聊只作用于 `mode=private + target + sessionId` 对应范围，不扩大为该助手的全部会话。
- 清空请求的网络错误、HTTP 错误和业务错误都通过 Toast 告知控制端。

## 兼容边界

- 不修改 Chat2API 对外协议中的 `reasoning_content`，只清洗 AASC 内部聊天展示链路。
- 不处理 MNN `.mmap` 预生成，也不改变模型文件打包策略。
- 没有思考标签的普通文本原样返回，仅保留必要的首尾空白清理。

## 落地实现

- LLM 服务流式回调与非流式结果分别提供最终回答、思考正文和无标签播报文本；聊天历史以可选 `reasoning`/`speech` 字段保存后两者，历史上下文构造仍只读取消息正文。
- 控制端历史和实时聊天气泡只展示最终回答，Think 按钮按需打开安全 Markdown 弹窗；显示端语音回复气泡以安全 Markdown 展示原顺序的 think 与回答。
- TTS 分句队列和历史重播使用无标签播报文本；旧历史缺少新字段时继续回放最终回答。
