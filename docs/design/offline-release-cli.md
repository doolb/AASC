# Offline 自动出包与发布入口

## 需求与范围

用户授权增加自动调用命令：自动递增版本、根据待出包状态选择资源，并允许手动指定种类；补充完整 APK。新增 `npm run release:offline`，默认自动识别相同目录/目标的最近未完成任务，未找到则按状态构建；`--publish` 才发布 LAN/WAN，`--dry-run` 预览计划。`--only=min,code,deps,task,node,full` 可单选/组合；`--only=all` 显式选择全部六种。完整 APK 不进入默认自动选择。`--resume` 可无路径自动识别，也保留指定报告；`--fresh` 清理后使用原任务编号重建；`--new` 显式创建自动升号的新任务。

## 评审与落地

使用 analyze-requirement-level 的 enterprise 模式：主等级 L5（选择、升版、构建、发布、失败恢复），次等级 L6（CLI/报告契约）。证据是用户要求“自动增加版本号”“打对应包”“手动指定出哪种”“full apk也加上”。结论可开发，建议下放至 L4，能力等级 L5；权重为 L5 三项、L6 一项，一致性0.9，置信度0.675。评分：清晰度24/25、证据20/20、完备18/20、风险18/20、可落地14/15，共94/100。

下放动作：声明类型表与状态映射、版本扫描表、串行构建动作表、按实际变化选择的发布组件、不可变报告和恢复流程。无需翻译或额外伪代码同步技能；用户已授权实现，先写对应 spec。

## 关键规则

- 显式种类覆盖状态选择；deps 与 code 必须联合构建，锁变化也联动；输出实际选择原因。
- min/full 同一应用包名，版本号从两者历史和现行 APK 共同最大值递增，支持互相覆盖安装。
- 服务、依赖、任务与 Node 版本避开已发布和本地已占用版本；其他新任务避开失败预留编号；resume/fresh 沿用原任务编号。
- 独立 `.release-offline-versions.json` 持久化编号高水位，删除报告也不回收历史编号。用户明确 `--fresh` 清理旧任务报告及其未发布APK/ZIP；仅同项目、输出目录和目标，归档须严格数字版本普通文件，发布记录/当前签名引用/LAN存在/WAN实际目录存在/HTTP非404或无法确认均保留。只处理产物输出根，种子/修复ZIP和profile原始输出保持；不递归删除、跟随链接或触碰业务数据。
- 保留现有构建与发布器；为发布器增加 selected 模式，以最终签名清单一次切换服务/依赖/任务/min 的联合发布。
- 构建成功与发布成功分别记录。成功且源码未改变时才清除对应状态；未选中项保持。full 无独立待出包字段，不清除 min 状态。
- 发布失败用报告 `--resume` 重试，避免再次升版/重建；构建中断可复用已完成项，未完成项经两端未发布检查及精确清理后，沿用原号补建。fresh 清理后也复用最近任务已分配版本，缺少编号或已发布时停止；不会静默递增。基线变化则拒绝覆盖其他发布；本次已生效候选允许重试。
- 默认不自动提交 Git，不把 APK/ZIP/报告入 Git；调用者可根据退出码与 JSON 报告安排 Git 同步。
- 目录锁保护同入口并发；捕获正常停止信号，取消命令/网络后保存报告并释放锁。强制杀死或断电留下的锁不自动删除，先核对旧进程和构建子进程；既有手工发布进程仍需操作者避免交叉执行。私钥缺失时构建前失败，dry-run 不需要私钥。

## 风险与边界

完整 APK 可能很大且依赖模型/多平台依赖输入，真正构建/网络发布需要出包机。跨 LAN/WAN 不构造分布式事务；失败保留已成功目标并支持重试。源码指纹仅用于避免清除构建期间有变更的待办，不将 Git dirty 标志当作源码内容验证。
