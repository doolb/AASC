# OpenSpec 文档转换技能设计文档

## 概述

为项目增加一个本地 AI 技能，将 OpenSpec 变更目录中的 `proposal.md`、`design.md`、可选的 `specs/**/*.md` 和 `tasks.md` 转换为项目长期维护的 `docs/design/<模块>.md` 与 `docs/spec/<模块>.md`。技能只负责文档转换和追踪，不直接修改业务代码。

## 需求背景

OpenSpec 的变更文件侧重一次变更的提案、技术设计和执行清单；本项目的 `docs/design/*.md` 记录功能需求与系统设计，`docs/spec/*.md` 记录真实实现路径、契约和中文伪代码。两套文档的职责不同，直接复制或改名会造成设计与实现混淆、任务状态失真以及真实文件路径漂移。

## 功能需求

1. 读取 OpenSpec 四类输入并识别各自职责；`specs/**/*.md` 不存在时仍能转换，但要记录行为场景缺失风险。
2. 将 proposal 的 why/what 与 design 的 how 合并到项目 design 文档，保留目标、非目标、约束、技术决策、数据流、风险和验收边界。
3. 将 tasks 的分组、顺序、编号和勾选状态映射到项目 spec 的真实文件清单、实现伪代码、自测项和实施状态。
4. 转换前必须检查当前仓库代码与已有 design/spec，避免使用不存在的文件、类、接口或测试名。
5. 结果必须更新项目 design/spec 索引；按项目规则同步 task、todo 和 changelog。

## 目标与非目标

### 目标

- 建立 OpenSpec 计划文档到 AASC 文档规范的稳定转换流程。
- 保证需求设计、实现伪代码、任务追踪和验证结果相互可追溯。
- 让未来代理在调用技能时优先依据仓库真实结构，而不是相似文档或源文件中的猜测。

### 非目标

- 不替代 OpenSpec CLI 的 proposal/spec/design/tasks 工作流。
- 不自动实现或修改业务代码。
- 不把 OpenSpec 原始目录复制到 `docs/`。
- 不为不存在的模块创建虚假的实现状态或测试结果。

## 输入与输出映射

| 输入 | 输出内容 |
|------|----------|
| `proposal.md` | design 的背景、需求、范围、目标和非目标 |
| `design.md` | design 的现状、架构、数据流、决策、兼容性和风险 |
| `specs/**/*.md` | design 的行为边界、spec 的场景与回归契约 |
| `tasks.md` | spec 的真实落点、伪代码章节、自测映射和实施状态 |

## 输出文档结构

### `docs/design/<模块>.md`

至少包含：概述、需求背景、功能需求、目标与非目标、现状、约束、设计原则、核心架构、数据流、接口/数据模型、兼容性、风险与取舍、验收标准、相关文件。

### `docs/spec/<模块>.md`

至少包含：模块与真实文件映射、输入输出契约、数据流或状态转换、主要流程伪代码、异常与边界、任务追踪、自测与回归契约、实施状态。未来计划必须显式标记为待实现或待验证。

## 一致性与风险控制

- design 可以描述目标方案，spec 只有在代码或测试证实后才能描述为已实现。
- 每个 OpenSpec 任务编号必须对应 spec 中的落点；无法映射的任务列为待确认，不静默丢弃。
- 目标模块不明确时先确认，不从相似文档推断。
- 伪代码使用中文命令式语句，禁止出现可运行代码；复杂分支使用状态表、规则表或提前返回表达。
- 只做文档转换时不修改业务代码；若发现源文档要求代码变更，保留为 spec 的待实现项。

## 验收标准

- 技能文件可被项目 `.agents/skills/` 发现，frontmatter 名称和描述有效。
- 给定完整 OpenSpec 输入时，能够生成 design/spec，并保留任务编号和状态映射。
- 给定缺少 `specs/`、存在相似模块或存在虚假路径时，能够明确降级或请求确认。
- 生成的 spec 不包含可运行 JavaScript，不把未验证任务写成已完成。
- 项目索引、task、todo、changelog 与本次文件变更一致。
