# APK 生成 TTS 页面卡顿修复

## 任务描述

修复 Android 显示端 APK 在生成 TTS 时页面卡住的问题。ADB 未发现 ANR 或进程崩溃，但显示 WebView 在 TTS 请求期间同步处理 CPU 配置，重复重建 ASR/TTS native pool，造成 UI 主线程阻塞、TTS slot 线程累积和内存上涨；同时修复声纹回调跨线程调用 WebView 的问题。

## Design 需求

- `display.html` 消费 `cpuConfig` 时不允许同步调用原生 CPU 配置。
- 新增非阻塞 `cpuConfigureAsync`，原生侧串行应用配置并合并待处理的最新值。
- 相同 ASR/TTS policy 不得重复创建 pool。
- `voiceprintConfigure` 的 `evaluateJavascript` 必须在 WebView 主线程执行。
- 保持现有 TTS 生成回执、旧 APK/浏览器降级和服务器回退协议。

对应设计：`docs/design/android-native-tts.md`、`docs/design/android-display.md`。

## Spec 设计

- 页面将 `{asr,tts}` 稳定序列化并去重，只调用 `cpuConfigureAsync`。
- `NativeBridge` 用单线程后台 worker 执行配置，pending 只保留最新请求。
- `AsrEngine.configurePolicy` 与 `TtsEngine.configurePolicy` 在 policy 相等时直接返回。
- 声纹模型事件统一 `mainHandler.post` 后再执行 JavaScript。

对应伪代码：`docs/spec/android-native-tts.md`、`docs/spec/android-display.md`。

## 自测用例

1. 静态契约确认页面不存在 `cpuConfigure(JSON.stringify(...))` 的 CPU 配置调用。
2. 静态契约确认页面有异步桥和重复配置去重。
3. 静态契约确认 ASR/TTS policy 相等短路，不创建新 pool。
4. 静态契约确认声纹回调经 `mainHandler.post`。
5. 运行既有 CPU affinity、TTS 异步桥、WebSocket 重连 Node 回归。
6. 运行 Android JVM focused tests 和 `npm run build:apk`。

## 兼容性测试

- 浏览器显示端：没有 `NativeDisplay` 时不报错。
- 旧 APK：没有 `cpuConfigureAsync` 时忽略 CPU 配置；TTS 原有兼容路径不改变。
- 新 APK：CPU 配置后台应用，TTS `ttsGenerating` / `ttsResult` 协议保持不变。
- Android 9 / arm64-v8a 真机：验证 WebView 不因重复 `cpuConfig` 同步阻塞。

## 性能测试

- 重复 `cpuConfig` 广播不重复创建 ASR/TTS pool。
- CPU 配置桥调用立即返回，不占用 WebView 消息处理线程等待 native pool 构造。
- TTS 生成期间不应因配置消息新增无限 bridge worker 或 slot 线程。

## 风险评估

- 异步配置可能在短时间内晚于 TTS 请求生效；通过单线程串行和最新值覆盖保证最终状态正确。
- 旧 APK 不再使用同步 CPU 配置回退，旧包的页面流畅性优先于实时调整 CPU policy；新包才消费异步配置。
- 应用退出时后台 executor 随进程结束；配置失败只记录日志，不影响现有 TTS 回退。
