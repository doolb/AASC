## Design 需求

- 服务器持久化 `cpuAffinity`：

```json
{
  "cpuAffinity": {
    "asr": { "bigCoreCount": 1, "littleCoreCount": 1 },
    "tts": { "bigCoreCount": 1, "littleCoreCount": 1 }
  }
}
```

- `GET /api/config/cpuAffinity` 返回规范化后的 `asr/tts` 大小核数量。
- `POST /api/config/cpuAffinity` 接受 `{asr:{bigCoreCount,littleCoreCount},tts:{bigCoreCount,littleCoreCount}}`。
- 显式提供的字段必须是非负整数；`asr` 和 `tts` 每个引擎自身都至少保留 1 个槽位；缺失字段回填默认值。
- 保存后广播 `cpuAffinityChanged` 给控制端，广播 `cpuConfig` 给显示端。
- 显示端首次连接初始化路径同步发送 `cpuConfig`；旧客户端忽略未知消息。
- APK 读取 `possible` / `online` CPU 列表和 `cpuinfo_max_freq`，动态识别 big/little 集群，不硬编码 display2 CPU ID。
- APK 根据 ASR/TTS 配置数量生成确定性的 CPU policy，数量超过可用核心时裁剪并标记 fallback；Kotlin/JNI 统一支持 CPU ID `0..62`，CPU 63 和更高 ID 不进入 policy/mask。合法配置至少请求一个槽位且存在受支持 CPU 时不返回空策略；如果只有不受支持 CPU，则返回空 fallback policy 和 `cpuMask=0`，避免生成无法应用的非空 mask。
- APK 通过 JNI 对当前 native 线程调用 `sched_setaffinity`；失败只返回 false 并记录日志，后续语音请求路径必须能降级为 Android 默认调度。
- ASR 并发池大小为 `max(1, policy.totalCoreCount)`；每个槽拥有独立 sherpa-onnx recognizer，单槽 `numThreads=1`，识别前在槽 worker 线程应用 affinity。
- ASR pool 重建必须安全：配置变更或模型重载时先构造新池，替换成功后旧池只退休，不释放正在识别的 slot。
- Task 3 review 修复：旧 pool retire 后仍继续服务已 retain 的旧请求，包括已经阻塞等待空闲 slot 的请求；最后一个 retained 调用退出后再释放所有 idle slot，避免 queued caller 永久等待。
- TTS 并发池大小为 `max(1, policy.totalCoreCount)`；每个槽拥有独立 Microsoft Embedded Speech SDK `SpeechSynthesizer`，并且必须使用 `SpeechSynthesizer(config, null)` 只生成 WAV，不连接默认扬声器。
- TTS 每个槽拥有自己的单线程 worker，合成前在 worker 线程应用 affinity；`CpuAffinity.applyCurrentThread()` 返回 false 只作为性能降级，不让合成失败。
- TTS pool 必须有显式有限准入：最多 `slotCount` 个活跃请求 + `slotCount` 个排队请求；超限立即返回明确 overload 错误，不能让 cached executor caller 无限阻塞在 `idleSlots.take()`。
- NativeBridge 必须有严格桥侧有限准入：`TtsBridgeDispatcher` 的 worker 数与队列容量均为 `max(1, policy.totalCoreCount)`；同步溢出返回普通错误 JSON，异步溢出返回 `accepted:false`，不能提交后再回调错误；TTS policy 成功应用后必须在提交同步锁内换代，旧 executor 允许排空且不打断活动任务。
- TTS pool 重建必须像 ASR 一样安全：模型加载或 TTS CPU policy 变更时先构造新池，替换成功后旧池 retire；已 retain、in-flight 或已经等待旧 slot 的请求继续完成，最后一个旧 caller 退出后再释放 synthesizer。
- `TtsEngine.probeVoice()` 除了关闭探测 synthesizer，还必须关闭 `SynthesisVoicesResult`，与 vendored Embedded Speech SDK 结果生命周期保持一致。
- `NativeBridge.cpuConfigure()` 应同时应用 ASR/TTS policy 并返回 `{ok, asr, tts, topology}`；TTS 模型未加载时缓存 policy，后续加载按最新 policy 建池。
- 控制端 `upload.html` 在现有语音设备区域补充 4 个数字输入：ASR/TTS 各自的大核数、小核数，默认值均为 `1`。
- 控制端 `tts.js` 负责 `GET/POST /api/config/cpuAffinity`、非负整数规范化、任一引擎至少一个槽位的前端兜底，以及状态文案更新。
- 控制端 `websocket.js` 收到 `cpuAffinityChanged` 后回填控件，避免多控制页配置漂移。
- 显示端 `display.html` 收到 `cpuConfig` 时，仅在 `NativeDisplay.cpuConfigure` 可用时透传给 APK；浏览器显示端和旧 APK 安全忽略，不影响原有 TTS/ASR fallback。

## Spec 设计（伪代码）

```text
DEFAULT cpuAffinity =
  asr.bigCoreCount = 1
  asr.littleCoreCount = 1
  tts.bigCoreCount = 1
  tts.littleCoreCount = 1

normalizeCpuAffinityConfig(raw):
  对 asr/tts 的 big/little 四个字段逐项读取
  缺失、存量非法值或任一引擎为 0/0 -> 该引擎 default(1+1)
  返回规范化对象

validateCpuAffinityPayload(payload):
  payload 不是对象 -> error
  已提供字段不是非负整数 -> error
  缺失字段 -> default
  asr.bigCoreCount + asr.littleCoreCount <= 0 -> error
  tts.bigCoreCount + tts.littleCoreCount <= 0 -> error
  返回规范化对象

GET /api/config/cpuAffinity:
  res = { status: 'success', cpuAffinity: normalizeCpuAffinityConfig(config.cpuAffinity) }

POST /api/config/cpuAffinity:
  parsed = validateCpuAffinityPayload(req.body)
  parsed.error -> 400
  config.set('cpuAffinity', parsed.value)
  broadcastToControls({ type: 'cpuAffinityChanged', cpuAffinity: parsed.value })
  broadcastToDisplays({ type: 'cpuConfig', asr: parsed.value.asr, tts: parsed.value.tts })
  res = { status: 'success', cpuAffinity: parsed.value }

display connect init:
  send asrConfig
  send ttsConfig
  send cpuConfig
  send voiceprintConfig

CpuCluster.detect(reader):
  possibleIds = parseCpuRangeList(reader("/sys/devices/system/cpu/possible"))
  onlineIds = parseCpuRangeList(reader("/sys/devices/system/cpu/online"))
  candidateIds = onlineIds 非空 ? onlineIds : possibleIds
  对 candidateIds 逐个读取 cpuinfo_max_freq
  读到频率 -> CpuTopology(cpuId, maxFreq)
  没有频率但有 candidateIds -> CpuTopology(candidateIds, freq=0, fallback="no_freq")

CpuTopology.policy(bigCoreCount, littleCoreCount):
  requested = 非负 big/little 数量
  supportedCpuIds = 0..62
  CPU 63 和更高 ID 不进入 policy/mask，因为 signed Long bit63 会变成负数
  多频集群 -> 最高频组为 big，其余为 little
  单频或无频率 -> 全部作为 little fallback 池
  selected = supportedBig.take(requestedBig) + supportedLittle.take(requestedLittle)
  selected 为空 且 requested 总数 > 0 -> 从 supported fallback 池取 1 个确定性 CPU
  selected 仍为空 -> 返回空 policy、cpuMask=0、fallback=true
  否则返回 bigCpus/littleCpus/正 Long cpuMask/effective counts/fallback reason

CpuAffinity.applyCurrentThread(cpuMask):
  cpuMask 为空 -> false
  native library 不可用 -> false
  nativeApplyCurrentThread(cpuMask) 仅解析 0..62 mask 位，使用当前 native thread id 调 sched_setaffinity
  syscall 失败 -> false

AsrEnginePool.configure(policy, modelFile, tokensFile):
  slotCount = max(1, policy.totalCoreCount)
  slotMasks = policy.selectedCpus 的单 CPU mask；selected 为空时使用 0 mask 自动调度槽
  为每个 slot 创建独立 OfflineRecognizer，config.modelConfig.numThreads=1
  构造失败 -> release 已创建 slot；保留旧池
  构造成功 -> 返回可排队 pool

AsrEnginePool.recognize(samples):
  slot = idleQueue.take()
  try:
    在 slot 单线程 worker 中:
      CpuAffinity.applyCurrentThread(slot.cpuMask)
      recognizer.createStream -> acceptWaveform -> decode -> getResult.text.trim
  finally:
    pool 未 retired -> slot 放回 idleQueue
    pool 已 retired 且 activeUsers > 1 -> slot 放回 idleQueue，继续服务已 retain 的旧请求
    pool 已 retired 且 activeUsers <= 1 -> slot.release()
  releaseRetain:
    activeUsers 减一
    retired 且 activeUsers == 0 -> drain idleQueue 并 release，slot release 原子防重复

NativeBridge.asrRecognize / asrRecognizeAsync:
  模型未 ready -> 保持旧 error/accepted=false 行为
  Base64 PCM 解码后调用 AsrEngine.recognize(samples)
  asrExecutor 允许多个 ASR 桥任务同时进入 AsrEnginePool；并发上限由 pool slot 队列控制
  60s 超时与 window.onNativeAsrResult 回调协议保持不变

TtsEngine.load(context, modelDir):
  校验 modelDir 与 2052.INI
  probeVoice(modelDir) 使用 SpeechSynthesizer(config, null) 获取声线
  probeVoice finally 同时关闭 SynthesisVoicesResult 与 probe synthesizer
  当前 policy = 已配置 TTS policy 或默认 1+1
  newPool = TtsEnginePool.configure(policy, modelDir, voiceName, embeddedKey)
  newPool 构造成功 -> currentPool 替换为 newPool；oldPool.retire；ready=true
  构造失败 -> 返回 false，不释放正在使用的旧 pool

TtsEngine.configurePolicy(policy):
  保存 currentPolicy
  当前模型未加载 -> return true
  基于当前 modelDir/voiceName 构造 newPool
  构造成功 -> 替换 pool；oldPool.retire；return true
  构造失败 -> 保留旧 pool；return false

TtsEnginePool.configure(policy, modelDir, voiceName, embeddedKey):
  slotCount = max(1, policy.totalCoreCount)
  slotMasks = selectedCpus 单 CPU mask；selected 为空时使用 0 mask 自动调度槽
  admission = fair Semaphore(slotCount + slotCount)  # slotCount 个活跃请求 + slotCount 个排队请求
  每个 slot 构造独立 SpeechSynthesizer(config, null) 并持有单线程 worker
  任一 slot 构造失败 -> release 已构造 slot；保留旧池
  构造成功 -> 返回 bounded pool

TtsEnginePool.synthesize(text):
  retain pool
  admission.tryAcquire() 失败 -> 抛 RejectedExecutionException("TTS 请求过多，请稍后重试")
  slot = idleQueue.take()
  try:
    在 slot worker 中:
      CpuAffinity.applyCurrentThread(slot.cpuMask)
      affinity false -> 继续合成
      result = synthesizer.SpeakText(text)
      SynthesizingAudioCompleted -> return result.audioData
      其他 reason -> 抛合成取消错误
  finally:
    admission.release()
    retired 且 activeUsers <= 1 -> slot.release()
    否则 slot 放回 idleQueue，服务已 retain 的旧请求
  releaseRetain:
    retired 且 activeUsers == 0 -> drain idleQueue 并 release

NativeBridge.ttsSynthesize / ttsSynthesizeAsync:
  模型未 ready -> 保持旧 error/accepted=false 行为
  synchronized(ttsSubmitLock):
  ttsBridgeDispatcher.submit(TtsEngine.synthesize(text)) 失败 -> 同步返回 {error} 或异步返回 {accepted:false,error}
  仅成功提交的任务调用 TtsEngine.synthesize(text)
  ttsBridgeDispatcher worker=max(1, policy.totalCoreCount)，queue=max(1, policy.totalCoreCount)
  TtsEnginePool 继续以公平 Semaphore(slotCount * 2) 作为额外准入保护
  60s 超时与 window.onNativeTtsResult 回调协议保持不变

upload.html:
  提供 asrBigCoreCountInput / asrLittleCoreCountInput / ttsBigCoreCountInput / ttsLittleCoreCountInput
  默认 value = 1
  提供保存按钮和 cpuAffinityStatus 文案

CpuAffinitySettings.normalizeCoreCount(raw):
  parsed = Number.parseInt(raw, 10)
  非数字或负数 -> 0
  return parsed

CpuAffinitySettings.normalizeEngineConfig(engine):
  big = normalizeCoreCount(engine.bigCoreCount)
  little = normalizeCoreCount(engine.littleCoreCount)
  if big + little <= 0 -> little = 1
  return { bigCoreCount: big, littleCoreCount: little }

CpuAffinitySettings.loadConfig():
  GET /api/config/cpuAffinity
  success -> applyConfig(cpuAffinity)

CpuAffinitySettings.saveConfig():
  payload = normalizeConfig(readInputs())
  POST /api/config/cpuAffinity with payload
  success -> applyConfig(cpuAffinity), updateStatus('已保存...')

WebSocketManager.handleMessage(data):
  data.type == 'cpuAffinityChanged' -> CpuAffinitySettings.handleConfigChanged(data.cpuAffinity)

display websocket onmessage:
  data.type == 'cpuConfig' -> applyCpuConfig(data)

applyCpuConfig(data):
  nativeBridge 不存在 -> return
  nativeBridge.cpuConfigure 不是函数 -> return
  nativeBridge.cpuConfigure(JSON.stringify({ asr: data.asr, tts: data.tts }))
```

## 兼容性测试

- 旧版显示端/浏览器不认识 `cpuConfig` 消息时应直接忽略。
- 旧配置缺失 `cpuAffinity`、字段不完整或某个引擎存量为 `0/0` 时，服务器回填该引擎默认值，不影响既有 `tts.device` / `asr.device` 配置。
- 旧 Android 设备缺少 cpufreq 时，APK 使用在线 CPU fallback policy；CPU 63 或更高 ID 会被排除并标记 fallback/clamped；JNI affinity 失败时只降级为 Android 默认调度。
- 旧 APK 没有 `ttsSynthesizeAsync` 时，display.html 继续使用同步 `ttsSynthesize(text)` fallback；Task 4 不修改显示端 JS 和控制端 UI。
- Embedded Speech SDK 合成器和声线探测器必须继续使用空 `AudioConfig`，确保 APK 生成阶段不播放本机扬声器。

## 性能测试

- Task 1/2 不引入新的原生并发执行，仅新增配置读写、WebSocket 初始化消息和 CPU 原语，性能影响可忽略。
- Task 3 引入 ASR 多 recognizer 池；并发上限受 ASR 配置核心数限制，单槽 `numThreads=1`，超额请求在池内排队。
- Task 4 引入 TTS 多 synthesizer 池；并发上限受 TTS 配置核心数限制，单槽单线程 worker，超额请求在池内排队。
- Task 4 review fix 补充显式有限准入；等待中的 TTS caller 数量也受限，避免 cached bridge executor 在高峰期无限增线程。

## 风险评估

- `config-app-service.js` 既是配置实例又承担导出接口，新增可序列化导出字段会污染 `config/config.json`。
- `server-app.js` 当前存在大量并行中的用户改动，提交整文件会混入无关变更。
- 多个 ASR recognizer 会增加 native 内存占用；默认 `1 大核 + 1 小核` 即 2 个 recognizer，需要真机继续观察 PSS/native heap。
- 配置重建如果直接 release 旧 recognizer 可能导致 in-flight ASR use-after-free，必须通过 retired slot 延迟释放规避。
- retired pool 如果不把完成 slot 重新放回旧队列，会让 reconfigure 前已经 retain 且等待 `idleSlots.take()` 的旧请求永久等待；已通过 `AsrEnginePoolTest.retire后旧池已排队请求仍会被旧slot服务` 覆盖。
- 多个 TTS synthesizer 会增加 Embedded Speech SDK native 内存占用；默认 `1 大核 + 1 小核` 即 2 个 synthesizer。本轮 Task 6 沿用已有 PSS/native heap 基线，后续如调整槽位数量仍需重新采集。
- TTS pool retire 若直接释放 active synthesizer，会造成 native 合成中的 use-after-free；已通过 `TtsEnginePoolTest.retire后旧池已排队请求仍会被旧slot服务` 覆盖。
- TTS pool 若只依赖 `idleSlots.take()` 排队，cached bridge executor 会在峰值下无限堆积等待线程；已增加显式 overflow 行为测试，要求超限立即拒绝。
- Task 4 review 修复后，`TtsEnginePool` 在 `idleSlots.take()` 前以公平 `Semaphore(slotCount * 2)` 非阻塞准入；final fix 进一步由 `TtsBridgeDispatcher` 在桥提交边界以固定 `slotCount` worker + 同等有限队列拒绝溢出，避免 cached executor 无限增线程。
- Task 4 final fix 的 dispatcher 换代与提交共享锁；旧 executor 使用 `shutdown()` 排空 active/queued 任务，不调用 `shutdownNow()`，确保 cpuConfigure 不打断既有 TTS 工作。
- `probeVoice()` 若不关闭 `SynthesisVoicesResult`，Embedded Speech SDK 结果对象会泄漏；已补充 focused 生命周期约束测试。
- `NativeBridge.cpuConfigure()` 先应用 ASR 再应用 TTS；若 TTS policy 构造失败，会返回错误但不回滚已成功的 ASR policy，后续可在集成任务里评估是否需要事务式回滚。
