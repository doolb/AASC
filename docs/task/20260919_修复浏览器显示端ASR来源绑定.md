# 修复浏览器显示端 ASR 来源绑定

## 任务描述

修复浏览器显示端有持久化 `displayId`，但在部分刷新、重连或 WebSocket ID 尚未回传时，向 `/api/asr/recognize` 上传的 multipart 表单缺少 `displayId`，导致服务端日志出现 `requested=- kind=-`，ASR 只回显而不进入来源显示端的语音命令处理链路。

本次不使用 `X-AASC-Display-Id` 请求头，仅使用 multipart 表单字段 `displayId`。

## Design 需求

- WebSocket 连接和 ASR 上传复用同一个持久化显示端 ID。
- 建立或重连 WebSocket 时立即写入运行时显示端 ID。
- ASR 上传时运行时 ID 为空，回退读取持久化显示端 ID。
- 服务端继续通过表单 `displayId` 绑定在线显示端，不按 IP 猜测浏览器来源。
- ASR 提供端与录音来源端可以不同，提供端的 `asrResult` 仍归属于原始来源端。

## Spec 设计

- `display.html` 声明运行时 `displayId`，连接初始化时使用 `getPersistentDisplayId()` 赋值。
- `sendAudioForRecognition()` 计算 `requestDisplayId`，只将其追加到 `FormData` 的 `displayId` 字段。
- 保持服务端 `getAsrRequestContext()` 对 `req.body.displayId` 的兼容解析，不新增请求头依赖。
- 增加显示端契约测试，防止后续只依赖异步 `displayId` WebSocket 消息而再次丢失来源字段。

## 受影响的功能模块和代码

- `src/apps/web-mediacenter/ui/public/display.html`：复用持久化 ID 构造 ASR 表单来源字段。
- `tests/display-asr-audio-pipeline.test.js`：验证连接初始化、上传回退和不使用请求头。
- `docs/design/server-side-asr-voice-input-processing.md`：补充浏览器来源绑定设计。
- `docs/spec/server-side-asr-voice-input-processing.md`：补充来源字段和伪代码。

## 自测用例

1. 显示端使用 URL 配置 ID 时，WebSocket 和 ASR 表单使用同一个 ID。
2. 显示端仅有 `localStorage` 持久化 ID 时，ASR 表单仍携带 `displayId`。
3. WebSocket 尚未收到服务端 `displayId` 消息时，ASR 上传回退到持久化 ID。
4. 浏览器 ASR 请求不增加 `X-AASC-Display-Id` 请求头。
5. 服务端收到有效表单 `displayId` 后继续进入统一语音命令处理链路。
6. 没有 `displayId` 的旧请求仍只回显，不按 IP 猜测来源。

## 兼容性测试

- 普通浏览器显示端保留现有 WebSocket 连接和 ASR multipart 协议。
- Node 子显示端现有表单字段和来源请求头逻辑不改动。
- 服务端 ASR 设备为 `server` 或 `display` 时均继续读取同一来源上下文。

## 性能测试

- 仅增加一次本地字符串读取和表单字段追加，不增加音频复制、网络请求或 ASR 推理次数。
- 保持服务端内存上传和既有 ASR 超时策略不变。

## 风险评估

- 持久化 ID 被手工修改且对应 WebSocket 未在线时，服务端仍会安全地只返回 ASR 回显，不会按 IP 错绑其他显示端。
- 运行时服务端回传 ID 与连接 URL 不一致时，以服务端回传值更新运行时变量；正常连接中两者应相同。
- 本次不改变 ASR 模型、声纹阈值、提供端选择或语音命令解析。
