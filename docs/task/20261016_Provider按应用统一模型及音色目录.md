## 需求评审

- 主等级L6，次等级L5，建议下放为L4数据流；拟复用目录→筛选→绑定→planner→适配器。证据：Provider列表未按应用分类（L6强），HTTP当前拼接聊天/语音目录（L6强），TTS别名已有voice默认映射且参数可覆盖（L5强）。置信度为6/9×0.90=0.60。
- 结论：需补充（范围确认后可实施），直接开发风险中；评分：清晰度22/25、证据19/20、完备度16/20、风险19/20、L4可落地性14/15，总分90/100。
- 范围与目标：首期建议只统一Chat2API现有chat/tts及四路网络TTS，系统原生沿用设备目录；用户尚未确认这一边界，直接包含系统会导致服务器无法兑现设备合成能力。
- 输入输出契约：建议id稳定且限定来源/name为声音名称；HTTP显式application/provider筛选，未筛选保持兼容；须确认用户接受这种展示名与调用ID区分，单用中文名存在同名歧义。
- 业务规则：建议生成音色模型固定voice，冲突明确拒绝，用户原映射保留；若仍允许覆盖，会出现选了声音模型却发出另一音色。
- 拆解动作：使用spec和.src的目录项、绑定、筛选、精确解析及兼容投影流程；不新建账号或配置存储。

## 自测/兼容/性能计划（待确认）

- 统一模型项、chat/tts与Provider筛选、无效或重复参数、空目录、已知3.1的68项、当前其他明确音色。
- 固定声音模型调用、请求/控制voice同值与冲突、同名来源隔离、英文ID大小写、自定义精确/通配冲突。
- 原models无筛选、旧model+voice、旧audio/voices、普通映射参数优先级、账号可见性和停用、缓存失效。
- 目录读取不触发上游合成/登录/配置写入；按Provider/底层模型一次取目录，缓存有界，不做音色逐项联网探测。
- 优先 `npm run check:chat2api`，补目标目录/planner/proxy用例；若后续涉及现有TTS消费者再跑对应npm定向脚本。
