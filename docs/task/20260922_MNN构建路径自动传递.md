# MNN 构建路径自动传递

## 任务描述

修复 MNN checkout 已存在但 Gradle 仍提示缺少 `AASC_MNN_ROOT` 的问题，使 npm APK 打包和直接 Gradle 单测复用同一份默认 root/revision 配置。

## design 需求

- 默认 root 为 `build/third_party/MNN`。
- 默认 revision 为 `d407447ed56c4121a11ccbd266dc184ca1ead0c2`。
- `AASC_MNN_ROOT`、`AASC_MNN_REVISION` 继续支持覆盖。
- APK 打包脚本显式传递解析后的 root/revision；直接 Gradle 不依赖 shell 环境变量。

## spec 设计

```text
resolveMnnBuildConfig:
  读取环境变量覆盖值
  缺失时使用 projectRoot/build/third_party/MNN 和固定 revision
  返回绝对 root 与 revision

buildApk:
  使用同一配置运行 MNN prepare
  将 root/revision 作为 Gradle project property 传入

directGradle:
  从 project property、环境变量或仓库默认值读取 root/revision
  校验官方 MNN checkout
```

## 受影响模块和代码

- `scripts/ops/mnn-build-config.js`
- `scripts/ops/prepare-mnnllm-android.js`
- `scripts/ops/build-apk.js`
- `src/apps/android-display/app/build.gradle.kts`
- `tests/mnn-build-command.test.js`

## 自测用例

1. 空环境变量下解析到 `build/third_party/MNN` 和固定 revision。
2. 自定义环境变量能覆盖默认 root/revision。
3. APK 构建命令参数包含 `aascMnnRoot` 和 `aascMnnRevision`。
4. 直接运行 `./gradlew :app:testDebugUnitTest` 的配置阶段不再因缺少 `AASC_MNN_ROOT` 阻断；完整执行受工作区已有 `assembleDebug` Gradle 锁占用，待该构建结束后复测。

## 兼容性与风险

- 不改变 MNN 编译选项、ABI、NDK、native 库或 APK 运行时行为。
- 不提交 MNN checkout 和 native 构建产物。
- 自定义 checkout 不存在时仍必须失败，避免生成缺少 LLM 能力的 APK。
