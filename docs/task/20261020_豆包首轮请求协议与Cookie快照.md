# 豆包新会话首轮协议与 Cookie 快照

## 任务描述与需求

用户要求按当前 Vivaldi 官网成功请求补齐 Chat2API Node 新会话首轮请求，并将续聊排查留待后续。保留 Responses 入口、同账号身份和现有错误分类；网页登录完成后保存 `www` 与 `accounts` 两个固定来源适用的 Cookie。

## 设计与伪代码

- 设计见 [豆包网页账号设计](../design/chat2api-doubao-web.md)；实现顺序见 [豆包网页实现伪代码](../spec/chat2api-doubao-web.md)。
- 账号凭据保留六项规范 Cookie 与 Node profile，新增按来源分开的快照。Android 登录捕获和已存账号外部网页“完成”分别采集；后者经一次性令牌和账号版本校验原子更新。
- 普通模型新会话首轮对齐浏览器实际静态字段、当前时间、时区和单条用户原文。动态签名与逐次追踪值不缓存；续聊代码维持现状。

## 受影响模块

- 服务端：豆包 Cookie 快照校验、账号存储、外部网页会话刷新、代理管理路由、Node 首轮构造、秘密脱敏。
- Android：登录捕获、外部网页完成保存、对应 JVM 单测。
- 文档与发布：design、spec、task、todo、changelog、Offline 出包状态。

## 自测、兼容与性能

- `npm run check:chat2api`：旧 Cookie 账号、首轮结构、续聊回归、刷新令牌与版本冲突、账号公开列表脱敏。
- Android `:app:testDebugUnitTest --tests com.aasc.display.Chat2ApiCredentialCaptureTest`；必要时复核登录 Activity 编译。
- 隔离 Responses 实例用当前同账号 Cookie 快照发送一条自然短句；同时记录 HTTP 与 SSE 业务结果，不以 HTTP 200 冒充成功。
- 每来源最多 64 项、32 KiB；最多两个固定来源。请求仍只发一次，不因错误自动重试。

## 风险评估与预计工时

- 官网动态 `a_bogus`、浏览器自动头与服务端风控不能靠静态字段复刻；实网通过与否必须单独报告。
- Android WebView 和桌面 Vivaldi 的 Cookie 集可能不同，后续可按相同来源规则比对。
- Android CookieManager 不提供 Cookie 的原 Path/Domain；同来源同名 Cookie 的网页恢复只写首项，Node 发送仍保存完整请求头顺序。
- 预计 4 小时，含实网诊断、服务端与 Android 回归。
