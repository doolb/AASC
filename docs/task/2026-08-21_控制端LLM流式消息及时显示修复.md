# 控制端 LLM 流式消息及时显示修复

## 任务描述

修复控制端普通聊天 LLM 的流式输出没有及时显示，必须刷新页面才能看到回复的问题。

## Design 需求

- 普通群聊/私聊 LLM 请求沿用控制端生成的唯一 `requestId`。
- 服务端每条 `chatChunk` 和最终 `chatResponse` 都透传该请求号。
- 不改变已有聊天内容、历史持久化、TTS 和工作 AI 角色消息路由。

## Spec 设计

- `handleChatMessage(options)` 接收 `requestId`。
- `chatStream` 的 `onChunk` 发送 `{ type: 'chatChunk', requestId, chunk, message }`。
- `onComplete` 发送 `{ type: 'chatResponse', requestId, success: true, message, history }`。
- `onError` 发送 `{ type: 'chatResponse', requestId, success: false, error }`。
- 未携带 `requestId` 的内部调用保持兼容；JSON 序列化时不强制新增空字段。

## 根因

控制端 `Chat.handleChunk()` 与 `Chat.handleResponse()` 会使用 `activeRequestId` 过滤异步消息。普通 LLM 服务端回包没有透传 `requestId`，因此实时消息被前端丢弃；服务端历史已经保存，刷新页面后历史加载使消息可见。

## 自测用例

1. 普通 LLM `chatChunk` 回包包含原始 `requestId`。
2. 普通 LLM 成功 `chatResponse` 回包包含原始 `requestId`。
3. 普通 LLM 失败 `chatResponse` 回包包含原始 `requestId`。
4. 工作 AI 角色既有 requestId 流式测试保持通过。
5. 控制端回包匹配当前请求时可直接更新流式节点，无需刷新页面。

- Node.js 普通聊天流式协议测试。
- AI 角色服务与 ClaudeBridge 现有测试。

## 性能测试

- 仅增加一个已有字符串字段的 WebSocket JSON 透传，不增加轮询、定时器或额外 LLM 请求。

## 风险评估

- 请求号缺失时仍按旧协议发送，兼容语音命令等内部调用。
- 请求号只用于前端回包归属，不改变历史存储和模型上下文。
