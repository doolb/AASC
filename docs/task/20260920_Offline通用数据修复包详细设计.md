# 任务：Offline 通用数据修复包详细设计

## 任务描述

设计一个支持所有持久化配置的 Offline JS 数据修复包。修复包通过服务端已有业务类修改配置并自动保存，也可以在服务无法正常运行时由 Offline 启动流程在 Node 启动前应用。

本任务只完成设计文档，不实现运行时代码和发布脚本。

## 已确认边界

- 支持 `config/`、`home/.config/aasc-user/` 和任务配置目录中的合法配置文件。
- 修复内容使用签名 `repair.js`，不使用 `repair.json` 或 JSON payload。
- JS 只能调用白名单原有业务类/服务对象，不直接访问配置路径和文件。
- 定位为只执行一次的配置/数据热修复；成功后按设备和 `repairId` 幂等跳过，失败或回滚允许重试。
- 支持修复包版本、最低服务代码版本、最低 APK 版本、数据版本和 repairId。
- 保留备份、原子保存、失败回滚和重复执行跳过。
- 不处理控制端 `requiredDataVersion` 并发冲突校验。
- 不允许修改日志、模型、results、源码、依赖、APK、证书和私钥。
- Chat2API 账号凭据作为敏感业务类能力支持，但默认不自动允许。
- mini、flash、pro 的多 Provider 路由暂不在本任务实现。

## Design 需求

- 新增可选 Offline 清单组件 `dataRepair`，保持现有 `schemaVersion: 1` 的旧客户端兼容性。
- 运行时配置修改统一进入 `RuntimeDataManager`，由原有业务类规范化、校验、持久化和广播。
- 修复脚本不接收主机绝对路径，只接收受控服务对象。
- 所有业务类操作先进入统一事务，任意失败都回滚全部变更。
- 只执行已验签的 `repair.js`，禁止脚本加载其他代码或访问 Node 原生能力。

## Spec 设计

```text
RepairBundle:
    repairId, repairVersion
    requiredCodeVersion, requiredApkVersionCode?
    requiredDataVersion, targetDataVersion
    script = repair.js
    capabilities[]

repair.js:
    接收 services、assert、readVersion 和 log
    调用原有配置类和 Chat2API 管理类
    不访问路径、文件、网络和系统命令

收到 Offline dataRepair:
    验签、校验 repair.js、能力和版本
    校验当前数据版本
    创建原有业务类事务代理
    执行 repair.js
    提交事务并持久化全部变更
    更新 applied state
    启动健康检查
    失败时恢复全部备份
```

## 自测用例

1. 构建并验签只包含一个 `repair.js` 的修复包。
2. 通过原有 `config` 类修改 AASC 配置。
3. 通过 Chat2API management service 修改配置、Provider、账号和模型映射。
4. 服务重启后验证运行时配置仍然存在并生效。
5. `requiredCodeVersion` 不满足时不执行。
6. `requiredApkVersionCode` 不满足时不执行。
7. `requiredDataVersion` 不匹配时不执行。
8. 相同 `repairId` 重复应用时跳过。
9. 任一原有业务类前置条件或校验失败时所有变更保持原值。
10. 写入中途失败时全部文件恢复备份。
11. 未注册业务类、路径访问、动态 require、网络和命令执行被拒绝。
12. 包含 `sensitive=true` 时前台显示敏感配置提示，日志不出现凭据。
13. 旧清单没有 `dataRepair` 时原有服务更新流程不回归。

## 兼容性测试

- 普通服务器运行时用户配置目录。
- Android Offline Runtime 的 `config/` 和 `home/.config/aasc-user/` 映射。
- 旧版 APK 读取包含未知 `dataRepair` 字段的签名清单。
- 代码更新后再应用数据修复包。
- LAN 可用、WAN 回退和两站点清单字节一致。

## 性能测试

- 多个原有业务类连续保存和多服务事务耗时。
- 备份空间不足时不修改任何目标。
- 修复包下载、解压和 hash 校验不阻塞 Android 主线程。
- 运行时保存不产生重复 WebSocket 广播或重复 TTS/模型加载。

## 风险评估

- 关键端口、TLS 和服务启动配置被修改后可能导致健康检查失败，需要目标适配器预检。
- 账号凭据属于敏感配置，必须显式允许，不能写入普通发布日志。
- `repair.js` 依赖原有业务类接口和最低服务代码版本，设备长期离线时可能无法直接应用。
- 运行时配置更新与服务重启之间存在短暂不可用窗口。
- 修复包不能替代代码更新；新字段、新路由算法必须先发布兼容代码。

## 预计工时

- 修复包格式、目标注册和版本门控：1.5 小时。
- 事务保存、备份和回滚：2 小时。
- Offline 构建、签名、发布和清理：2 小时。
- Android 下载、确认和状态流：3 小时。
- 单测、集成测试和文档：2 小时。
