# ASR 后台预热与输出路由保护

## 任务描述

修复正式 Android 显示端第一次 ASR 请求耗时约 15 秒，以及 Android 9/API 28 切换输出设备后 WebView 播放无声的问题。ASR 模型已经加载不代表 sherpa-onnx native recognizer 的首次 session/计算图已经初始化；输出设备选择不能用通信路由接口控制 WebView 的 `STREAM_MUSIC`。

## design 需求

- ASR 模型加载完成后，在后台对每个 recognizer slot 执行短静音真实推理；完成后才上报 ready。
- 预热不阻塞 WebView 主线程、录音线程和页面交互；预热中的 ASR 请求不进入未就绪的 native pool。
- Android 26–30 不用输出 SCO 或 `setSpeakerphoneOn` 强行改变 WebView 媒体路由；无法精确控制时保持系统媒体路由并回报 fallback。
- 输入录音 Bluetooth SCO 逻辑保持不变，不能因输出设置释放输入 owner。

## spec 设计

- `AsrEnginePool` 增加逐 slot warmup；`AsrEngine` 暴露后台 warmup 入口。
- `AsrModelManager.ensureBundledModel/ensureModel` 在 load 后执行 warmup，ready 只在 warmup 成功后发布。
- `NativeAudioOutputController.applyLegacyRoute` 改为 API 26–30 的 WebView 媒体安全回退，不再启动输出 SCO 或改写 speakerphone 状态。
- 更新音频契约测试和 Android 单元测试，覆盖 warmup 顺序、后台线程、输出 fallback 和输入 owner 隔离。

## 自测用例

- 模型 load 成功但 warmup 未完成时，页面不声明 `voiceRecognition=true`。
- warmup 在后台线程执行，每个 pool slot 至少调用一次真实 recognizer。
- warmup 完成后第一条真实 ASR 不再触发 10 秒级冷启动。
- Android 9 选择 SCO/A2DP/有线/内置输出时不改变 WebView 通信路由，不导致媒体无声，并回报 `system_default/fallback`。
- Native 输入 SCO 运行时切换输出配置，不释放输入 owner。

## 兼容性测试

- Android 9/API 28：SM-N9500，WebView `STREAM_MUSIC` 和 AIMIC-M4 SCO 输入。
- Android 12/API 31+：保持现有通信设备路由代码和状态回报。
- 浏览器显示端：无 NativeBridge 时既有 ASR/输出行为不变。

## 性能测试

- 预热只占用后台 worker；页面主线程不等待模型初始化。
- 启动阶段额外耗时允许转移到后台，ASR ready 前不接受显示端 ASR 请求。
- 每次模型 load 只为每个 pool slot 预热一次，不增加常驻 recognizer 数量。

## 风险评估

- 每个 slot 都执行一次真实推理会增加启动阶段 CPU 使用和模型初始化时间，但可消除首请求长尾。
- Android 26–30 无法精确控制普通 WebView 媒体输出，修复后控制端显示系统默认回退，不承诺伪造目标设备。
- warmup 失败时需保留已验证模型文件并允许后续重试，不能把运行时初始化错误误判为模型损坏。

## 执行结果

已完成代码实现：

- `AsrEnginePool` 按 slot 执行真实静音推理，`AsrEngine` 暴露后台预热入口。
