# Pi 与 Chat2API 原生会话复用

## 任务描述

修复 Pi Agent 连续聊天时 Chat2API/Qwen 原生 `sessionId` 偶发变化的问题。重点保证同一个 Pi 进程内正常复用 `previous_response_id`，Pi 上下文压缩或快照变化时使用稳定的 Pi 会话归属重建 Provider 会话，并在简洁日志中区分 Pi 会话和 Provider 原生会话。

## Design 需求

- Pi assistant 消息快照按语义字段比较，忽略运行时元数据。
- 每个 Pi 子进程生成独立 `piSessionId`，群聊、私聊和重置后的进程互不串链。
- 正常续接只发送 Pi 快照之后的消息并使用 `previous_response_id`。
- 快照重建发送完整 Pi input，同时清空 Chat2API 的旧 native state，避免将完整上下文追加到旧原生会话。
- 普通 Responses 客户端的会话校验和历史规则保持不变。

## Spec 设计

```text
Pi provider:
    semanticSnapshot = 过滤 assistant 运行时元数据后的消息快照
    如果 semanticSnapshot 是上次快照前缀:
        input = 本次新增消息
        request = previous_response_id
        mode = delta
    否则:
        input = Pi 当前完整消息
        request = piSessionId 对应 conversation
        mode = snapshot
    metadata = { aasc_context_owner: pi, aasc_pi_session_id: piSessionId, aasc_pi_context_mode: mode }

Chat2API:
    如果 owner == pi 且 mode == snapshot 且已有 nativeState:
        input = Pi 完整消息
        responseSession.nativeState = {}
    否则按 nativeState 是否存在选择增量或本地历史
```

## 自测、兼容性与性能

- 测试语义快照忽略 assistant 运行时元数据，仍正确返回 `previous_response_id`。
- 测试 Pi snapshot/delta 两种模式的 input、native state 和会话 metadata。
- 测试每个 Pi 进程生成稳定且不同的 `piSessionId`。
- 测试 compact 日志同时记录 Provider `sessionId` 和 Pi `piSessionId`，full 日志行为不变。
- 普通 Responses 会话、非原生 Provider 历史重放和既有工具调用测试保持通过。
- 仅增加进程内字符串和 metadata，未引入常驻线程或额外网络请求；Pi 进程销毁时相关状态随进程回收。

## 风险评估与预计工时

- 风险：第三方 Responses 实现不接受 metadata。当前 Chat2API 接口允许额外字段，且 metadata 只在 Pi 内部使用；若上游拒绝，可仅保留服务端 context 传递。
- 风险：上下文压缩后完整快照与旧 native 会话不能混用；实现明确在 snapshot 模式清空 native state。
- 预计工时：1.5 小时。
