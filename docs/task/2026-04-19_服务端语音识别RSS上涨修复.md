# 任务：服务端语音识别 RSS 上涨修复

## 任务描述

修复服务端语音识别在持续调用时 RSS 一直上涨的问题，重点处理 native 识别资源释放、请求堆积和临时文件清理。

## Design 需求

### 服务端 ASR 稳定性
- 服务端 ASR 需要限制并发访问，避免多个请求同时占用同一个 native recognizer
- 每次识别结束后必须立即释放 stream 和音频样本引用
- 临时音频文件在成功、忽略、异常路径都要清理
- 高负载时要快速失败，避免无限排队导致 RSS 持续升高

## Spec 设计

### `core/asr.js`
- 为 `SherpaOnnxASR` 增加串行识别队列
- 增加 `maxQueueLength`、`pendingCount`、`completedCount` 统计
- 将真正识别逻辑拆分为 `performRecognition()`
- 新增 `destroyStreamSafely()` 和 `tryCompactMemory()`

### `server.js`
- 增加 `cleanupTempFile()` 统一清理 `/api/asr/recognize` 的上传临时文件
- 当 ASR 排队过多时返回 429，避免请求持续堆积

## 自测用例

1. 启动服务端，确认 ASR 初始化正常
2. 单次调用 `/api/asr/recognize`，确认可返回识别结果
3. 连续多次调用 `/api/asr/recognize`，确认临时目录无残留文件
4. 模拟并发请求超过队列上限，确认接口返回 429
5. 观察服务端日志中的 RSS / ArrayBuffers，确认高频识别后不再持续单向上涨

## 兼容性测试

- Windows Node.js 服务端
- 已启用 `--expose-gc` 的启动方式
- 控制端、显示端、子显示端共用 `/api/asr/recognize`

## 性能测试

- 高频短音频识别下验证队列长度稳定
- 连续识别 50 次后观察 RSS 是否进入平台期
- 验证 429 快速失败不会阻塞后续正常请求

## 风险评估

- 中风险：串行队列会降低峰值吞吐，但能显著提升内存稳定性
- 低风险：临时文件清理为幂等操作，重复调用不会影响结果
- 中风险：部分调用方若未处理 429，需要后续补重试策略
