# 显示端重连直连媒体恢复

## 任务描述

修复浏览器/Android 显示端和 Node 子显示端首次播放、断线重连时媒体地址策略不一致的问题。保持原始媒体 URL 为首选，仅把 HTTPS 页面无法直接加载的 HTTP 资源代理地址作为失败备用，并确保持久化状态不被下发过程修改。

## Design 需求

- 单媒体、播放列表、`restoreState` 和节点就绪后的播放重发共用相同的媒体 URL 规则。
- 直连失败前不得主动请求媒体代理；客户端按已有 `fallbackUrl` 逻辑在资源加载失败后切换。
- 规范化只作用于 WebSocket 下发副本，不把代理 URL 写回配置或媒体库。
- 旧版遗留代理主 URL 尽可能解码回直连地址，并将代理地址放在 fallback。

## Spec 设计

- `docs/spec/media-library.md` 描述 `normalizeDisplayMediaMessage` 及其调用位置。
- URL 媒体保留 `url`；HTTPS 下 HTTP `url` 产生同源 `/api/media-proxy` `fallbackUrl`。
- `playlistStart` 遍历播放项；`restoreState` 处理当前媒体与当前播放列表。
- 不处理 Base64、临时媒体或无 URL 的对象；不修改输入对象。

## 自测用例

- HTTPS 单媒体 HTTP 地址保持直连优先，代理只放入 fallback。
- HTTPS、相对 fallback 原样保留；HTTP fallback 转为同源代理。
- 旧版代理主 URL 解码还原直连。
- 播放列表和恢复状态覆盖 URL 项，不改变 Base64/临时项或传入状态。
- HTTP 服务不创建代理地址。
- 静态检查实时下发、restoreState 和 playlistStart 均使用同一规范化器。

## 兼容性测试

- 保持 `url`、`fallbackUrl`、`playlistStart` 和 `restoreState` 的现有消息字段与客户端加载协议。
- 浏览器/WebView 使用已有媒体元素 `error` 回退；Node mpv 使用已有 `fallbackUrl` 备用加载。
- 旧服务端保存状态与不含 `fallbackUrl` 的旧媒体条目继续兼容。

## 性能测试

- 规范化只遍历本次消息中的媒体对象，不做网络探测、不读写额外文件；开销随播放列表项数线性增长。
- 未增加初始播放的网络往返。

## 风险评估

- HTTPS 浏览器可能因混合内容策略直接拒绝 HTTP 地址；此时应由客户端错误事件切换到同源代理。
- 代理端点仍受原有 SSRF 校验与网络可达性约束。
- 单元测试不能替代真实 Android/WebView、Node mpv 及目标媒体服务器现场验证。

- `node --test tests/display-media-payload.test.js`：8/8 通过。
