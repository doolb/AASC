# 显示端 TTS 与视频焦点竞争修复

## 任务描述

处理 Android 显示端播放 TTS 时其他视频被暂停，以及 TTS 自身一卡一卡的问题。重点确认并修复网页媒体恢复逻辑和原生音频焦点重复争抢造成的焦点来回切换。

## Design 需求

- TTS 播放期间由 TTS 持有唯一原生音频焦点。
- TTS 开始前记录当前视频是否正在播放。
- 视频保持画面和音轨播放，不主动静音、暂停视频或重新申请媒体焦点；系统可按焦点策略自动 duck。
- TTS 活跃期间屏蔽视频 pause/error/watchdog 的媒体恢复循环，避免视频和 TTS 互相触发恢复。
- TTS 队列结束、显式停止或页面销毁后不写回视频音频属性；仅在视频原来播放、后来确实暂停且控制端仍期望播放时恢复一次。
- 普通 TTS、文本媒体逐句 TTS、远程文本 TTS 共用同一协调状态。

## Spec 设计

- 显示端网页维护 `ttsVideoState` 和 TTS 音频焦点 owner。
- `requestNativeAudioFocus(owner = 'media')` / `abandonNativeAudioFocus(owner = 'media')` 对媒体请求做 TTS 活跃守卫。
- TTS 请求焦点使用 `owner = 'tts'`；TTS 结束后才释放。
- 视频在 TTS 活跃期间保持原始音频属性，禁止进入普通媒体焦点恢复重试。
- 文本媒体播放器通过开始/结束回调接入协调状态。
- APK 原生 `AudioFocusController` 和 `NativeBridge` 复用既有焦点回调协议，本任务不改变 Kotlin 层接口。

## 自测用例

1. 正在播放视频时启动普通 TTS：视频保持画面和原有声音，TTS 只申请一次焦点且音量为 100%。
2. TTS 播放中触发 video pause/watchdog：不申请媒体焦点、不启动媒体循环恢复；不修改视频音频属性。
3. TTS 连续多句：句间不修改视频音量、不释放焦点。
4. TTS 正常结束或显式停止：不修改视频音频属性；原来播放、后来暂停且仍期望播放时只恢复一次。
5. 文本媒体逐句 TTS 和远程文本 TTS：使用同一协调状态。
6. 无 NativeDisplay 的普通浏览器：保持原有网页兼容行为。

## 性能测试

- TTS 活跃期间不启动媒体焦点恢复定时器，减少 `play()` 和焦点请求次数。
- 视频保留解码和原始音频渲染，不重复暂停/恢复，降低卡顿概率。
- TTS 生成仍为异步任务，不在 WebView 主线程同步等待。

## 风险评估

- 视频在 TTS 播放期间保持解码和发声会占用少量 CPU/GPU，并可能与 TTS 混音；系统可通过 duck 降低视频音量。
- 个别 WebView 可能仍因系统策略暂停视频；此时只做有限的播放恢复，不重新抢占音频焦点。
- 原生焦点协议保持不变，旧 APK 页面仍可在无 owner 参数时使用默认媒体路径。

- 视频被 WebView 暂停时只允许恢复播放，不再启动媒体焦点循环；TTS 队列结束后不写回视频音频属性，仅按播放意图恢复视频。

## 二次修复：真机焦点循环

- 真机 `dumpsys audio` 确认 Chromium AudioFocusDelegate 的 `req=3` 与 APK 原生 `req=1` 每约 150ms 交替，网页把 `-3` 错误当成硬焦点丢失后再次申请 `GAIN`。
- 修复方案：原生改用 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`；网页忽略 `-3`，只对 `-1/-2` 恢复；`waiting/stalled` 不再触发焦点重申请。
- 原生 `AudioFocusController` 改用 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`；网页忽略 `-3`，只对 `-1/-2` 恢复；`waiting/stalled` 不再触发焦点重申请。
- 验证：新增焦点循环契约后显示端焦点测试 9/9 通过；重新构建并覆盖安装 APK 成功，进程 PID=16250，页面重新加载成功。
- 真机 `dumpsys audio` 显示 Chromium 使用 `GAIN`、APK 使用 `GAIN_TRANSIENT_MAY_DUCK`，未再出现此前约 150ms 的 `req=1/req=3` 交替抢焦点循环。

## 三次修复：视频音量恢复

- 曾尝试在 TTS 协调状态中保存并恢复 `mediaVideo.muted` 和 `mediaVideo.volume`。
- 后续按最终需求改为 TTS 开始和结束均不写回视频音频属性，以下一次修复的实现为准。
- 已完成：补充“不主动静音视频”契约，TTS 期间保留视频 `muted`/`volume`，并重新构建安装验证。

## 四次修复：TTS 期间保留视频声音

- 需求：视频不再由网页主动静音，TTS 和视频允许同时播放。
- 实现：移除 `beginTtsVideoCoordination()` 及 TTS 活跃视频恢复分支中的主动静音；仍保留 `MAY_DUCK` 焦点策略和视频焦点竞争保护。
- 验证：新增视频不静音契约后相关回归通过，Debug APK 构建、覆盖安装和 display 2 启动成功。

## 五次修复：TTS 音量保持 100%

- 需求：TTS 开始和结束均不修改视频声音，TTS 使用 100% 音量。
- 实现：协调状态只记录视频播放意图；普通、远程和逐句 TTS 播放前统一设置 TTS 音量为 1，视频恢复直接调用 `video.play()`，不经过临时静音的自动播放流程。

## 六次修复：TTS 使用独立高优先级焦点

- 需求：视频播放时 TTS 仍保持正常音量，允许视频收到系统暂停或失焦通知。
- 实现：原生桥增加独立 TTS 音频焦点接口，TTS 使用 `AUDIOFOCUS_GAIN_TRANSIENT`；视频仍使用 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`，网页按 owner 选择对应接口。
- 状态：该中间方案已被后续“显示端统一网页媒体焦点”方案替代。

## 七次修复：显示端统一网页媒体焦点

- 需求：视频、普通音频和 TTS 都属于同一个网页媒体源，不区分焦点 owner。
- 实现：删除独立 TTS 焦点接口；所有网页媒体统一使用 `requestAudioFocus()`/`abandonAudioFocus()`，只有显示端没有其他播放意图时才释放焦点。
- 验证：统一焦点契约 11/11，相关显示端/文本媒体/语音/睡眠回归 41/41；Debug APK 构建、覆盖安装和 display 2 启动成功，PID=20732。
