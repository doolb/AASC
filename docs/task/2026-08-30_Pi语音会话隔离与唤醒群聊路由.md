# Pi 语音会话隔离与唤醒群聊路由

## 任务描述

修复显示端进入私聊时复用群聊 Pi 历史、切换会话未重置 Pi 进程，以及群聊唤醒后通过音频流识别的普通文本仍被指令模式拦截的问题。

## Design 需求

- 群聊共用一个 Pi Agent 会话。
- 私聊按助手角色隔离 Pi Agent 会话。
- 模式或私聊角色切换时回收旧 Pi 进程；应用层历史不删除。
- 语音 chat 结果完整传递 `mode`、`target`、`sessionId`、`templateTarget`。
- `audioChunk` 完成 ASR 后按显示端当前会话状态传递 `conversationActive`。

## Spec 设计

- `chat.setMode()` 比较前后模式和目标，发生切换时重置旧 conversationKey。
- `chat.switchSession()` 切换私聊 sessionId 时重置旧 conversationKey。
- 私聊语音分支返回当前助手的模式、目标、会话和模板信息。
- 服务端普通语音聊天使用返回的会话元数据调用 `handleChatMessage()`。
- 音频流入口与普通 `voiceInput` 入口使用一致的活跃会话判断。

## 受影响的功能模块和代码

- `src/external/llm/llm-service.js`：切换模式时回收旧 Pi 会话。
- `src/apps/web-mediacenter/modules/voice/voice-command-app-service.js`：补齐私聊语音 chat 元数据。
- `src/apps/server/boot/server-app.js`：修正音频流活跃会话传递和语音聊天路由。
- `tests/group-chat-templates.test.js`、`tests/display-voice-normal-chat.test.js`、`tests/llm-agent-mode.test.js`：回归测试。
- `docs/design/*.md`、`docs/spec/*.md`、`docs/todo.md`、`changelog.md`：设计、伪代码和变更记录。

## 自测用例

1. 群聊唤醒后说无角色名普通文本，能进入正常聊天，不受 commandMode 拦截。
2. 进入私聊角色后，语音 chat 使用 private 模式、目标角色和默认会话。
3. 群聊切换私聊、私聊切换角色时旧 Pi 会话被回收，新请求创建独立进程。
4. 私聊历史只按目标角色和 sessionId 读取，不混入群聊历史。

## 兼容性测试

- 控制端群聊、私聊及手动会话切换。
- 显示端文本 `voiceInput` 与 `audioChunk` 两条 ASR 入口。
- 普通 LLM 模式不受 Pi 会话重置逻辑影响。

## 性能测试

- 同一群聊或同一私聊角色连续请求复用一个 Pi 进程。
- 模式切换不会遗留旧 Pi 子进程。

## 风险评估

- 切换时会终止旧 Pi 请求；这是会话切换的预期行为，应用层历史仍保留。
- 旧显示端不携带会话状态时沿用原有等待唤醒兼容逻辑。

## 补充问题

- 发现 `conversation.state` 是状态对象，原门控却直接与 `activeGroup`/`activePrivate` 字符串比较，导致 `conversationActive` 永远为 false。
- 补充在 `voiceInput` 和 `audioChunk` 两个入口记录门控状态，并统一使用 `conversation.state.state` 判断活跃会话。
