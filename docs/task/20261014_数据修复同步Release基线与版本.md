# 数据修复同步 release 配置、基线版本与真实结果

## 需求与状态

用户恢复处理之前新包数据修复验证不通过的问题，提出新增修复包时同时修改release目录配置并递增数据版本，新包携带该版本。用户已确认完整方案并补充要求实际写入现有两项修复；现已完成源码、种子与自动测试，正式出包/发布及真机验收待安排。旧“暂时不处理”决定已由本次恢复请求撤销。

## design 与 spec

对应`docs/design/offline-data-repair.md`、`docs/spec/offline-data-repair.md`顶部2026-10-14小节。主L6（发行种子/签名迁移/运行结果契约），次L5（准备、提交、初始化、执行、健康、拒绝、重试）；enterprise分析，主等级强证据为release同源版本与新包携带基线，次等级证据为真实版本拒绝与健康误报。置信度0.68，评分24/25+20/20+17/20+19/20+15/15=95；可开发，风险中，建议下放为L4的数据流与事务表达，不需要变更AASC拓扑。

新增基线`release/config/data-repair-state.json`用于实际已完成的种子修复。隔离临时项目用原业务服务执行相同脚本，配置、数据版本、修复归档与签名元数据成功后统一提交；失败不升版本。full与min首装只初始化新配置，旧配置与修复状态不覆盖。旧环境新累计脚本显式声明兼容0/1/2，依次补齐缺失配置效果；不篡改已发布v2，也不伪造旧v1已运行。真实执行结果与服务健康分别通知，失败自动去重但允许手动重试。

## 已定位证据

- LAN签名清单仍为`hide-offline-display-status-bar-v2`，requiredDataVersion=1、targetDataVersion=2；脚本只隐藏offline-display状态栏。
- 前序v1脚本开启voiceprint.acceptVoiceInputDuringTtsWithoutVoiceprint。新种子未包含数据修复state，缺状态按0处理；release配置当前也没有对应修复开关，新包未证明具备v1效果。
- `createOfflineDataRepairArtifacts`仅写repair.js ZIP及签名组件，不更新release种子；完整Runtime仅复制config/userconfig/task，没有数据版本。
- `NodeServerService`在服务健康后用字符串通知已应用，没有读取预期修复成功记录；Native更新器当前只按repairId寻找appliedRepairs。
- 当前实际设备数据版本仍未读取，本轮不把默认0推定为设备实测值。实施前full候选43/min候选45；本任务将候选改为full46/min47，full代码基线80，防止新full被旧min45自动覆盖。最终出包前核对所有最高版本与依赖基线。

## 影响文件与实施步骤

1. 已先更新spec，再新增`scripts/ops/offline-data-repair-seeds.js`及隔离业务执行入口，复用runner而不修改运行中的开发配置。
2. 修改`scripts/ops/offline-update-package.js`，接入种子事务、版本一致性和显式兼容版本；更新release/config/config.json及需要的release/userconfig文件，新增数据基线文件。只改修复实际涉及字段。
3. 复用`scripts/ops/build-apk.js`现有调用，修改`prepare-android-node-runtime.js`、`node-min-seeds.js`与`NodeRuntimeInstaller.kt`、`OfflineBootstrapManager.kt`，携带并在新配置初始化时恢复基线，增加中断恢复和既有状态保护。
4. 修改`data-repair-js-runner.js`及服务启动衔接，记录门控拒绝/成功/回滚真实结果；兼容集合仅来自已验签pending，不放宽未知版本。
5. 修改`OfflineUpdateManifest.kt`、`OfflineUpdateManager.kt`、`NodeServerService.kt`及必要的`MainActivity.kt`，传递兼容元数据、核对预期修复结果、按失败指纹去重并保留手动重试。
6. 新累计迁移脚本复用config/user-config业务方法，按真实阶段补齐两项历史修复，已有版本2不重复重置后续用户偏好；已发布v2字节保持不变。
7. 补充runner、构建与种子/Android自测，更新SelfTest只读检查和design/spec/usage/changelog/todo。确认源码完成后只提交本任务变更到origion；发布状态仅标记实际受影响项，不清除其他任务的dependenciesPackage状态。

## 自测与兼容

- 修复成功：实际release配置修改、版本递增、归档/签名/基线一致；二次相同版本拒绝且不修改文件。
- 修复失败/缺项/非法路径/并发配置变化：原配置与版本原样保留，不留下可误发布的成功清单。
- full首装、独立min首装、nodeMinSeeds：种子与版本同步；初始化中断恢复；覆盖旧用户配置和已有state时不抬版本。
- 旧包严格单版本继续支持，新累计包0/1/2正向迁移，未知版本拒绝；已包含/已覆盖旧目标不重复提示，不虚构旧repairId执行历史。
- 服务代码健康但修复拒绝/回滚：独立报告失败、不显示修复成功、不回滚健康代码；自动失败去重，手动重试/版本变化仍可执行。
- 累计迁移后校验声纹开关与offline-display状态栏；真实设备覆盖安装、LAN/WAN签名清单及实际下载另验。

## 性能、风险与工时

只复制小型配置，禁止扫描模型/日志/results；结果与版本读取有大小上限，不在查询时触发业务修复。预计2–4小时完成源码与自动验证，签名出包、发布及真实设备验收另计。风险为多文件事务失败恢复、旧客户端不识别新兼容声明、种子与既有用户配置的识别；使用私有暂存、变更前指纹比对、支持版本门控和首次初始化事务处理。

## 待确认与发布边界

完整方案已确认，现有两项修复也已追加授权并通过验签/原脚本摘要核验后实际写入。本轮不构建完整APK；“如果打新包”是携带基线需求，不视为现在授权完整APK发布。新的正式修复包编号、最低APK/代码版本和实际发布时机待出包时核对，不能覆盖v2归档。正式发布仍需先准备支持新协议的服务与APK，再生成累计修复包；不使用旧v2字节或未经核对的版本号覆盖发布。

## 实际写入与验收记录

`npm run sync:offline-data-repair-seeds`已执行并重复执行校验：声纹开关true、offline-display状态栏false、dataVersion/latestRepairVersion=2，includedRepairs为真实v1/v2身份与摘要，配置摘要一致；开发机运行配置与设备数据未执行修复。两份小型公开签名历史清单和v1脚本一并保存，支持重现；ZIP、APK与签名私钥不提交。

源码增加有界last-result、成功证明、旧失败去重及手动“重新检查”；只有重新确认更新才下载。配置损坏拒绝、失败回滚刷新内存并恢复pending；full升级的MUTABLE目录加入data-repair防止修复记录被旧目录清理。新数据包同时生成/签名首装种子，发布两项版本化文件后才切换清单；种子版本独立递增且不覆盖已有本地产物。
