# MNN native 线程数读取 CPU 配置

## 任务描述

修复 Android APK 的 MNN-LLM 线程配置链路：控制端配置的 LLM 大核数与小核数经过 `CpuCluster.policy` 计算后，必须真正覆盖官方 MNN runtime 的 `thread_num`，避免 JNI 虽然收到配置但官方 `LlmSession` 仍使用模型配置或默认 4。

## design 需求

- 保留现有 `llm.bigCoreCount`、`llm.littleCoreCount`、`llm.preferBigCores` 和 CPU mask 计算。
- `threadCount = max(1, policy.totalCoreCount)`。
- AASC JNI 创建官方 `LlmSession` 时，把 `threadCount` 放入 session 主配置；`keep_history`、mmap 目录等运行选项继续作为额外配置传递。
- 不改变 ASR/TTS 的配置、线程池和协议行为。

## spec 设计

```text
cpuConfig.llm
  -> CpuCluster.policy
  -> selectedCpus + cpuMask + threadCount=max(1, selectedCpus.size)
  -> MnnLlmEngine.load
  -> JNI 校验 thread_num
  -> sessionConfig.thread_num = thread_num
  -> official LlmSession(sessionConfig, extraOptions)
  -> Llm.set_config(sessionConfig)
  -> MNN runtime 使用 thread_num
```

## 受影响的功能模块和代码

- `src/apps/android-display/app/src/main/cpp/aasc_mnn_jni.cpp`：将校验后的线程数写入官方 session 主配置。
- `tests/apk-llm-explicit-thread-count.test.js`：增加 JNI 到 `LlmSession` 主配置的回归契约。
- `docs/design/android-mnnchat-llm.md`：修正线程数必须进入官方主配置的设计约束。
- `docs/spec/android-mnnchat-llm.md`：同步真实伪代码数据流和验收要求。
- `docs/todo.md`：完成后移除进行中条目。
- `changelog.md`：记录修复内容和验证结果。

## 自测用例

1. 默认 LLM policy 为 2 个大核、0 个小核时，JNI session 主配置包含 `thread_num=2`。
2. LLM 配置改为 1 个大核时，后续模型加载传入 `thread_num=1`。
3. JNI 不再以空主配置创建 `LlmSession` 并把线程数只放在 extra config。
4. ASR/TTS 配置和既有 LLM 请求协议测试保持通过。

## 兼容性测试

- 缺失或损坏的 CPU 配置仍由服务端规范化为有效配置。
- 只有一个 CPU 频率集群或大核不足时，沿用 `CpuCluster` 的确定性回退，线程数至少为 1。
- 旧 APK 不支持新字段时，不影响已有 ASR/TTS 和媒体功能。

## 性能测试

- 重新加载模型后用 `top -H` 观察 MNN native 工作线程数，不再以模型默认线程数运行。
- 对比 1、2、4 核配置下的推理 CPU 占用和首 token 时间。

## 风险评估

- 官方 MNN 版本的 `LlmSession` 主配置与 extra config 职责不同；通过固定 native revision、源码契约测试和真机线程观测降低配置未生效风险。
- 本任务只修正线程数传递，不扩大到 MNN native 工作线程 affinity 的实现重构；若真机仍出现线程跑出选定 mask，另立任务处理。
