# 聊天协议归属 LLM 服务器配置

## 任务描述

将聊天调用协议从全局聊天配置调整为每个 LLM 服务器配置。Responses API 不再单独配置 Base URL 和 Key，而是复用当前 LLM 服务器的 Chat Completions API URL 和 API Key。

## Design 需求

- `llmProfiles[]` 增加 `protocol`，支持 `openai-responses` 和 `openai-completions`。
- 当前 profile 的 `apiUrl` 是 Chat Completions 完整地址；Responses 模式去掉 `/chat/completions` 后缀并请求 `/responses`。
- 聊天设置页面只编辑系统提示词、Agent 后端等全局聊天级字段；服务端保留旧的 URL、模型等字段作为无 profile 配置的兼容回退。
- 旧配置启动时可用全局 `chat.protocol` 补齐缺失的 profile 协议，但忽略全局 Responses 地址和密钥。

## Spec 设计

- 控制端在 LLM 服务器编辑器中编辑协议、Chat Completions API URL 和 API Key。
- 普通聊天、`llm.chat` 任务和 Pi Agent 均从当前 profile 读取协议、地址和密钥。
- Responses 客户端按 profile 地址缓存；profile 切换或地址/密钥变化时不得复用旧客户端或旧会话指纹。
- 服务器端继续使用现有 `/api/chat/config`、`/api/chat/profiles` 流程，不新增独立配置接口。

## 受影响的功能模块和代码

- 控制端聊天设置：`upload.html`、`chat.js`
- LLM 服务与 profile 规范化：`llm-service.js`、`pi-runtime-policy.js`
- Pi Agent 与内置任务：`pi-runtime-manager.js`、`llm-chat.js`
- 默认配置及服务启动：`config-app-service.js`、`server-app.js`
- 回归测试：聊天配置、LLM Responses、`llm.chat` 任务和 TaskManager 注入测试
- 项目设计、实现伪代码、待办和变更日志

## 自测用例

1. 两个 profile 分别配置不同协议和地址，切换后普通聊天分别命中对应端点。
2. Responses profile 使用 `apiUrl=/v1/chat/completions` 时请求 `/v1/responses`，并复用同一 API Key。
3. Chat Completions profile 仍发送原有 `messages`、`max_tokens` 和 Bearer Key。
4. `llm.chat` 与 Pi Agent 不读取全局 `responsesBaseUrl`、`responsesApiKey`。
5. 旧配置缺少 profile 协议时可启动，并按旧全局协议补齐；新保存结果不包含全局 Responses 路由字段。

## 兼容性测试

- 旧 profile 没有 `protocol` 时按旧 `chat.protocol` 或默认 Responses 处理。
- 旧 profile 的 `apiUrl` 仍是 Chat Completions 完整 URL。
- 不修改聊天历史、会话键、模板、Agent 权限和显示端 LLM 协议。

## 性能测试

- Responses 客户端仅在当前 profile 的 API URL 或 Key 变化时重建。
- profile 切换不增加请求次数；会话复用逻辑仍按现有 Responses 会话指纹执行。

## 风险评估

- 旧配置的全局 Responses 地址可能与 profile 的 Chat Completions 服务不是同一实例；迁移后请求会按新规则进入 profile 服务，属于本需求的预期行为。
- 不合法协议回退到 `openai-responses`，不允许任意字符串进入请求分支。
- API Key 仍通过现有配置接口返回和持久化，未新增明文日志输出。
