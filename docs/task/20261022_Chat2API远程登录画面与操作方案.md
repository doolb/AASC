# Chat2API远程登录画面与操作方案

日期：2026-10-22；状态：代码及隔离自测已完成，真实官网人工验收待进行。

## 需求与设计

用户要求普通控制端远程操作服务器网页登录，暂不接Android；支持其他Provider，全服务只保留一个登录页，并与豆包运行页面分开。设计与伪代码：docs/design/chat2api-remote-login.md、docs/spec/chat2api-remote-login.md。

已核对现有10种Provider登录声明、账号OAuth/刷新以及豆包launcher/bridge。现有launcher换账号会关闭浏览器，运行bridge会整理官网旧页，因此登录页需要独立角色及资料/页面生命周期；复用启动和凭据基础设施，不能把登录页塞进运行页面集合。

## 分析与实现范围

沿用analyze-requirement-level enterprise：主L6登录浏览器及协议契约，次L5唯一页面生命周期。三项明确证据为多Provider、单登录页、与豆包运行页分离，主证据6/8×0.90=0.675。评分24/25、20/20、17/20、19/20、15/15，共95/100，可开发，风险中；建议按spec拆为页面角色、会话所有权、帧/输入、Provider捕获与保存L4流程。

拟修改chat2api.js/样式、通用浏览器启动封装、login-profiles声明复用及服务装配；新增登录会话管理、CDP画面/输入与AASC路由。Android不改。自测和文档同步按design/spec/todo/changelog/usage/task执行，代码修改时仅标记servicePackage。

## 验证、兼容与风险

用隔离浏览器夹具验证10种Provider采集声明、唯一登录页、切换关闭旧上下文、重复打开、双控制端占用、账号隔离、输入坐标/拖动/中文、帧背压、取消/超时，以及豆包运行页在登录/切换期间持续存在且不被导航。API Key类型保留原入口。实体官网由用户手动完成验证码，按Provider记录真实验收边界。

性能观察首帧与输入响应、帧确认背压、持续登录内存，不预先承诺帧率。风险为运行浏览器旧标签清理、独立资料与账号保存的一致性，以及不同官网验证流程。预计2～3个工作日，依真实官网验证情况调整。不明确需求：无；用户已确认实施。

本轮完成服务器WS会话管理、独立登录浏览器、共享凭据采集、控制端远程画面/输入、账号并发保存保护。新增定向自测和真实Vivaldi本地夹具；未操作真实账号或构建发布。

性能边界：固定视口、约3fps客户端拉帧、250ms服务端缓存、64项有界命令队列。真实官网响应和长期内存未做基准测试。兼容：保留Android原登录入口，普通浏览器走服务器入口。
