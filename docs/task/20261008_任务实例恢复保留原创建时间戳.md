# 任务服务重启恢复保留首次创建时间戳

日期：2026-10-08。状态：已完成。

## 任务描述

任务索引 `results/index.json` 中的 `timestamp` 是任务实例首次创建/提交时间。服务器重启后恢复 `mode=service && status=running` 实例时，`restoreAutoStartServices()` 再次调用 `submit()`，当前实现重新使用 `Date.now()` 覆盖该时间，造成索引文件无意义变化，并影响实例时长和排序语义。

## Design 需求

- 新建实例时继续生成当前 Unix 毫秒时间戳。
- 恢复已有运行中服务时保留索引中的非负有限数值时间戳，不因服务器重启重置。
- `display_offline` 孤儿恢复路径、普通外部提交、任务状态机和索引格式保持现状。

## Spec 设计

- `restoreAutoStartServices()` 对 running 服务调用 `submit(restoredEntry, { preserveTimestamp: true })`。
- `submit(task, options)` 仅当内部选项启用且输入时间戳为非负有限数值时复用该值；否则使用 `Date.now()`。
- 维持 `index.json` 当前结构，不新增实例元数据文件或 Git 忽略规则。

## 受影响模块与文件

- `src/apps/server/modules/task-engine/task-manager.js`：恢复时显式保留原时间戳。
- `tests/task-engine-restore.test.js`：断言恢复后内存实例与索引中的时间戳都不变。
- `docs/design/remote-task-system.md`、`docs/spec/remote-task-system.md`、`docs/todo.md`、`changelog.md`：同步行为、伪代码和完成记录。
- `release/offline-release-status.json`：标记服务代码包待重新构建。

## 自测用例

1. 构造一个带已知时间戳的 running service 索引实例，调用 `restoreAutoStartServices()`。
2. 确认恢复后的内存实例及 `results/index.json` 中该实例的时间戳均与原值相同。
3. 确认普通 `submit()` 不采纳外部传入的时间戳，仍由服务器生成当前时间。
4. 确认原有 running 显示端任务进入 pending 队列、display_offline 任务进入孤儿表的恢复行为不变。
5. 由于 package.json 没有该模块的定向 npm script，使用 `node --test tests/task-engine-restore.test.js` 运行相关恢复回归用例。

## 实施与本机验证

- `restoreAutoStartServices()` 恢复 running 服务时显式调用 `submit(..., { preserveTimestamp: true })`；`submit()` 只有在该内部选项启用且已有时间戳是非负有限数值时沿用旧值，普通新任务仍取 `Date.now()`。
- `tests/task-engine-restore.test.js` 为 running 显示端服务增加内存对象与实际磁盘 `results/index.json` 的原值断言；`node --test tests/task-engine-restore.test.js` 6/6 通过。
- `node --check src/apps/server/modules/task-engine/task-manager.js` 与 `git diff --check` 通过。完整仓库 `npm test` 未完成：追加过滤参数仍执行了全量用例，输出出现现有依赖路径/契约断言失败后已取消；未将其计作本次回归结果。
- 因修改服务端代码，`release/offline-release-status.json` 中 `servicePackage=true`；未构建或发布服务包。

## 兼容、性能与风险

- 索引字段和 APK/Offline 任务种子格式不变，旧索引可直接读取；没有合法时间戳时仍由 `Date.now()` 兜底。
- 仅增加选项判断和数值检查，运行时开销可忽略。
- 主要风险是将恢复选项错误暴露给普通提交，因此通过 `submit()` 的第二参数由恢复器内部显式传递，不从外部任务 payload 读取。
