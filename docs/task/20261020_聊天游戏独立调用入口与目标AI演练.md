# 聊天游戏独立调用入口与目标 AI 演练

日期：2026-10-20

## 任务描述与需求

用户要求把聊天与游戏协议解析单独提供为可调用 JS 入口，并用子代理扮演目标 AI，实际模拟一轮以测试功能。现有 `runGameAwareChat` 已是生产桥接逻辑，但独立调用仍需手工装配聊天接口、权威棋局和回调。新增入口只装配这些依赖，复用原有解析、校验与状态写入。

## Design 需求与 Spec 设计

设计见 `docs/design/game-gomoku.md` 的独立演练入口段；伪代码见 `docs/spec/game-gomoku.md` 开头。JS 入口接收临时棋局文件、显示端 ID、异步目标 AI 回调和事件回调，返回最终聊天、事件列表及快照；交互式 JSON 行脚本把模型请求和模型回复按实际 GM 结果往返。默认棋局文件在临时目录，显式指定路径才复用状态。

## 受影响模块与代码

- `src/apps/server/modules/game/game-chat-session.js`：可 `require()` 的独立会话入口；真实聊天模式选角色并转发原有 `chatStream`。
- `scripts/demo/game-chat-session.js`、`package.json`：JSON 行命令行入口及 npm script。
- `tests/game-chat-session.test.js`：普通聊天、目录/规则、开局、旧协议、失败回执与状态隔离。
- 五子棋 design/spec/usage、todo、changelog 和 Offline 待打包状态。

## 自测与兼容、性能

用真实桥接函数与权威服务检查对话中多次 AI/GM 往返，确认普通正文不触发游戏、非法协议不改棋盘、新旧格式均沿用既有约束。用子代理作为目标 AI，仅传给它入口产生的提示和 GM 原文，核对一轮开局的事件顺序与棋盘。单轮最多沿用桥接层七次续接，新增适配层只作内存事件记录与临时文件持久化，不增加外部网络请求。

## 风险与预计工时

风险在于演练入口与生产路径的行为漂移或误触真实棋局；入口直接调用生产桥接与权威服务，默认隔离临时棋局文件，且不建立 WebSocket。预计 2–3 小时，含设计文档、实现和演练。

## 执行结果

已新增可 `require()` 的会话入口和 JSON 行脚本，沿用正式 `runGameAwareChat` 与权威棋局。针对用户补充要求，真实聊天模式通过角色名读取项目已有模板，再交给正式 `chat.chatStream` 构造 `System:`、会话选项与流式请求；独立入口不手工拼接系统提示。`npm run test:game-chat` 31/31 通过，覆盖独立入口和既有五子棋回归。

用子代理扮演目标 AI、通过交互脚本逐次转交真实 GM 回执：用户要求 9 路开局 → AI 查询目录 → GM 返回五子棋 → AI 查询规则 → GM 返回规则 → AI 开局 → GM 快照版本 1 → AI 给出开局答复；下一条用户 C3 → GM 版本 2 确认黑子 → AI 选择 E5 → GM 版本 3 确认白子 → AI 给出自然语言。最终快照为 9 路、C3 黑子、E5 白子、轮到 User；协议行未进入最终聊天正文或 speech。该演练为隔离的完整回复适配器测试，真实模型账号、正式流式传输和 Android 显示端仍按原有待验收事项处理。

用户随后指定改用 `192.168.1.39` 的 qwenchat AI，且要求发送必须走现有聊天会话并选择角色。先前手工拼 `System:` 的试验只算非正式诊断：简单“只回复 OK”返回 HTTP 200、实际模型 Qwen3.7；游戏开局出现无效或残缺协议，之后两次上游 HTTP 403 `RGV587_ERROR::SM`（“被挤爆啦”）。

改由项目 `llm-service.chatStream` 执行真实 private 会话、读取现有“小爱”角色模板并请求同一 `aasc-qwen-flash` 后，Qwen 首答仍输出无效的 `Game:五子棋,AI,列表`；接着又将调用行放在自然语言后，权威棋局保持未开局。第二次同路径复测首答相同，纠错后收到空回复；桥接层最终给出“游戏操作已处理”的兜底文字，但棋盘仍为空。真实 Qwen 未完成一轮；模型协议遵循及空回复兜底语义需另行修正和验收。这两次测试均使用隔离临时棋局文件，没有写入实际显示端棋局。

同样路径再试 `aasc-qwen-pro` 也返回空模型正文，未创建棋局。该结果没有证明游戏解析出错；它确认当前不能把空模型回复视作“游戏操作已处理”。
