# 显示端播报层级与聊天语音自动发送

## 任务描述

将聊天 TTS 和天气详情放入 MMD 上方、聊天层下方的播报辅助层；聊天打开时隐藏仍在有效期内的天气详情和 TTS 文字，关闭后恢复未到期内容。同时修复聊天层语音识别只回显、不自动发送或不更新显示端聊天窗口的问题。

## 设计需求

- 层级：媒体 < MMD < 播报辅助层 < 聊天层。
- 聊天打开/关闭只影响播报文字和天气弹窗可见性，不停止音频。
- 聊天层打开期间语音识别直接发送到当前聊天对象/会话，绕过普通语音确认拦截。
- 语音聊天流式消息同时发送到控制端和发起语音的显示端。

## 自测用例

1. MMD、聊天 TTS、天气详情和聊天层按目标顺序叠放。
2. 天气详情显示期间打开聊天，弹窗隐藏；关闭聊天且未超时，弹窗恢复；超时后不恢复。
3. TTS 文字在聊天打开时隐藏，关闭后恢复未结束的文字；音频持续播放。
4. 聊天层打开后语音输入无需确认即可进入当前聊天，会话选择正确。
5. 显示端收到 `chatInput`、`chatChunk`、`chatResponse` 并更新聊天气泡，控制端同步收到消息。
6. 普通聊天关闭时保持原有唤醒词、确认和指令路由。

## 兼容性与风险

- 普通浏览器显示端和 Offline WebView 共用同一 DOM/WS 协议。
- 不改变天气/TTS 服务端生成和音频播放协议。
- 聊天层绕过确认仅限 `chatLayerVisible=true` 的显示端来源，控制端和普通语音不受影响。

## 后续缺陷修复

- 普通 `voiceCommand` 的 `response` 分支此前仍使用默认 `document.body` 宿主，导致普通 TTS 弹窗可能位于聊天层上方，且没有聊天打开抑制标记。
- 已将普通 response 弹窗改为追加到 `displayBroadcastLayer`，并设置 `suppressWhenChatVisible=true`，与天气详情弹窗统一处理。
- 已增加浏览器回归用例，实际验证普通 TTS 弹窗在聊天打开时隐藏、关闭后恢复，且生命周期计时不被重置。

### 普通聊天回复重复弹窗

- 根因：普通语音聊天完成时，无论来源端是否支持 `voicePlayback`，服务端都会发送 `voiceCommand/action=response`；有语音能力的显示端同时收到 `tts/playAudio`，于是出现 TTS 播报文字和 response 弹窗两份内容。
- 修复：复用服务端 `hasManualVoicePlayback(displayId)` 判断来源端能力；有语音能力时只保留 TTS 和聊天气泡，无语音能力时保留 response 文字兜底。
- 不改变实际 TTS 目标选择；来源端无能力但其他显示端有能力时，仍允许其他显示端播放，同时来源端显示文字兜底。

### 天气播报重复弹窗

- 根因：天气查询完成后，服务端既通过 `onTts` 发送 TTS，又无条件通过 `weatherResult` 发送天气详情弹窗；有语音能力的来源端因此同时显示播报文字和天气详情。
- 修复方案：复用来源显示端 `voicePlayback` 能力判断；有能力时只保留 TTS，来源端无能力时保留 `weatherResult` 天气详情文字兜底。
- 天气详情弹窗继续使用播报辅助层和聊天抑制生命周期，不改变实际 TTS 目标选择。

### TTS 播报文字自适应

- 现状：TTS 文字使用固定字号和固定旋转侧边距，Android 300% 缩放时可能超出屏幕，竖屏左右留白过大。
- 方案：按旋转逻辑画布短边、可用宽度和文本长度动态计算 `16px–36px` 字号，使用动态安全边距和最大高度，长文本自动换行并可滚动。

### TTS/天气弹窗左右空隙适配

- 现状：TTS 和天气详情弹窗同时受 `80% max-width`、固定左右 `50px` 内边距和旋转布局边距影响，Android 放大后左右空隙过宽。
- 方案：以 CSS 视口 100% 为基准计算弹窗外框，左右安全边距限制为 `8px–20px`，使用 `border-box` 将 padding 计入宽度，并覆盖 300% 手机视口和 90/270 度旋转。
