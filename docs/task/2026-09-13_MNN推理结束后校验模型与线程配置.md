# MNN 推理结束后校验模型与线程配置

## 任务描述

用户将 LLM CPU 核心数从 2 调整为 4 后，偶发观察到下一次推理仍未切换。现有逻辑只在下一次推理开始时按 policy generation 判断，且没有比较 MNN engine 实际线程数和已加载模型身份。本任务在当前推理结束后预检查并准备下一次运行时，同时在调用 native `generate` 前保留最终校验。

## design 需求

- 当前推理不被配置检查或 runtime 换代中断。
- 推理结束后仅在串行 worker 中检查，线程数不一致时从同一 `active` 目录安全加载候选 engine。
- 记录 `selectedModelId/selectedRevision` 与 `loadedModelId/loadedRevision`，模型切换仍复用既有切换队列。
- 下一次推理前比较模型身份、policy generation、配置线程数和 engine 实际线程数。
- 候选加载失败时释放候选并保留旧 engine，下一次推理继续重试；ASR/TTS 不受影响。

## spec 设计

```text
finishInference:
  decrement activeRequests and notify model switch waiters
  if no active request and no model switch is running:
    mark runtime preparation in progress
    reconcileRuntimeAfterInference()
    clear runtime preparation flag and notify waiters

reconcileRuntime:
  expectedModel = selectedModelId + selectedRevision
  expectedThreadCount = max(1, current llm policy totalCoreCount)
  actualModel = loadedModelId + loadedRevision
  actualThreadCount = currentEngine.threadCount
  if actualModel differs from expectedModel:
    leave model replacement to the existing switch queue
  else if generation differs or actualThreadCount differs:
    candidate = load activeDirectory with expectedThreadCount
    require candidate.threadCount == expectedThreadCount
    atomically replace currentEngine after candidate is ready

beforeGenerate:
  repeat the same model/generation/thread comparison
  reload safely or return an inference error when the runtime is inconsistent
```

## 受影响的功能模块和代码

- `src/apps/android-display/app/src/main/java/com/aasc/display/MnnLlmModelManager.kt`：记录已加载模型身份、实际线程数，推理结束后预检查，并在 generate 前最终校验。
- `tests/apk-llm-explicit-thread-count.test.js`：增加结束后预检查、模型身份和实际线程数契约测试。
- `docs/design/android-mnnchat-llm.md`、`docs/spec/android-mnnchat-llm.md`：同步运行时一致性伪代码和状态字段。

## 自测用例

1. 推理期间 2→4，当前请求继续完成，结束后候选 runtime 使用 4 线程加载。
2. 下一条推理前发现 engine 实际线程数仍为 2 时，重新加载后再调用 `generate`。
3. 已加载模型 ID/revision 与选中模型不一致时，不错误复用旧模型，交给模型切换队列处理。
4. 推理结束后 runtime 预加载失败，旧 engine 保持可用，后续请求继续重试。
5. 没有配置变化时不重复加载，也不重建 ASR/TTS pool。

## 兼容性测试

- 旧 APK 仅上报 `selectedModelId` 时，服务端既有路由字段保持兼容。
- 模型下载、模型切换、LLM 禁用/启用和请求取消流程保持原有等待顺序。
- ASR/TTS 的 policy、线程池和 affinity 行为不改变。

## 性能测试

- 配置变化后的模型加载耗时尽量发生在上一条推理完成后；下一条请求避免再次重复加载。
- 没有变化时，结束后校验只读取状态，不产生 native engine。
- 运行时短暂同时保留新旧 engine，确认候选失败时释放完整。

## 风险评估

- 推理结束后预加载会暂时占用额外 native 内存，必须候选成功后释放旧 engine。
- 模型选择与预加载并发时必须由状态锁和等待标志串行化，不能在 native 推理使用旧 engine 时释放它。
- 配置在候选加载期间变化时不得提交过期 candidate，下一次请求必须重新校验。

## 预计工时

约 1 小时，包含契约测试、APK 构建、真机短请求和日志验证。

## 实施结果

- 已在推理 `finally` 阶段记录 runtime 预检查状态；同一单线程推理 worker 在当前请求结束后校验并预加载下一次所需的线程配置，模型切换和禁用释放会等待该阶段完成。
- 已增加 `loadedModelId/loadedRevision` 与 `loadedThreadCount`，下一次 `generate` 前同时校验模型身份、policy generation、配置线程数和 native engine 实际线程数；候选 runtime 只有在配置未变化且线程数一致时才替换旧 engine。
- 服务端 LLM 路由保留实际加载模型字段，实际加载模型与选中模型不一致时不进入路由池；旧 APK 缺少字段时回退 `selectedModelId`。
- 定向测试：`apk-llm-explicit-thread-count` 4/4、APK 页面桥接测试 3/3、LLM 路由相关测试 5/5 通过。
- 使用固定 MNN checkout `d407447ed56c4121a11ccbd266dc184ca1ead0c2` 完成 `:app:assembleDebug`，APK 已安装到 `192.168.1.6:5555`。
- 真机验证：请求开始时日志出现 `thread_num:2`；请求期间切换到 4 后，请求结束阶段出现新的 `thread_num:4` 加载和旧 session 销毁；随后短请求只有 `submitNative`，未重复加载 runtime。
- 组合路由测试中的 ModelScope 缓存断言因工作区已有完整模型缓存而失败，属于既有测试数据状态与本次改动无关；配置已恢复为用户当前的 LLM 4 大核设置。
