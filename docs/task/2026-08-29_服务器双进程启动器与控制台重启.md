# 任务：服务器双进程启动器与控制台重启

## 任务描述

当前服务器通过 `/api/restart` 在服务进程内部 `spawn` 新进程，并使用 `detached: true`、`stdio: 'ignore'`。重启后新服务器脱离控制台，原控制台终端不再绑定服务进程，表现为服务器变成后台进程。

## Design 需求

- 新增前台常驻启动器，负责服务器子进程的启动、重启、异常退出恢复和信号转发。
- 服务器子进程继承控制台输入输出，不使用 detached 或忽略标准流。
- 主动重启后由启动器重新拉起子进程；普通停止信号不能触发自动重启。
- 重启前清理 TUI、WebSocket 和受管运行时，避免 TTY raw mode、端口和子进程资源残留。
- 不引入 WebSocket 代理；控制端/显示端允许短暂断线，并沿用现有重连和状态恢复机制。

## Spec 设计

- `server-launcher.js` 使用 IPC 接收服务器的 `restartRequested` 消息。
- `server-app.js` 在 IPC 可用时只发送重启请求并优雅退出，不再自行 detached 启动新进程。
- 启动器用继承标准流启动服务器，退出原因区分主动重启和外部停止。
- 对异常退出使用有限重启次数和递增延迟，防止崩溃循环占满终端。

## 自测用例

1. `npm start` 启动时启动器保持前台，服务器子进程继承标准流。
2. 调用 `/api/restart` 后，旧服务器退出，启动器拉起新服务器。
3. 重启过程中不出现 `detached: true` 或 `stdio: 'ignore'`。
4. 新子进程重新监听原端口并恢复 TUI。
5. `SIGINT`/`SIGTERM` 后启动器和子进程均退出，且不循环重启。
6. 子进程异常退出时按策略重启，超过上限后停止。
7. 运行启动器单元测试、相关重启脚本测试、语法检查和 `git diff --check`。

## 兼容性测试

- 保留 `npm run restart:server` 的 HTTP/HTTPS 调用方式。
- 保留直接执行 `server-app.js` 的开发调试能力；无 IPC 时不依赖启动器通信。
- Linux TTY、无 TTY 的后台启动和 `--no-tui` 模式均可运行。
- 控制端和显示端短暂断线后按原 WebSocket 重连机制恢复。

## 性能测试

- 常驻启动器仅维护一个子进程句柄和少量 IPC 事件，不参与 HTTP/WebSocket 数据转发。
- 正常运行不增加业务请求和轮询；异常重启采用延迟退避。

## 风险评估

- 服务器重启期间仍会有短暂 WebSocket 断线，不能实现零连接中断。
- TUI 画面会在新子进程启动时重新绘制，但控制台设备绑定保持不变。
- 服务器直接运行且无 IPC 时，重启接口只能退出当前进程，需由外部进程管理器负责拉起。

## 未明确需求

- 已确认：允许短暂断线，重点保持服务器控制台 TTY 绑定，不要求 WebSocket 连接零中断。
