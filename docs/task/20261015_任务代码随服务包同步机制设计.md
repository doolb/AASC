## Design 需求

1. 独立产物 task-code/task-code-vN.zip，独立版本/摘要，可只下载任务包。
2. 代码唯一源 res/tasks，明确选择 JS/HTML/CSS 等文件；首批四任务六文件共 31,019 字节源码，压缩大小待构建。
3. 配置、参数、实例、results、日志、任务链、模型及输入输出保持原目录与生命周期。
4. 复用现有签名服务 manifest，新增可选 components.taskCode；代码 ZIP 不嵌入任务快照。
5. 兼容约束参与候选计划；code/dependencies/taskCode 完整组合原子切换与失败回滚。
6. 现有 min56 不识别独立任务组件，需要支持版 min 原生与桥接服务，不能宣称仅服务热更足够。
7. 后续仅任务变更且兼容要求已满足时，不重新构建 code/deps/min；任务更新先通过受管服务重启生效。
8. 任务可声明精确 requiredDependencyVersion/requiredLockSha256，与服务的依赖锁定规则共同校验；不满足时选择兼容联合更新，不能只按版本较大推断兼容。
9. 任务必须声明服务代码包 codeRequirement，聚合为 requiredCodeVersion/maximumCodeVersion/taskCodeApiVersion；依赖包满足但服务代码过旧时也要联合更新代码包。

## Spec 摘要

```text
选择清单 + res/tasks → 独立任务 ZIP + 包内摘要清单
ZIP 身份与兼容约束 → 签名 manifest.components.taskCode
候选 := 验证 APK、code、任务 API、任务依赖版本/锁与实际依赖平台的兼容组合
多任务代码包区间/API → 求兼容交集，无交集或 API 冲突构建失败
多任务生产依赖要求 → 聚合为同一基线，冲突明确失败
变化集合 := 仅下载变化组件
候选全部就绪 → 原子 pending 组合 → Node 固定启动上下文
任务 catalog → 独立任务版本目录；业务数据 → 原 tasksDir
健康成功提交，失败恢复完整 previous
显示端通过既有 task:execute 获得当前有效代码
```

## 自测用例

| 场景 | 验收结果 |
|---|---|
| 独立构建 | 单独 task-code ZIP，六文件及包内清单，无配置/results/测试/模型 |
| 代码源与种子不同 | 内容来自 res/tasks，release/task 旧副本不影响有效代码 |
| 任务专用发布 | 原服务和依赖满足新任务要求时，只改 taskCode 引用；不满足则拒绝不兼容发布 |
| 任务专用下载 | 完整组合已兼容时只有 manifest 与必要任务 ZIP，无 code/deps/seeds 下载 |
| 内容复用/冲突 | 同版本同摘要复用，内容或兼容约束变化新版本，同版本异摘要拒绝 |
| ZIP 与身份异常 | 缺失、损坏、链接、越界、重复、大小写冲突、超限或元数据错配均拒绝 |
| 兼容约束 | APK/code/API 不兼容不启动；候选可组合时提示联合更新 |
| 任务代码包依赖 | 必需声明服务版本区间/API，包内外一致，实际 code 身份验证通过 |
| 多任务代码包约束 | 交集为空/API 不一致时报错，精确依赖可用相同上下界 |
| 代码包更新必需 | 依赖已满足但 code95 不满足 T2 的 code96 要求时，仍下载并联更服务包 |
| 仅代码发布 | 新服务不符合沿用任务的版本/API 约束时拒绝发布 |
| 任务依赖声明 | requiredDependencyVersion/requiredLockSha256 成对有效，包内外一致 |
| 版本与指纹 | 同版本异锁、较高版本但未声明兼容、平台/Node ABI 不匹配均拒绝 |
| 多任务要求聚合 | 一致要求生成包级约束，不一致明确报冲突；无新增约束仍满足服务原规则 |
| 仅改依赖要求 | 文件未变化但兼容声明变更时仍生成新任务版本 |
| 联合更新 | C1 绑定 D10/H10，T2 要求 D11/H11 时选择匹配 C2；拒绝 C1/D11/T2 |
| 联合更新回滚 | 新任务/依赖/服务任一失败，恢复旧依赖版本、锁指纹、组身份和任务代码 |
| 完整切换 | code/deps/taskCode 同一事务，不存在半组合活动状态 |
| 失败/断电/回滚 | 暂存未激活；pending 验证失败恢复完整 previous |
| 初次迁移 | min56 不能消费任务包；支持版 min+桥接服务可进入新路径 |
| 首装和旧指针 | 正确恢复种子数据，任务 catalog 独立；无任务指针按兼容路径 |
| 读取一致性 | 元数据、HTTP、入口、files、重连读取同一任务 revision |
| 数据保护 | 无业务写入 fixture 中，配置/参数/results/日志/输入/任务链摘要保持 |
| 自定义与受管写入 | 自定义原流程，受管错误发生在写入及生命周期变更前 |
| 移除与退役 | 不从旧目录补回代码，不删除历史数据 |
| 显示端恢复 | 原 instanceId/参数/任务链可用，无重复 DOM/定时器/监听 |
| 清理与镜像 | 仅处理严格任务版本资源，保留 active/pending/previous，链接和数据保护 |
| 其他客户端 | 新可选组件不破坏现有 Node/Termux 原流程，不谎报已消费任务包 |

优先使用既有 npm test、test:offline-bootstrap、test:offline-sync、test:subserver-update 对应的受影响用例；现有脚本无定向入口时才直接使用 Node test runner。原生验证使用项目既有 Gradle 检查入口。本轮新增test:task-code-sync定向入口和Android原生任务包用例；实际结果记录在末尾。

## 兼容性测试

- SM-N9500 Android 9、min56/code95 已有数据先升级支持版 min/桥接服务，再独立更新任务包。
- 同一任务包适配不同兼容服务版本；仅任务更新、仅服务更新和联合更新分别覆盖。
- 基础生产依赖组合版本与 common/android 组版本、taskDependencies 资源版本分开验证；新任务需求不能绕过现有服务 package-lock 约束。
- 完整 APK/min 首装、历史无任务字段指针、候选回滚到历史旧服务组合。
- 普通显示端浏览器缓存重验证、离线重连与同实例替换。
- Node/Windows/Linux 的共享清单与镜像路径兼容；其独立任务包自动应用暂不属于首期。

## 性能测试

- 当前服务/依赖满足任务要求时，测量任务 ZIP 与下载字节，确认不附带约 17 MB 服务包；需要联合更新时按实际组件记录字节及分组复用。
- Android 启动校验首批六文件的额外耗时以 500 ms 内为目标，需实测记录，尚未验证。
- catalog 建立一次索引，更新检查复用现有入口和轮询，不新增逐帧请求。
- 连续恢复同实例 20 次，覆盖层、定时器和监听数量不随次数增长。
- task-code-only 仍存在一次服务受管重启，记录中断/重连耗时，不能宣传为无中断热替换。

## 风险、未决与预计工时

中风险：独立组件涉及原生与服务两端协作，必须验证完整组合，而非只修改某个指针；旧 APK 忽略可选字段不能当成同步成功。发布器、镜像、状态及清理需共同识别新产物。任务读取入口遗漏、旧缓存 files、__dirname 数据写入和显示端释放分别以统一解析与定向用例覆盖。

服务当前精确绑定依赖版本及锁指纹，任务要求另一依赖基线时可能必须同时更新服务。构建前聚合冲突、发布前组合校验和启动前实际依赖校验是必要边界；不能把独立 ZIP 理解成允许任意版本混用。

设计不依赖未提供的外部资料。本轮采用待构建min58、任务服务下界96/API1；官方受管代码只读和四任务六文件已经用户确认执行。代码之外的资源、用户任务跨节点双向同步、独立网络 manifest 和无重启在线替换不纳入本次计划。

预计独立包/发布 0.5–1 天，原生组合/迁移 1–1.5 天，服务读取和显示端接入 1 天，定向兼容/回滚与文档 0.5–1 天，合计约 3–4.5 人日；真实出包发布等待另计。
