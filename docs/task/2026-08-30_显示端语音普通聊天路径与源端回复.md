# 显示端语音普通聊天路径与源端回复

## 任务描述

修复显示端语音输入未及时进入控制端正常聊天界面的问题，并确保语音普通对话的完整 `detailText` 和 TTS 回复回到发起语音输入的显示端。

## Design 需求

- 显示端语音通过现有唤醒/内置指令判断后，普通文本复用聊天服务端路径。
- 服务端在调用 LLM 前发送 `chatInput`，控制端复用现有流式聊天 UI，不重复提交请求。
- 普通语音回复向来源显示端发送完整 `detailText`。
- 来源显示端弹窗按文字长度计算显示时间，每 3 个可见字符 1 秒，最短 5 秒、最长 90 秒。
- 普通语音回复的 TTS 继续使用原有通用路由；来源显示端只接收完整弹窗内容，不自动播放专属 TTS。
- 内置指令、确认和唤醒提示保持原语音命令流程。

## Spec 设计

- `handleChatMessage()` 生成或沿用 `requestId`，先发 `chatInput`，再发送 `chatChunk/chatResponse`。
- 控制端 WebSocket 收到 `chatInput` 后设置当前请求号并调用 `showStreamingMessage()`。
- `voiceOriginDisplayId` 只贯穿普通聊天完成后的来源弹窗回传，不改变 TTS 路由。
- 显示端 `voiceCommand(response)` 使用 `detailText || text` 展示回复。

## 受影响功能模块和代码

- `src/apps/server/boot/server-app.js`：普通语音聊天请求事件、来源显示端响应和 TTS 目标。
- `src/apps/web-mediacenter/ui/public/js/websocket.js`：控制端 `chatInput` 消息分发。
- `src/apps/web-mediacenter/ui/public/js/chat.js`：复用正常聊天临时消息显示。
- `src/apps/web-mediacenter/ui/public/display.html`：使用 `detailText` 显示语音回复。
- `docs/design/*.md`、`docs/spec/*.md`、`docs/todo.md`、`changelog.md`：设计、伪代码和变更记录。

## 自测用例

1. 显示端说普通问题，控制端在 LLM 首个流式片段前出现用户气泡和助手占位气泡。
2. 同一 `requestId` 的 `chatChunk/chatResponse` 能更新控制端正常流式消息，且不会重复发送聊天请求。
3. 来源显示端收到完整 `detailText` 并显示完整回复。
4. 普通语音回复仍按原有通用目标播放 TTS，来源显示端只显示 `detailText` 弹窗。
5. 内置指令仍不产生 `chatInput`，原有语音播报和控制端提示不变。

## 兼容性测试

- 控制端文本聊天、私聊、群聊和控制端定向 TTS。
- 显示端内置指令、天气结构化回复、唤醒提示和普通语音聊天。
- 旧显示端忽略新增 `chatInput` 时，服务端聊天和来源显示端语音仍可工作。

## 性能测试

- 每次语音普通聊天只调用一次 LLM 请求。
- `chatInput` 为一次性轻量 WebSocket 事件，不新增录音、AudioContext 或 TTS 生成链路。

## 风险评估

- 若控制端未更新，忽略 `chatInput` 不会重复请求；已有 `voiceCommand` 和来源显示端回复仍可用。
- 来源显示端离线时沿用服务端发送失败保护，不影响控制端聊天历史和流式响应。
