# offline 首包启动解包优化

## 任务描述

优化 offline APK 首次启动时的 Node Runtime 安装流程。当前流程在 staging 完成解包和完整校验后，又把 Runtime 代码、依赖和模型复制到正式目录，导致包含近 1 GB 模型的首包启动出现不必要的二次 I/O。

## Design 需求

- staging 完成 manifest 文件大小与 SHA-256 校验后，使用同一父目录内的重命名直接切换为正式 Runtime 目录。
- 切换时保留用户的 `config`、`home`、`logs`、`res/tasks`、`res/uploads`、`res/temp`。
- 首次安装时仅初始化缺失的默认配置；不生成或预处理 `.mmap` 文件。
- 切换失败时恢复旧 Runtime，避免留下半安装目录。

## Spec 设计

伪代码已写入 `docs/spec/android-mnnchat-llm.md` 的“offline 首包解包启动补充伪代码”章节：完整校验 staging 后，旧目录改名为 backup、staging 改名为正式目录、恢复可变目录并写入版本标记；失败时逆向恢复。

## 自测用例

- 静态契约测试确认安装器使用 staging 原子切换，并且不再调用 `replaceDirectory(root, staging, "res/models")`。
- Android Display JVM 编译/单元测试通过。
- offline APK 构建成功，APK 可通过完整性检查。
- 真机安装启动冒烟，确认应用仍可启动 Node Runtime。

## 兼容性测试

- 已安装 Runtime 的快速复用路径不改变。
- 有旧配置、任务、日志、上传和临时目录时，升级后这些目录仍保留。
- 首次安装无旧 Runtime 时，staging 可直接成为正式目录。

## 性能测试

- 对比安装器代码路径，确认模型不再执行 staging 到正式目录的第二次复制。
- 记录 APK 体积、构建结果和真机启动日志；`.mmap` 本次不处理。

## 风险评估

- Android `File.renameTo` 需要 staging 与正式目录位于同一文件系统；本实现将两者放在 `filesDir` 同级目录，满足该条件。
- 若重命名或可变目录恢复失败，回滚逻辑会恢复旧 Runtime；异常路径仍可能遗留 backup，需要后续启动时再清理。
