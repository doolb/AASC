# 添加 Chat2API 到 Pi 工具转换

## 任务描述

修复 Agent 模式使用 Chat2API/OpenAI 兼容网关时，模型把工具调用作为 `<|CHAT2API|...>` 文本返回，导致 Pi 不执行 `read` 等工具、协议标签被发送到聊天和 TTS 的问题。

## design 需求

- 在 Pi Provider 边界完成 Chat2API 标签到 Pi 原生 ToolCall 的转换。
- 支持当前只读权限策略中的文件读取/搜索和受限网络工具。
- 普通文本不受影响，原始工具标签不能进入助手文本或 TTS。
- 未知工具、重复参数、未闭合标签和空调用禁止执行并返回清晰错误。

## spec 设计

- 新增纯函数解析器，输出剩余文本、工具调用或协议错误。
- `aasc-openai` Provider 使用 Pi AI 标准 OpenAI 流适配器作为底层流，并在最终消息边界转换 Chat2API 文本。
- 转换后的消息使用 Pi `toolCall` 内容块和 `toolUse` 停止原因，交给 Pi Agent 内部工具循环继续执行。

## 自测用例

- 解析日志中的 `read(path)` 调用并生成 Pi ToolCall。
- 同一响应解析多个调用和参数。
- 普通回答保持原文。
- Chat2API 标签被分片返回时，底层完成后仍能正确转换。
- 未知工具、非法标签和重复参数被拒绝。
- Provider 源码注册自定义 stream，且不再只注册无法转换工具标签的普通 provider 配置。

## 兼容性测试

- `mode=llm` 普通 LLM 路径不变。
- Pi 无工具的普通回答不变。
- Pi 原生 `tool_calls` 不被二次转换。
- 现有只读工具白名单和网络访问限制不变。

## 性能测试

- 转换器只对单次 AssistantMessage 文本做一次线性扫描。
- 不缓存完整历史之外的额外响应副本；Provider 适配层只在 Chat2API 文本转换时暂存当前响应。

## 风险评估

- Chat2API 标签格式可能因网关或模型不同而变化，因此只接受明确闭合的调用结构，并对未知格式报错。
- Provider 自定义流依赖当前 Pi 0.84.2 API；启动时若扩展加载失败，应由现有 Pi 请求错误处理回传。
- 工具执行仍受 Pi 启动参数和服务器固定白名单约束，不从模型文本动态开放权限。
