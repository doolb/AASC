# 显示端 ASR 能力状态回传修复

## 任务描述

显示端 `192.168.1.39` 的麦克风能力正常，但控制端显示“监听不可用”。原因是显示端连接 WebSocket 时先回传了初始 `voiceSupported=false`，异步 ASR 检查完成后没有补发最新 `voiceStatus`，完整能力状态也可能停留在 `voiceRecognition=false`。

## Design 需求

- ASR 状态异步确定后立即重新回传 `voiceStatus`。
- 同步更新并回传 `capabilities.voiceRecognition`，让服务端和控制端使用最新状态。
- 覆盖服务端 ASR、本地 ASR 和原生 ASR 模型就绪/失败路径。
- 不改变麦克风权限、监听开关、唤醒状态和命令处理规则。

## Spec 设计

```text
reportVoiceAvailability(available):
    voiceSupported = available == true
    currentCapabilities 已存在 -> 更新 voiceRecognition
    发送 voiceStatus(supported=voiceSupported, listening=isListening)
    currentCapabilities 已存在 -> 发送 capabilities

checkAsrStatus:
    native ASR -> 按模型状态回传
    本地 ASR 初始化成功 -> reportVoiceAvailability(true)
    服务端 /api/asr/status ready -> reportVoiceAvailability(true)
    失败或未就绪 -> reportVoiceAvailability(false)

detectCapabilities 完成:
    保存完整 capabilities
    按 capabilities.voiceRecognition 更新 voiceSupported
    同时发送 capabilities 和 voiceStatus
```

## 自测用例

1. 服务端 ASR 已 ready 时，显示端初始状态为 false，异步检查完成后控制端变为可用。
2. 服务端 ASR 未 ready 时，控制端保持不可用。
3. 本地 ASR 初始化成功后，补发 `voiceStatus.supported=true`。
4. 原生 ASR 模型 ready/error 后，分别补发 true/false 状态。
5. 麦克风 `voiceRecording` 能力正常但 ASR 未就绪时，不误报为监听中。

## 性能测试

- 状态只在能力确定或变化时补发，不增加录音和 ASR 推理次数。
- 不增加定时轮询；避免重复能力探测造成额外请求。

## 风险评估

- 能力探测完成时可能产生一次额外 `voiceStatus` 和 `capabilities` 消息，但只修正状态，不改变业务流程。
- ASR 服务确实不可用时仍然回传 false，不会绕过能力检查强制启动监听。

## 实现结果

- 新增 `reportVoiceAvailability()`，统一更新 `voiceSupported`、`capabilities.voiceRecognition` 并补发 `voiceStatus`/`capabilities`。
- 服务端 ASR、本地 ASR、完整能力探测和原生 ASR 模型 ready/error 路径均会刷新控制端状态。
- 验证：显示列表、语音会话、监听状态/回传、WebSocket 重连相关测试 7/7 通过；监听契约 19/19 通过；显示端内嵌脚本语法检查通过。
- `192.168.1.39` 当前服务端 ASR 返回 `ready:true`，实时连接也已回传 `voiceSupported=true`；当前仍显示不可用的原因是控制端持久化的 `userCapabilities.voiceRecognition=false` 手动覆盖了自动能力。刷新页面后需在该显示端能力面板开启“语音识别”，才能启动监听。
