# Chat2API 错误显示端提示

日期：2026-10-18；状态：实际请求复现并完成方案，待用户确认后实施。

## 任务描述与设计需求

用户要求实际调用 Chat2API 检查豆包 403，并让相关聊天错误也在显示端可见。全新豆包 Responses 流式请求收到 `response.created` 后紧接 `response.failed/doubao_risk_control`，没有传旧会话 ID，因此风险控制不能归因于旧会话不存在。设计详见 `docs/design/chat-system.md`。

用户进一步要求测试旧会话：从本机保存的最近一个 `ready` 豆包会话取上游状态内存副本，实际请求确认带入原 `conversation_id`、`need_create_conversation=false`，仍得到 `doubao_risk_control`（403）。测试未改写本地旧会话存储。官网同账号安全验证若出现滑块或短信流程应在官网完成；没有验证提示时不能把一次性码或 Token 填进 Chat2API 规避上游拒绝。

后续代码复核确认：适配器沿用当时抓取的网页请求结构，但由 Node Axios 发送，使用已保存的 Cookie/CSRF/nodeProfile 和动态生成的 `web_tab_id`，并不在当前已登录浏览器页面执行 `fetch`。官网能发送消息与此 Node 请求被 403 拒绝可以同时成立；真实触发因素仍需上游证据，不能单凭错误码指定为会话、Cookie 或某个设备字段。

2026-10-19 复测同一保存账号：Node 核心适配器的新会话与旧会话续接均返回 `doubao_risk_control`（403）。独立 Vivaldi 调试实例载入保存的 Cookie 和 User-Agent 后，官网网页确实发出新会话请求，但 HTTP 200 的 SSE 含 `STREAM_ERROR`、无回复正文块；临时实例与资料已清理。移植资料的独立实例不等同于用户日常浏览器的实时登录状态，后续需在官网核对验证/重新登录后再测。

## Spec 伪代码与受影响模块

见 `docs/spec/chat-system.md`。拟修改 `src/apps/server/boot/server-app.js` 普通聊天失败回调，把当前请求的公开错误文字定向送往语音来源或控制端指定的显示端；修改 `src/apps/web-mediacenter/ui/public/display.html` 与 `css/display.css`，以现有旋转弹窗显示醒目错误。显示端聊天窗原有 `chatResponse` 错误分支继续使用。测试新增显示端错误回显、目标过滤和迟到消息场景；同步 `release/offline-release-status.json` 中服务包状态。

## 自测、兼容性与性能

拟用定向测试覆盖控制端仍收到错误、语音来源显示端显示错误、控制端指定显示端显示错误、无目标不广播、旧请求不覆盖新回复、普通成功回复和显示端聊天窗原有错误。消息体仅含已公开的错误文字，不含 Cookie、令牌或上游验证参数；不增加额外上游调用。
