# LLM 显式线程数与核心绑定

## 任务描述

将 Android MNN-LLM 单次推理从“仅配置 CPU affinity”改为显式设置 MNN native `thread_num`，使一次推理的 native 线程数不超过当前 LLM CPU policy 选中的核心数；默认使用 2 个大核、0 个小核，不影响 ASR/TTS。

## 需求等级分析

- 主等级：L6（Android LLM 引擎模块契约）。
- 次等级：L5（线程与状态流程）、L7（JNI/native 引擎边界）。
- 结论：可开发；输入、输出、默认值和验收边界已由用户确认。
- 关键风险：仅修改 Java executor 数量不能限制 MNN native 内部线程；必须把 `thread_num` 传入官方 `LlmSession`，并在 native 创建线程前应用 affinity。

## design 需求

- LLM CPU policy 计算 `threadCount = max(1, selectedCpus.size)`。
- MNN 模型加载 options 显式包含 `thread_num=threadCount`，不使用模型默认值。
- 模型加载和每次推理前对调用线程应用当前 LLM CPU mask，native 工作线程继承该 mask。
- LLM 状态返回显式线程数和实际选中 CPU；ASR/TTS 配置、线程池和状态不改变。

## spec 设计

```text
cpuConfig.llm
  -> CpuCluster.policy
  -> { selectedCpus, cpuMask, threadCount=max(1,totalCoreCount) }
  -> MnnLlmEngine.load(options.thread_num=threadCount)
  -> MnnLlmEngine.generate(affinity=cpuMask)
  -> status.cpuPolicy/threadCount
```

## 自测用例

1. 默认 LLM policy 产生 `thread_num=2`、小核数为 0。
2. LLM 配置改为 1 大核时，后续加载传入 `thread_num=1`。
3. LLM 配置不会修改 ASR/TTS policy 或线程池。
4. MNN native 收到的 options 保留显式 `thread_num`。
5. LLM 禁用时不加载模型、不创建推理线程。

## 真机验收

- 使用 `npm run build:apk` 构建并安装到 `192.168.1.6:5555`。
- 使用 `npm run start:apk:display` 无参数启动。
- 启用 Qwen3.5 模型后查看 LLM 状态中的 `threadCount=2`、`selectedCpus` 和 `cpuMask`。
- 发送一次 Chat Completions 请求，确认推理只落在选定的两个大核范围内。
- 关闭 LLM 后确认 native engine 释放，重新启用后仍按显式线程数从缓存加载。

## 风险评估

- 风险：官方 MNN revision 对 options 字段的覆盖顺序不同。
  - 控制：固定 revision，native 入口校验并记录实际传入 options；构建后使用真实模型验证。
- 风险：系统 CPU 拓扑不足或 affinity 失败。
  - 控制：复用 `CpuCluster` 确定性回退，状态返回 `fallback`，不影响推理正确性。
