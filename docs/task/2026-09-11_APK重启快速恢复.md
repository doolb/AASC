# APK 重启快速恢复

## 任务描述

手动关闭 APK 显示端后允许暂时离线，但重新打开 APK 时，APK-SM-N9500 的内置 Node.js 子服务器应在 5 秒内重新连接主服务器。当前 Service 启动会对约 631 MB 的 Runtime 做全量校验，且在内容变化时重新复制 Runtime，导致恢复耗时约 3 分钟。

## design 需求

- 正常重启只执行 Runtime 版本标记和关键启动文件的轻量检查。
- 只有首次安装、APK 更新、内容指纹变化或关键文件缺失时才执行全量安装。
- 默认 Runtime 版本由构建输入内容指纹生成；显式版本配置继续优先，Node.js 版本很少变化不影响服务器代码更新检测。
- Runtime 完整校验通过后才更新已有 Runtime；安装失败清理 staging，并在下次启动继续修复。
- 记录快速复用、全量安装、Node 启动和 AASC 连接的阶段耗时。

## spec 设计

```text
启动 NodeServerService
    → 读取 runtime-manifest.version 和私有目录 .runtime-version
    → 版本一致且 Node launcher、启动入口和关键目录存在时立即复用
    → 复用路径跳过所有 Runtime 文件 SHA-256
    → 版本不一致或关键文件缺失时复制到 staging 并完整校验
    → 安装成功后写入版本标记，再启动 Node launcher
    → 记录启动阶段耗时和 AASC connected 时间
```

```text
构建 Android Runtime manifest
    → 对 Runtime、server、node_modules、证书和原生 Node 库生成稳定内容指纹
    → 未配置显式版本时使用内容指纹作为 manifest.version
    → APK 更新时仅在内容确实变化时触发一次 Runtime 安装
```

## 自测用例

1. 已安装 Runtime、版本标记一致且关键文件完整时，启动不计算全部文件 SHA-256。
2. Runtime 版本变化时，执行 staging 全量安装并更新版本标记。
3. 关键启动文件缺失时，执行修复安装。
4. 构建输入未变化时，自动生成的 manifest 版本保持稳定。
5. 修改 server launcher 后，自动生成的 manifest 版本发生变化。
6. NodeServerService 原有启动命令、退避重试和环境变量测试保持通过。
7. 手动关闭并重新打开 APK，记录 Node launcher 启动到 AASC connected 的耗时。

## 兼容性测试

- Android 9/API 28、arm64-v8a、SM-N9500 真机。
- 保留 Android 共享存储权限、HTTPS/WSS、自签名证书和媒体库行为。
- 保留 APK 更新后 server 包内容变化的 Runtime 更新能力。

## 性能测试

- 快速复用路径不读取并哈希 631 MB Runtime 全部内容。
- 普通重新打开 APK 后 Node launcher 启动至 AASC connected 目标不超过 5 秒。
- 首次安装和版本变化的全量复制仍允许较长耗时；复制中断时可能留下不完整的目录替换状态，由下一次启动重新完成安装。

## 风险评估

- 轻量检查无法发现所有文件的内容位翻转；通过构建内容指纹、关键文件大小检查和版本更新时全量校验控制风险。
- 内容指纹若生成不稳定，会导致每次 APK 构建都重新安装；需要使用稳定排序和确定性 JSON 输入。
- 目录级替换不是完整事务；若安装过程中进程被杀，下一次启动会因版本标记或关键文件检查失败而重新安装。
- Android 被“强行停止”后系统仍可能阻止后台自动启动；本任务只保证用户重新打开 APK 后的恢复速度，不承诺绕过系统强制停止。
