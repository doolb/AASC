# 任务：修复等待唤醒状态下确认词误匹配

## 任务描述

等待唤醒的显示端收到“拒绝奖励出街注意”时，因文本包含“拒绝”被错误判定为无需唤醒的内置确认指令，日志出现 `accepted=true`。需要保留确认/取消指令免唤醒能力，同时阻止普通语音包含关键词时进入命令处理链路。

## Design 需求

- 确认、拒绝、取消等免唤醒短指令必须按完整规范化文本匹配。
- 等待唤醒状态下的普通句子，即使包含“拒绝”或“取消”，也必须继续忽略。
- 不改变 activeGroup/activePrivate 下已有的确认和取消处理路径。

## Spec 设计

- `isBuiltinVoiceCommand(text)` 先按现有规则去除首尾空白和末尾标点。
- confirmation matcher 使用完整短指令集合，不使用对“拒绝”“取消”的任意包含匹配。
- `reduceConversationInput(waitingWake, text, ..., { isBuiltin })` 只有 matcher 返回 true 才生成 `{ type: 'input', bypassWake: true }`。

## 自测用例

1. `拒绝`、`拒绝。`、`取消`、`确认添加` 仍识别为免唤醒内置指令。
2. `拒绝奖励出街注意。` 和 `取消奖励出街注意` 不识别为免唤醒内置指令。
3. 等待唤醒状态下，上述普通句子返回 `accepted=false`，状态仍为 `waitingWake`。
4. 活跃群聊/私聊中的确认和取消处理不受影响。

## 兼容性测试

- 系统、报时、天气、搜索、录音、静音和停止播报等其他内置指令。
- 显示端等待唤醒、群聊和私聊三种状态。
- 标点、空白和中文全角标点规范化。

## 性能测试

- 指令判定继续使用内置定义集合扫描，不增加 ASR 或网络请求。

## 风险评估

- 以前依赖“取消xxx”在等待唤醒时免唤醒的调用需要显式唤醒；这是为避免普通 ASR 误识别污染命令链路的预期收紧。
- 活跃会话仍可交给原有命令处理逻辑，因此不会削弱已进入对话后的取消操作。
