## 任务描述

用户希望 qwen-chat、qwen-api、doubao-api 统一由 Chat2API 提供，并以 `input(text/audio/image/video)＋model＋系统提示词＝output(text/audio/image/video)` 调用。模型确定 Provider，Provider 再按应用场景解释受限提示词并选用上游接口。当前 qwen-chat TTS 已复用 Chat2API speech；另外两者尚未复用，Responses 只保留文字。

## 设计与伪代码要点

- 统一 schema 与能力矩阵，明确模型归属与歧义处理；保留旧文本/语音入口的协议兼容。
- `resolveModelOwner(model) -> provider`; `dispatchByApplication(provider, application, typedInput, systemInstructions, outputModalities) -> adapter`；应用分派不能只靠自然语言系统提示词猜测。
- Provider 专属 TTS 适配器先接三个已知来源。明确未接入的 ASR、图片/视频生成和理解能力，不静默丢弃媒体内容。
- 原 TTS 业务选择与 AASC/WebSocket 权威回传继续有效；API 密钥迁移由用户确认后另做安全/回滚策略。

## 自测用例

1. 已知/未知/同名模型严格归属；Provider 禁用、账号不可用、凭证缺失和超时明确错误。
2. 旧 `/v1/responses` 文本、流式、工具和会话续接以及旧 `/v1/audio/speech` 二进制 WAV 格式不退化。
3. qwen 网页/百炼/豆包同文本、音色、速度、音量与 WAV 严格校验；emoji 跳过仅 qwen-chat；豆包上一句上下文仅在既有 AI/Agent 兼容业务发送。
4. 输入图片、音频、视频及输出混合片段：支持则完整透传，不支持则可预期地拒绝，不能只生成空文字误报成功。
5. 原生 TTS、AI 模板继承、文本媒体、系统播报、队列/打断及远端配置重连兼容。
6. API Key 和上游返回中的私密字段、媒体数据不进入日志、账号公开列表或会话持久化。

## 兼容性、性能与风险

- 兼容：旧自定义百炼/豆包端点、已有凭证和显式模型/音色不得被迁移悄悄覆盖；迁移前不得清理旧值。UI 变化需同步使用文档和自测。
- 性能：按输入类型限制媒体大小和数量、请求时限/并发；大视频走引用/流，避免在每一层 Base64 复制或记录，复用既有 16 MiB 音频边界。
- 风险：当前 Responses 丢媒体；上游三方能力不同，不能承诺任意输入到任意输出；豆包 context_texts 的模型/资源限制；系统提示词自由文本作控制面存在歧义/越权风险；用户工作区已有独立的未提交改动须保留。
- 预计工时：首批协议+现有三路语音迁移约 2–4 开发日（需用户确认口径及测试环境）；其他模态按目标模型/接口逐项评估，不作无证据估时。
