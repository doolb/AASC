## 任务描述与设计需求

客户端已有一次可识别断连恢复，但实际仍见 `Responses 流式API调用失败: socket hang up`。读代码确认：Chat2API Responses 流先输出 `response.created`，后续上游错误进入代理外层异常处理时，由于 HTTP 响应头已发送，代理销毁连接，原错误码丢失。需求主等级 L6（流式接口错误契约），次等级 L5（恢复流程）；下放 L4 描述为“上游错误 → 公开错误事件 → 客户端恢复判断”。

## Spec 设计与影响代码

先更新 `docs/spec/chat-system.md`。`chat2api-proxy-service.js` 在已发送事件的流中捕获上游异常，写出包含规范化 `code`、`statusCode`、`message` 的 `response.failed`，结束 SSE，不写 `[DONE]`。流开始前保持 JSON 错误响应；客户端断开后不写入。`llm-responses-client.js` 从失败事件读取上游状态，保留既有错误码判断。代理只记录阶段、码和状态，不记录输入、输出或凭据。集成测试验证原生会话位置不确定时连接正常结束且客户端拿到状态 409。
