# 修复 LLM 请求总时长超时中断

## 任务描述

当前本地 LLM 网关使用 120 秒固定总时长计时器。即使 APK 持续返回 `llm.chunk`，长回答超过 120 秒仍会返回 `LLM_REQUEST_TIMEOUT`。旧超时路径只拒绝 HTTP promise 并释放路由，没有向 APK 发送 `llm.cancel`，可能留下继续生成的 native 推理。

## Design 需求

- `llm.requestTimeoutMs` 改为无 chunk 活动超时，默认仍为 120 秒。
- 每收到任意 `llm.chunk` 都重置计时器，持续生成的长回答不因总时长被截断。
- 超时必须发送对应 `requestId` 的 `llm.cancel`，复用 APK 原生取消链路。
- 超时后服务端拒绝 HTTP 请求、清理 pending、释放路由；后续旧 chunk 不得恢复该请求。
- 不影响客户端主动断开、正常完成、其他 LLM 请求以及 ASR/TTS。

## Spec 设计

- `LlmGatewayService.startRequest()` 创建/刷新 idle timer。
- `handleDisplayMessage('llm.chunk')` 先刷新 timer，再转发 chunk。
- idle timer 回调调用 `cancel(requestId, LLM_REQUEST_TIMEOUT)`，不再直接调用只清理服务端状态的 `fail()`。
- `cancel()` 统一发送 `llm.cancel`、清理 timer/pending 并释放 router。

## 受影响的功能模块和代码

- `src/apps/server/modules/llm/llm-gateway-service.js`：实现 chunk 续期和超时取消。
- `config/config.json`、`src/apps/server/modules/config/config-app-service.js`：明确 120 秒参数语义。
- `tests/llm-local-routing.test.js` 或新增 LLM gateway 契约测试：覆盖超时取消、chunk 续期和路由清理。
- `docs/design/android-mnnchat-llm.md`、`docs/spec/android-mnnchat-llm.md`：同步超时协议。

## 自测用例

1. 超过 120 秒没有首个 chunk 时返回 `LLM_REQUEST_TIMEOUT`，并发送 `llm.cancel`。
2. 每 60 秒收到一个 chunk 的请求持续超过 120 秒仍不超时。
3. 超时后 pending 和 router active/queue 计数归零。
4. 正常 `llm.completed` 清理 timer，不触发超时取消。
5. 客户端主动断开仍只取消对应 requestId。

## 兼容性测试

- `/v1/chat/completions` 流式和非流式请求。
- `/v1/responses` 流式请求。
- Qwen3.5 Android MNN 显示端长回答。
- 旧显示端和 ASR/TTS 请求不受影响。

## 性能测试

- 每个 chunk 只执行一次 timer 重置，不增加模型推理轮询。
- 超时或完成后不保留 timer、pending 和 router 状态。

## 风险评估

- 如果模型在单个 chunk 之间超过 120 秒，仍会超时；该参数可后续按设备性能调整。
- 超时发送取消后，native 当前算子仍可能短暂收尾，但不会继续产生后续 token。

## 预计工时

约 30 分钟，包含网关测试和真机长回答验证。

## 实施结果

- `requestTimeoutMs=120000` 已改为无 chunk 活动超时；每收到 `llm.chunk` 都会重新计时，持续生成的长回答不再受固定总时长限制。
- 超时路径已复用 `cancel(requestId)`，向 APK 发送 `llm.cancel`，再清理服务端 pending、计时器和路由状态。
- 定向 LLM 测试 15/15 通过，网关语法检查通过。
- 已执行 `npm run restart:server`；Qwen3.5 真机流式请求重启后正常返回多个 chunk 和 `[DONE]`。
