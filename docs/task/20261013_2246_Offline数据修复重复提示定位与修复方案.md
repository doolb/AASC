# Offline数据修复重复提示定位与修复方案

状态：只读定位完成，代码方案待用户确认。

## 需求/design

用户询问APK为何一直提示已应用的数据修复包。ADB真机min40/code73日志为rejected-data-version（hide-offline-display-status-bar-v2）；包要求数据版本1→2。实际应用标记未满足，Native却在服务健康后通知应用成功，随后检查又发现同一pending。当前具体dataVersion未知，不将fresh默认0当作设备读取值。

## spec候选

```text
完成 := 目标repairId存在成功state才反馈修复成功
拒绝 := 当前数据版本不符签名前置条件 → 显示原因；不跳过门控或伪造成功记录
去重 := repairId/repairVersion/实际数据版本同一失败只提示一次，允许手动重试；状态变化重新评估
代码/修复 := 健康代码独立提交，修复失败独立呈现
```

## 影响代码和任务

候选修改OfflineUpdateManager.kt、NodeServerService.kt、MainActivity.kt及原生自测；读取当前应用私有root中的state/pending，保持现有服务端修复器和签名契约。原生变更需要新min APK，服务包/依赖是否受影响只按实际修改标记。目前状态全部false，未修改源码/profile或运行修复、未重新发布新产物。

## 自测/兼容/性能/风险

覆盖成功记录跳过、版本拒绝不写成功、健康服务不能冒充修复完成、同失败去重/手动重试/版本变化、混合代码更新加修复失败保留健康代码。旧state缺失按已有默认0规范化；只读有界元数据，不读取业务凭证。避免把拒绝错误隐藏成已应用，也避免全体服务更新被同一修复失败挡住。预计1–2小时含构建/发布/ADB。
