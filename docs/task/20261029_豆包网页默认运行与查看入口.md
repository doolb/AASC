# 豆包网页默认运行与查看入口（待方案确认）

## 用户目标与现状

用户希望数据修复包使Android豆包网页兼容模式默认运行，并询问查看WebView的入口。现有doubao.web任务启动后使同进程Chat2API走browser-fetch；Android桥通过受令牌保护的本机IPC使用后台WebView。当前只恢复上次running任务，不为新配置自动创建实例。账号管理“打开外部网页”启动Chat2ApiLoginActivity，是另一个WebView，并非后台运行页面。

## 拟定设计和规格

- 数据修复通过既有config业务服务启用Android豆包网页自动运行配置，保留其他任务、账号和自定义参数，不注入账号ID或凭据。
- 服务启动在恢复任务后检查Android环境及配置，复用TaskManager.ensureBuiltinServiceInstance确保一个doubao.web实例；网页仍按首个请求懒加载，不自动发聊天消息。
- 新增repair.js并用既有build:offline-data-repair生成下一版签名修复包，同步release配置种子与真实数据基线；需配套支持该配置的服务代码。不直接改设备配置或伪造修复记录，未获发布授权时不切换LAN/WAN清单。
- 可选实际运行页入口：豆包网页面板提供查看运行页面，原生桥调用同隔离进程的新Activity承载Service当前WebView；关闭仅返回后台，不清Cookie或更换账号。此项需要min APK更新，不能仅靠数据修复实现。

伪代码：
```text
修复输入 := 当前任务配置与数据版本
配置更新 := 业务config.set持久化Android豆包网页自动运行开关
服务启动 := 恢复原服务实例 → Android且已启用 → 确保doubao.web唯一实例
首次聊天 := 原账号解析 → 当前WebView页面fetch → 原Responses流
查看运行页（可选） := 原生桥 → 隔离Activity → 当前Service页面；关闭 → 页面归还后台
```

## 拟影响文件与验证

repair-sources中的新repair.js、任务自动启动辅助模块、server-app.js、release种子与基线；可选doubao-web.js、chat2api.js、Chat2ApiNativeBridge.kt、DoubaoWebViewService.kt、新Activity和AndroidManifest.xml。更新对应design/spec/todo/changelog及服务/原生产物状态。

测试包含修复幂等/版本门控/保留其他设置、已有任务复用/重启/启动失败、Android条件、查看/返回/服务销毁与未加载提示；隔离测试不调用真实上游。UI原生部分需配套APK实机验收。启动不自动生成消息或预加载所有账号，避免额外上游负载；账号目录沿用手机本地服务。预计修复启动与包30～60分钟，实际页面入口另需原生验证。风险为双实例与页面生命周期，使用现有唯一实例服务和明确页面归属处理。
