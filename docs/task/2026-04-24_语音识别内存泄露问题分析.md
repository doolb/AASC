# 任务：语音识别内存泄露问题分析

## 任务描述

分析当前项目中语音识别链路的内存泄露风险，区分服务端 `sherpa-onnx-node`、显示端 `sherpa-onnx-wasm`、子显示端 HTTP ASR 客户端三条路径，整理问题等级、现状、改进建议和验证方案。

## Design 需求

### 语音识别内存稳定性分析
- 需要识别服务端是否仍存在 native stream / WAV 解码 / 临时文件残留导致的 RSS 持续上涨风险
- 需要识别浏览器本地 ASR 是否存在 AudioContext、ScriptProcessor、WASM recognizer 和 stream 未完整释放的问题
- 需要识别子显示端是否因请求风暴、429 未退避、长连接对象未复用而放大服务端内存压力
- 需要给出可执行的监控指标和压测口径，便于后续修复验证

## 自测用例

1. 使用 `scripts/asr-stress-test.js` 连续调用 `/api/asr/recognize`，观察服务端 RSS / ArrayBuffers 是否进入平台期
2. 在浏览器连续执行多轮 `startStreaming()` / `stopStreaming()`，观察 Performance 面板中 AudioContext 和 JS Heap 是否回收
3. 子显示端持续录音识别 30 分钟，确认 429 或网络波动时不会形成请求堆积
4. 检查 `temp/asr` 目录，确认异常路径后无临时文件残留

## 风险评估

- 高风险：浏览器本地 ASR 当前 `stream` 在多次启停之间复用，若 WASM 内部状态未完全 reset，可能累积 native / WASM 堆内存
- 中风险：`createScriptProcessor()` 已废弃，浏览器实现差异会放大音频节点释放时机不确定性
- 中风险：服务端虽然已有串行队列和临时文件清理，但仍缺少长期 soak test 的自动化平台期判定
- 中风险：子显示端收到 429 后直接失败，若上层重试策略不一致，可能形成间歇性流量尖峰
