# MNN 线程配置异步应用失败重试

## 任务描述

用户将 LLM CPU 核心数从 2 调整为 4 后，部分场景必须重启 APK 才能再次生效。排查发现页面把 `cpuConfigureAsync` 的“入队成功”误当成 native 配置“应用成功”；当 ASR/TTS 忙导致实际应用失败时，同一配置会被页面永久去重。

## design 需求

- 区分 CPU 配置已入队和 native 实际应用成功。
- 原生配置失败必须回调页面，页面清理 pending key 并允许同配置重试。
- 成功配置才进入页面 `lastAppliedCpuConfigKey`，不能因异步入队提前确认。
- ASR/TTS pool 应用失败不能提前返回阻断 LLM policy 更新；LLM 线程切换必须独立生效。
- 不阻塞 WebView 消息线程，不打断当前 LLM 推理，不改变 ASR/TTS/LLM runtime 换代规则。

## spec 设计

```text
applyCpuConfig(config):
  key = stableSerialize(config)
  if key == lastAppliedCpuConfigKey or key == pendingCpuConfigKey:
    return
  pendingCpuConfigKey = key
  result = nativeBridge.cpuConfigureAsync(config)
  if result.accepted != true:
    clear pendingCpuConfigKey
  else if result.applied == true:
    lastAppliedCpuConfigKey = key
    clear pendingCpuConfigKey
  else:
    keep pendingCpuConfigKey until native callback

onNativeCpuConfigResult(result):
  if result.applied == true:
    lastAppliedCpuConfigKey = result.configKey
  if pendingCpuConfigKey == result.configKey:
    clear pendingCpuConfigKey
  if result.applied != true:
    log error and allow next broadcast to retry

nativeCpuConfigWorker(request):
  result = applyCpuConfig(request.configJson)
  # ASR/TTS 失败只加入错误汇总，仍然更新 llmCpuPolicy 并递增 LLM generation
  result.configKey = request.key
  result.applied = result.ok == true
  callback page on mainHandler with result
```

## 受影响的功能模块和代码

- `src/apps/android-display/app/src/main/java/com/aasc/display/NativeBridge.kt`：回传异步 CPU 配置实际应用结果。
- `src/apps/android-display/app/src/main/java/com/aasc/display/NativeBridge.kt`：隔离 ASR/TTS pool 失败，保证 LLM policy 仍更新。
- `src/apps/web-mediacenter/ui/public/display.html`：延后已应用去重确认并处理失败重试。
- `tests/apk-tts-page-freeze.test.js`：增加异步应用失败后允许重试的回归契约。
- `docs/design/android-display.md`、`docs/spec/android-display.md`、`docs/spec/android-mnnchat-llm.md`：同步确认/重试协议。

## 自测用例

1. `cpuConfigureAsync` 返回 accepted 但尚未 applied 时，页面仍保留 pending。
2. native 应用成功回调后，页面记录 lastApplied 并清理 pending。
3. native 应用失败回调后，页面清理 pending；再次收到同配置可以重新入队。
4. ASR/TTS 应用失败时，LLM policy 仍更新并可在下一次推理切换线程。
5. 配置成功时仍不重复构造 ASR/TTS pool。
6. LLM 推理期间配置变化仍由既有 runtime generation 和推理结束预检查处理。

## 兼容性测试

- 旧 APK 缺少 `cpuConfigureAsync` 时页面继续安全忽略。
- 旧页面未注册 `onNativeCpuConfigResult` 时原生配置仍可应用，不影响推理和语音。
- 服务器 `cpuConfig` 消息字段和 ASR/TTS 配置行为保持兼容。

## 性能测试

- 页面只增加一次轻量回调和 key 比较，不同步等待 native pool。
- 应用成功时不重复重建；失败时仅在后续相同配置到达后重试。

## 风险评估

- 页面关闭或 WebView 重载期间回调可能丢失，下一次连接初始化会重新发送权威配置。
- 多个配置快速到达时，页面必须按 `configKey` 匹配结果，不能清理较新的 pending 配置。
