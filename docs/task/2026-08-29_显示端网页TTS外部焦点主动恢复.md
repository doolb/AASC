# 显示端网页 TTS 外部音频焦点主动恢复

## 任务描述

修复 Android 显示端在网页 TTS 播放期间，其他 APK 播放视频抢占音频焦点后，TTS 被暂停且队列永久卡住的问题。保留网页 `<audio>` 播放方式，由 APK 原生焦点回调驱动网页主动恢复。

## design 需求

- TTS 播放前申请 APK 原生音频焦点。
- 焦点丢失、网页音频 `pause/stalled/waiting` 后保留当前句和播放位置，立即恢复并短延迟重试。
- 焦点恢复时立即再次播放，不重新生成、不重复取队列。
- stop、正常结束、页面销毁和不可恢复错误必须取消恢复，不能误播。

## spec 设计

- `AudioManager.OnAudioFocusChangeListener` → `NativeBridge` → `window.onNativeAudioFocusChanged(change)`。
- `display.html` 增加 TTS 当前项、恢复定时器和取消状态；TTS 与媒体播放的恢复状态分离。
- `ttsAudio.play()` 失败时保持当前项，使用单飞 100~200ms 重试；`ended` 后才推进队列。

## 自测用例

1. TTS 正常播放：仍按顺序播放，正常 `ended` 后进入下一句。
2. TTS 播放中触发 `pause`：当前句不丢失，恢复任务只启动一个。
3. 原生回调 LOSS/GAIN：立即调用网页恢复，不重复生成和取队列。
4. `tts stop` 后收到迟到的焦点回调：不重新播放。
5. 外部 APK 持续占用焦点：保留当前句并重试，不伪造 TTS 完成。

## 兼容性测试

- 浏览器显示端无 `NativeDisplay` 时保持原有网页播放行为。
- Android 8/API 26 及以上使用 `AudioFocusRequest`；旧 Android 使用兼容接口。
- 单段 TTS、连续多段 TTS、文本媒体 TTS 和普通 Chat TTS 均保留网页 `<audio>` 播放；普通 TTS 与文本媒体 TTS 使用各自的当前句状态，但共用原生焦点回调。

## 性能测试

- 焦点恢复立即尝试；播放被拒绝时重试间隔 100~200ms。
- 恢复过程不重新生成 WAV，不增加 TTS 推理耗时。
- 恢复定时器单飞，不因多个 pause/focus 回调累积任务。

## 实施结果

- 已完成：普通 TTS 和文本媒体逐句 TTS 播放前申请原生焦点；焦点丢失以及网页音频暂停、缓冲等待时主动恢复，150ms 单飞重试。
- 已完成：显式 stop、正常结束、切页和文本播放器失效时清理恢复定时器，迟到焦点回调不会重新播放。
- 验证：显示端焦点契约 6/6、文本媒体/集成回归 25/25 通过；内联脚本语法检查通过；`npm run build:apk` 成功。
- 真机限制：当前设备已有 `com.aasc.display` 使用旧签名 `bc24e5…`，本机旧私钥不存在；新构建使用当前 debug 签名 `a57fd4…`，因此未卸载旧 APK，避免丢失应用数据。原生焦点桥已存在于已安装 APK，本次网页逻辑可通过服务器页面重载验证。

## 风险评估

- 外部 APK 持续持有独占焦点时，系统可能拒绝网页 `play()`；只能持续等待，不能保证同时发声。
- 反复抢焦点可能影响外部视频，需限制为当前 TTS 存在时恢复，stop 后立即取消。
- WebView 可能只触发 `pause` 而不触发焦点回调，因此必须同时监听网页音频事件。
