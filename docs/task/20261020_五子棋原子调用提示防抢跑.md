# 五子棋原子调用提示防抢跑

日期：2026-10-20

## 任务描述

用户提供 A9/E7 对话记录：模型在 User A9 尚未得到 GM 回执时就预写 AI E7，随后又把 E7 误说成已确认。用户给出完整替换 `System:` 文本，要求强调需要等待确认或数据、以及需要状态确认的 User/AI 游戏操作都是原子操作，等待该调用行回复后才能发其他调用行。

## Design 需求与 Spec 设计

见 `docs/design/game-gomoku.md`、`docs/spec/game-gomoku.md`。保留用户所给提示的“回复开头最多 8 条”、目录与规则示例及原有第二段；只按原文增加原子等待措辞。游戏桥仍允许最多八条并兼容旧调用；若同一回复预写 User 与 AI 落子，只执行 User 行，GM 回执后让模型重新选择 AI 棋步。

## 受影响模块与代码

- `src/apps/server/modules/game/game-chat-bridge.js`：替换 `GAME_PROMPT` 为用户给出的完整文本正文。
- `tests/game-gomoku.test.js`：断言提示原文，复现 A9/E7 抢跑与 AI 漏调用后的权威纠正。
- 五子棋 design/spec/usage、todo、changelog；Offline 服务包状态。

## 自测、兼容性与性能

运行 `npm run test:game-chat`，覆盖新提示、旧尖括号、多调用解析、抢跑只确认 User 棋步、GM 状态续答。此项只改提示，不新增持久状态或网络接口；正常回合仍按原有 GM 续接次数运行。真实模型是否遵从原子等待需隔离 Qwen 和显示端现场复测。

## 风险与预计工时

提示可以降低抢跑概率，不能替代服务端校验。用户原文仍保留“最多 8 条”，模型可能继续在同次回复发多个调用行；桥接层必须继续丢弃未确认的预写 AI 行。预计约一小时。

## 执行结果

`npm run test:game-chat` 37/37 通过，包含 A9/E7 抢跑与漏 AI 调用后的 GM 纠正。首次全套运行时交互脚本因 3 秒启动等待超时，重跑通过。隔离真实 Qwen `aasc-qwen-flash` + “小爱”角色按正式 `chatStream` 发送用户原话“我下 A9。我继续下散子，你尽量连五获胜。”：模型先发 User A9，收到 GM 第 6 手确认后才发 AI E5，没有同回复抢跑；E5 已占用被 GM 拒绝，模型随后发 AI H8 并得到第 7 手确认。最终棋局仍在进行、轮到 User。该单次样本说明原子等待生效，但模型仍会选非法坐标且最终叙述没有说明 H8；真实两端与更多回合仍需验收。测试用的聊天历史和棋局都在临时目录，结束后清理。
