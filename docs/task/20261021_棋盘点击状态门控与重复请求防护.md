# 棋盘点击状态门控与重复请求防护

## 任务描述与 Design 需求

玩家快速点击棋盘可能提交多条消息。原页面只有布尔锁，同版本快照、无关错误或其他棋局广播会提前解锁；AI 已落子但本轮聊天尚未完成时，也可能启动下一轮。按用户确认方案，页面检查当前状态，服务端串行处理每个显示端的点击棋步。

## 需求分析

enterprise：结论可开发；主等级 L5（点击状态与请求生命周期），次等级 L6（请求与恢复契约）；置信度 0.68。证据为“当前状态才发送”（强 L5）、“避免一次多条消息”（强 L5）、确认方案中的“请求编号与服务端重复请求防护”（中 L6）。规则密度与跨端确认契约要求必须下放到 L4，能力等级 L5；清晰度24/25、证据18/20、完备度19/20、风险18/20、落地性14/15，总93/100。风险是旧广播误解锁及重连丢失在途状态，通过匹配请求和权威恢复处理。用户已确认实施，无需补充信息。

## Spec 设计（先于代码更新）

```text
已有声明 := 显示端棋局、对话状态、棋盘格和现有消息通道
新增定义 := 页面 pendingMove、recoveryRequestId；服务端按 displayId 保存处理中请求
检查活动对话、可见、玩家回合、空位、无提交及同步 → 锁定 requestId/gameId/revision → 只发送一次
收到普通棋盘广播 → 更新权威状态但不解锁；旧版本忽略
服务端验证身份及权威棋局 → 在途同编号仅回处理中，其余重复拒绝 → 用户落子成功只启动一次 AI
AI 完成或失败 → finally 清理请求锁 → 回对应 complete；页面再次按轮次和空位启用
重连或缺口 → 锁定独立恢复编号 → gameRecoverResult 返回快照与 pendingRequestId → 只应用匹配本次的恢复结果
```

## 受影响模块与代码

- `display-game.js`：统一可点击条件、请求锁、旧消息隔离和重连恢复。
- `server-app.js`：按显示端串行、重复请求拒绝、完成状态和恢复协议。
- `tests/game-move-request.test.js`：真实消息分支与真实棋局，控制 AI Promise 复现并发窗口。
- `tests/display-game-browser.test.js`：Chromium 真实页面快速点击、旧消息、重连和状态门控。
- `package.json`：现有 `test:game-chat` 纳入点击与浏览器回归；五子棋 design/spec/usage、todo、changelog 同步。

## 自测、兼容与性能

- `npm run test:game-chat`：56/56通过，零跳过，含原有会话、规则、GM、胜负与演示回归。
- 快速20次点击只提交一次；同版本/旧版本快照、无关错误和旧完成回包不能解锁；AI落子后仍等待聊天完成；处理失败释放服务端锁。
- 目标空位、AI回合、隐藏棋盘、非活动对话、同步和发送失败均验证；重连恢复处理中编号并向新连接返回完成。
- 旧客户端不带恢复编号时仍收到普通快照；新页面需与服务端同时更新，才能识别恢复结果与完成状态。
- 每次点击与恢复只增加常数次 Map 查询及状态消息；每显示端最多保留一个在途请求，完成后删除；不增加棋盘持久化次数。
- 服务端语法及差异检查通过；真实设备连点与断线恢复待更新后验收。
