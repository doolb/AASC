# ASR 与 TTS 优先大核开关

## 任务描述

为 APK 显示端的 ASR、TTS CPU affinity 配置增加两个独立开关，分别控制对应引擎是否优先使用大核，同时保持已配置的并发槽位总数。

## Design 需求

- 控制页提供 `ASR 优先大核`、`TTS 优先大核` 两个独立开关。
- 开关状态通过 `cpuAffinity` API、控制端广播和显示端 `cpuConfig` 消息完整透传。
- 开启时按“大核优先、小核补齐”选择 CPU；关闭时保持原有大核/小核数量精确分配。
- 缺少新字段的旧配置按关闭处理，保持兼容。

## Spec 设计

- 每个引擎配置增加布尔字段 `preferBigCores`，默认 `false`。
- `CpuTopology.policy(bigCoreCount, littleCoreCount, preferBigCores)` 开启时以数量总和为目标，先选大核再选小核。
- ASR 与 TTS 分别读取自己的开关，不共享状态，不改变 pool 的总槽位数。

## 自测用例

1. 服务端默认、缺失字段和非法布尔值校验。
2. 控制页两个开关的加载、保存和 WebSocket 广播回填。
3. CPU topology 开启优先大核时优先选择大核，不足时使用小核补齐。
4. 关闭开关时保持原有大核/小核精确选择。
5. Android JVM focused tests、APK 构建、安装和 display2 启动验证。

## 兼容性测试

- 旧配置缺少 `preferBigCores` 时默认关闭。
- 旧 APK 不识别新字段时继续按原有 CPU 数量配置运行。
- 浏览器控制端可以保存配置，浏览器显示端不依赖原生桥。

## 性能测试

- 开关仅改变 CPU policy 选择，不增加 TTS/ASR pool 槽位。
- 重复 `cpuConfig` 仍由现有异步去重和 policy 去重逻辑处理。

## 风险评估

- 设备大核数量不足时，开启开关可能实际使用小核补齐；返回的 policy 仍记录实际 CPU 列表和 fallback 状态。
- 大核优先可能提高功耗，故 ASR、TTS 分开提供开关。
