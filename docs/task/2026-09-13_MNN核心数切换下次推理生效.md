# MNN 核心数切换在下一次推理生效

## 任务描述

让控制端切换 LLM 大核/小核配置后，不打断当前 MNN 推理；当前请求完成后，下一条已接受的推理请求自动复用本地模型文件重建 MNN runtime，并以新的 CPU policy 线程数运行。

## design 需求

- CPU policy 更新只增加 generation，不立即释放当前 engine。
- 推理队列不绑定配置更新前的 engine；请求真正进入 native 前检查 generation。
- generation 不一致时等待当前串行请求结束，释放旧 engine，在同一 `active` 模型目录重新加载，不重新下载文件。
- 新 engine 加载成功后才清除 generation 差异；失败保留旧 engine 并让后续请求重试。
- ASR、TTS、模型协议和既有模型切换流程不改变。

## spec 设计

```text
applyCpuConfig:
  llmCpuPolicy = normalizedPolicy
  llmModelManager.onCpuPolicyChanged()

inferAsync(request):
  enqueue request without capturing currentEngine
  inference worker starts after earlier request completes
  if loadedPolicyGeneration != policyGeneration:
    candidate = load(activeDirectory, currentPolicy.threadCount)
    replace currentEngine only after candidate is ready
  generate request with candidate/current engine
```

## 受影响的功能模块和代码

- `src/apps/android-display/app/src/main/java/com/aasc/display/NativeBridge.kt`：CPU policy 更新后通知 LLM manager。
- `src/apps/android-display/app/src/main/java/com/aasc/display/MnnLlmModelManager.kt`：记录 policy generation，下一请求前按 active 缓存换代 engine。
- `tests/apk-llm-explicit-thread-count.test.js`：增加 policy 更新通知、请求不捕获旧 engine 和 runtime 换代契约。
- `docs/design/android-mnnchat-llm.md`、`docs/spec/android-mnnchat-llm.md`：同步下一请求生效规则。

## 自测用例

1. 推理进行中切换 2 核到 4 核，当前请求继续完成。
2. 当前请求完成后，下一请求触发同一模型目录的 engine reload，并使用 `thread_num=4`。
3. 只切换配置但没有模型时，不提前构造 native runtime；后续模型加载使用最新配置。
4. reload 失败时旧 engine 不被替换，后续请求仍可重试。

## 兼容性测试

- 配置未变化时不触发重复 reload。
- 模型切换与 CPU policy 变化同时发生时，保持现有模型切换串行和等待规则。
- ASR/TTS CPU 配置和线程池不受影响。

## 性能测试

- 配置变更后的第一条请求增加一次 native 模型加载耗时，模型文件不重复下载。
- 后续请求不重复 reload，线程数与最新 policy 一致。

## 风险评估

- reload 期间会短暂保留候选 engine 和旧 engine，失败时必须释放候选 engine。
- 线程数生效仍依赖 MNN runtime load；仅在 generate 前调用 `set_config` 不足以重建线程池。

## 预计工时

约 1 小时，包含队列状态调整、回归测试、APK 构建和真机请求验证。

## 实施结果

- 已完成 `cpuPolicyGeneration` / `loadedCpuPolicyGeneration` 代数管理；CPU 配置更新只通知 LLM manager，不打断当前 native 请求。
