# 临时对话在 TTS 全部播完后计时

日期：2026-10-18。状态：源码与定向测试完成，待显示端现场验收。

## 任务与证据

用户发现临时对话窗口在回复 TTS 尚未播完时开始倒计时。现场日志中，旧音频 `tts action=stop` 后约 55 毫秒即收到 `voiceConversationTtsFinished`，服务端随即记录“重新计时30秒”；新回复的 `chatResponse` 和多段音频仍在后续产生。服务端还会在某一段 `voiceTtsPlaybackFinished` 后播放集合暂空时恢复窗口。两个入口均缺少“回复仍在生成”状态。

## Design 与 Spec

保持临时窗口默认 30 秒及权威 `expiresAt` 协议。来源显示端开始语音回复时增加独立生成标记；普通聊天流覆盖 LLM 调用、TTS 调度器与全部音频下发回调，语音命令覆盖逐段生成区间。生成中集合和实际播放集合都为空，才按窗口类型重新完整计时。旧版队列完成事件须检查两个集合，并忽略对已运行计时器的重复回执。见 `docs/design/display-voice-conversation.md` 与 `docs/spec/display-voice-conversation.md` 的伪代码。

## 兼容、性能与风险

不改 WebSocket 消息字段、窗口配置或 Android 包。生成标记是进程内集合，断线清除；每个回复仅增加常数级 Map/Set 操作。若音频完成回执丢失，仍依赖现有播放超时释放；服务重启会清空运行中计时状态。真实设备需要验证长回复、打断和下一轮语音的倒计时。预计修改及离线回归约 1 小时，设备验收另计。
