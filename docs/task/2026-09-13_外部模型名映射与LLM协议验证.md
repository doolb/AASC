# 外部模型名映射与 LLM 协议验证

## 任务描述

为本地 LLM 网关增加外部模型名到内部 `modelId` 的映射，并使用 `qwen3.5-0.8b-claude-opus-distilled-mnn` 验证 Chat Completions 和 Responses 两种协议。

## design 需求

- 模型清单支持 `aliases`。
- 外部别名仅在主服务器网关入口解析；APK 和显示端继续使用内部模型 ID。
- 同一别名冲突时拒绝清单加载。
- `/v1/models` 返回内部 ID 和别名。
- 支持 `/v1/chat/completions`、`/v1/responses` 和 `/v1/chat/responses` 兼容入口。

## spec 设计

```text
请求 body.model
  -> LlmModelManifestService.resolveModelId
  -> LlmGatewayService.validateRequest
  -> router.resolveTarget(internalModelId)
  -> llm.request(modelId=internalModelId)
```

## 受影响的功能模块和代码

- `res/models/llm/manifest.json`：增加 Qwen3.5 外部别名。
- `src/apps/server/modules/llm/llm-model-manifest-service.js`：解析 aliases 和冲突校验。
- `src/apps/server/modules/llm/llm-gateway-service.js`：请求归一化和响应模型名处理。
- `src/apps/server/boot/server-app.js`：增加 `/v1/chat/responses` 兼容入口。
- `tests/llm-local-routing.test.js`：增加别名、冲突和两种协议契约测试。

## 自测用例

1. 使用外部名 `qwen3.5` 可以解析到 Qwen3.5 内部模型。
2. 内部 `modelId` 仍可直接请求。
3. Chat Completions 使用别名时路由消息携带内部 ID。
4. Responses 使用别名时路由消息携带内部 ID。
5. `/v1/chat/responses` 与 `/v1/responses` 使用相同协议处理器。
6. 别名冲突会返回清单错误，不覆盖已有映射。

## 兼容性测试

- APK 模型清单解析忽略新增 aliases 字段并继续使用内部 ID。
- 既有 `/v1/chat/completions` 和 `/v1/responses` 行为不变。
- 不改变模型下载、显示端选择和最短队列算法。

## 性能测试

- 别名解析使用内存清单查找，不增加显示端请求次数。
- 每个请求只做一次外部名到内部 ID 的归一化。

## 风险评估

- 风险：外部别名重复可能导致请求路由到错误模型。
- 控制：清单加载阶段建立唯一索引并对冲突直接失败。

## 预计工时

约 1 小时，含服务端重启、两种协议请求和错误分支验证。

## 实施结果

- Qwen3.5 增加外部别名 `qwen3.5` 和完整 ModelScope 展示名别名。
- 网关在路由前把外部名称归一化为内部 `modelId`，APK 和显示端仍只使用内部名称。
- 增加 `/v1/chat/responses` 到 Responses 处理器的兼容入口。
- `/v1/models` 已返回 aliases，别名冲突会保留 `MODEL_ALIAS_CONFLICT` 错误。

## 验证结果

- LLM 定向契约测试：9/9 通过。
- `npm run restart:server` 成功，`/v1/models` 返回 Qwen3.5 aliases。
- `qwen3.5` 调用 `/v1/chat/completions`：真实返回 200 和 `chat.completion`。
- 完整展示名别名调用 `/v1/responses`：真实返回 200 和 `response`。
- 内部 `qwen3.5-0.8b-claude-opus-distilled-mnn` 调用 `/v1/chat/responses`：真实返回 200 和 `response`。
- 测试前用 `npm run start:apk:display` 无参数启动显示端，模型切换最终达到 `state=ready`。
