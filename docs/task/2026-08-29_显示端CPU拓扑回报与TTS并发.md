# 显示端 CPU 拓扑回报与 TTS 并发

## 任务描述

读取 Display APK 实际可用的 CPU 拓扑和 TTS 生效槽位，回传服务端，并据此允许同一显示端最多两句 TTS 同时生成。

## design 需求

- APK 回报实际大核、小核、当前 policy 和 TTS 有效槽位。
- 服务端按显示端保存内存态 CPU 状态，断开后清除，不写入用户配置。
- TTS 生成最多并发两路；生成完成顺序不改变播放顺序。
- 仅包含标点的 TTS 分句直接跳过，不触发显示端失败和服务端回退。
- 浏览器显示端、旧 APK 和无状态显示端保持单路兼容。

## spec 设计

- 新增 NativeBridge.cpuStatus()，返回 topology、ASR policy、TTS policy。
- 新增 WebSocket cpuStatus 消息，服务端校验后写入 display state。
- 文本媒体、普通 Chat、旧版 Chat、手动 TTS 和 Agent TTS 按显示端 TTS 槽位建立双路生成通道，生成可以并行但发送/播放保持句序。

## 自测用例

1. APK cpuStatus 返回 topology、ASR policy 和 TTS policy。
2. 显示端首次连接和 CPU 配置应用后均回报 cpuStatus。
3. 服务端拒绝非法 CPU 状态，不覆盖已有有效状态。
4. TTS 槽位为 1 时保持串行，槽位为 2 或更多时最多两路并行。
5. 普通 Chat、手动 TTS 和 Agent 流式 TTS 均能双路生成。
6. 仅标点分句不调用 TTS，后续正文句仍能正常播放。
7. 两句生成完成顺序相反时，发送和播放顺序仍按句子序号。

## 兼容性测试

- 浏览器无 NativeDisplay 时不发送 cpuStatus。
- 旧 APK 不回报 CPU 状态时，服务端按单路默认处理。
- 控制端和显示端重连不复用已断开设备的 CPU 状态。

## 性能测试

- 两路 TTS 生成的总等待时间应接近较慢的一路，而不是两路耗时相加。
- 播放端仍只使用一个音频元素串行播放，不增加同时发声。
- 普通 Chat 和手动 TTS 的双句生成阶段不应因回调等待重新退化为串行。

## 风险评估

- CPU 槽位只代表实际生效的 native pool 容量，不保证两个任务一定线性加速。
- TTS SDK 或设备内存不足时，原生桥仍按已有有界队列拒绝或排队。
- 并发完成乱序必须由服务端/显示端句子序号处理，不能直接按回包顺序播放。
