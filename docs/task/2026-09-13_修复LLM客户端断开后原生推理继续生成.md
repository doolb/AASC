# 修复 LLM 客户端断开后原生推理继续生成

## 任务描述

客户端关闭流式 HTTP 连接后，服务端能够向显示端发送 `llm.cancel`，但 Android JNI 的 `nativeCancel()` 当前为空实现，MNN 仍继续生成；排队请求也可能在断开后开始。本任务补齐从 HTTP、WebSocket、Kotlin 到 JNI/MNN 回调的 requestId 取消链路。

## Design 需求

- 客户端断开只取消对应 requestId。
- 排队中的请求不得在取消后启动。
- 执行中的请求在下一个 MNN token 回调边界停止。
- 取消请求不释放仍在使用的模型 session，不影响 ASR/TTS 和其他请求。
- 取消后不发送 `llm.completed`，服务端释放路由计数。

## Spec 设计

```text
server:
  response close -> llmGatewayService.cancel(requestId)
  cancel sends llm.cancel to display and releases HTTP route

APK:
  pendingInferenceIds tracks queued and active requests
  cancelledRequestIds tracks cancellation until worker cleanup
  activeRequestId identifies the native request
  cancel(requestId) marks cancelled and calls engine.cancel for active request

JNI:
  each native session owns an atomic cancel flag
  nativeCancel sets the flag
  ResponseWithHistory callback returns true when the flag is set
```

## 受影响的功能模块和代码

- `src/apps/android-display/app/src/main/cpp/aasc_mnn_jni.cpp`：实现 session 级原子取消标志。
- `src/apps/android-display/app/src/main/java/com/aasc/display/MnnLlmEngine.kt`：保留 native 取消入口并更新说明。
- `src/apps/android-display/app/src/main/java/com/aasc/display/MnnLlmModelManager.kt`：按 requestId 管理排队/执行/取消状态，抑制取消后的完成回调。
- `docs/design/android-mnnchat-llm.md`、`docs/spec/android-mnnchat-llm.md`：同步取消契约。

## 自测用例

1. 流式 HTTP 客户端断开后服务端发送 `llm.cancel`。
2. APK 排队请求在取消后不调用 native generate。
3. APK 执行中的请求收到取消后不发送 `llm.completed`。
4. JNI 回调检测取消标志并停止后续 token。
5. 取消后 active/queue 计数归零，模型切换等待可以继续。
6. 正常完成、非流式请求和 ASR/TTS 不受影响。

## 兼容性测试

- Android API 26+ arm64-v8a Debug APK。
- Qwen3.5 MNN 模型真实推理。
- curl、`chatv2.py` 流式请求中断。
- 服务端 `/v1/chat/completions` 和 `/v1/responses`。

## 性能测试

- 取消仅在下一个 token 回调边界生效，不增加正常请求轮询。
- 取消后不保留 requestId、队列计数或 native session 临时状态。

## 风险评估

- 官方 MNN 没有公开的强制中断接口，取消粒度为 token 回调边界；prefill 或单个 native 算子完成前可能仍短暂占用 CPU。
- JNI 取消标志必须与 session 生命周期同步，避免释放后的指针访问。
